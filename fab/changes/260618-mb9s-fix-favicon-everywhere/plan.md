### Favicon: Valid multi-resolution ICO (Fix 3 — root-cause)

- **AND** assembles a valid ICO container embedding all three PNG frames
- **AND** writes the bytes to `public/favicon.ico`, with no new dependency introduced

### Non-Goals

- **Redirect-page rewrite (former "Fix 2") — dropped.** Headless routes (incl. the
  7 redirect stubs) take their tab icon from the root `/favicon.ico` fallback, which
  R2/R3 fix. No `src/pages/` redirect rewrite; the `redirects:` block stays intact.
- **No `package.json` dependency change.** `sharp` is already present; the
  hand-assembled ICO needs no encoder dependency (Constitution VI).
- **No `seo-social-meta` memory edit.** The stubs are untouched, so the `kb1r`
  og:image invariant holds verbatim (no memory cascade).
- **No README edit.** Line 41 (`favicon.{svg,ico}`) stays accurate (filename/purpose
  unchanged). The conditional repo-layout note for the new script is low-priority and
  not taken (Assumptions #5 / intake §4).

### Design Decisions

1. **Hand-assembled PNG-in-ICO container**: write a 6-byte ICONDIR, three 16-byte
   ICONDIRENTRYs, then the three `sharp`-produced PNG payloads — *Why*: the ICO format
   permits a directory entry to carry a PNG-encoded image directly, so no ICO-encoder
   dependency is needed (Constitution VI) — *Rejected*: adding `png-to-ico`/`to-ico`
   (new build dep, violates VI); using BMP/DIB frames (more complex, larger, no benefit
   for 16/32/48).
2. **Rasterize with `sharp` directly from SVG**: `sharp(svgPath).resize(n,n).png()` —
   *Why*: `sharp` is already a dependency and rasterizes SVG natively at exact pixel
   sizes — *Rejected*: headless-Chromium screenshot (the og-image approach) — heavier
   and unnecessary for a flat vector icon; `sharp` is the lighter, already-present tool.
