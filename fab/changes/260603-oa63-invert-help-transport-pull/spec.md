## Non-Goals

- **Schema enrichment / richer command-reference UI** — the explicit FOLLOW-ON change. `schema_version` stays `1`; no new fields are added here. The pull model exists precisely to give that follow-on a single contract to iterate against.
- **The actual teardown of push producers in the 7 tool repos** (producer CI, PR-opening, auto-merge wiring, `SHLLAI_TOKEN`) — that is tool-repo work. This change only DOCUMENTS the teardown instruction and its safety precondition; it executes none of it.
- **Adding the `help-dump` subcommand to tools** — it ALREADY exists, uniform across the 7 tools (`tu`'s is in progress). This change consumes it; it does not author it.
- **Any change to `CommandReference.astro`, `src/lib/schemas.ts`, `validate-help.mjs`, `astro-content-alias.mjs`, or `deploy.yml`** — these are transport-agnostic and stay untouched.

- **GIVEN** the contract's §Overview

### Requirement: §1 Invocation — uniform STDOUT JSON envelope, exit-coded

The contract §1 SHALL specify that `<tool> help-dump` is uniform across all 7 tools, emits a JSON envelope to **STDOUT**, leaves **stderr empty on success**, and exits **0** on success. A non-zero exit MUST be defined as a hard error that the puller treats as a failed capture for that tool.

#### Scenario: Successful invocation
- **GIVEN** a tool with `help-dump`
- **WHEN** `<tool> help-dump` runs successfully
- **THEN** a single JSON envelope is written to stdout, stderr is empty, and the exit code is 0

#### Scenario: Failed invocation
- **GIVEN** a tool whose `help-dump` errors
- **WHEN** it runs
- **THEN** it exits non-zero, which the puller MUST treat as a failed capture for that tool (see per-tool failure isolation below)

### Requirement: §2 `help-dump` is hidden and self-filtering

The contract §2 SHALL require `help-dump` to be `Hidden: true` (Cobra) so it never appears in the tool's own `-h`, AND to filter ITSELF out of the emitted tree. Because it is a `Hidden` node, the existing §4 filter rule (drop any `Hidden` node) MUST cover it — no special-case logic.

#### Scenario: help-dump does not appear in its own output
- **GIVEN** a tool whose `help-dump` is `Hidden: true`
- **WHEN** `<tool> help-dump` emits the tree
- **THEN** no node named `help-dump` appears anywhere in `root.commands` (it is dropped by the §4 `Hidden`-node filter)
- **AND** `help-dump` does not appear in `<tool> -h`

### Requirement: §3 Output schema — envelope + recursive Node, with the `captured_at` asymmetry

The contract §3 SHALL reproduce the envelope and recursive Node verbatim so the doc is self-contained, and SHALL state the critical asymmetry: **`captured_at` is shll.ai-OWNED**. The `help-dump` output MUST NOT include `captured_at`; the puller stamps it at capture time.

- **TOOL-EMITTED shape** = `{tool, version, schema_version, root}` — no `captured_at`.
- **VALIDATED POST-CAPTURE file** (what `schemas.ts` validates) = the above PLUS `captured_at`.
- `Node = {name, path, short, usage, text, commands: Node[]}`, recursive; a leaf has `commands: []`. Every node carries the raw `text` AND the structured `short`/`usage`/`path`.

The post-capture envelope reproduced in the contract MUST match `sites/astro-starlight-terminal1/src/lib/schemas.ts` (where `captured_at` is REQUIRED and `schema_version` is `z.literal(1)`):

```jsonc
{
  "tool": "wt",                          // invoked binary name (wt, rk, fab) — not the file slug
  "version": "1.4.2",                    // from the built binary (ldflags / rootCmd.Version)
  "captured_at": "2026-06-02T00:00:00Z", // ISO-8601 UTC — STAMPED BY THE PULLER, NOT emitted by the tool
  "schema_version": 1,                   // integer; current = 1
  "root": { "name": "wt", "path": "wt", "short": "…", "usage": "…", "text": "…", "commands": [ /* Node[] */ ] }
}
```

#### Scenario: Tool emits everything except captured_at
- **GIVEN** the contract §3
- **WHEN** a tool author reads what `help-dump` must emit
- **THEN** the tool-emitted shape is `{tool, version, schema_version, root}` with NO `captured_at` line
- **AND** the asymmetry is stated explicitly: the puller adds `captured_at` post-capture so the file conforms to `schemas.ts`

#### Scenario: Post-capture file conforms to the Zod anchor
- **GIVEN** a captured `help/<slug>.json` after the puller has stamped `captured_at`
- **WHEN** validated against `HelpDocSchema` in `src/lib/schemas.ts`
- **THEN** it passes — the required `captured_at` (`z.string()`) is present and `schema_version` is the literal `1`

### Requirement: §4 Filter rules

The contract §4 SHALL require dropping Cobra's auto-generated `completion` and `help` subcommands, and any `Hidden` node (which now INCLUDES `help-dump` itself, per §2).

#### Scenario: Noise nodes are filtered

- **WHEN** `help-dump` walks it

### Requirement: §5 Discovery & recursion — programmatic, never regex

The contract §5 SHALL require walking `rootCmd.Commands()` programmatically with full recursion to any depth, and SHALL forbid regex-parsing `-h` text to discover structure.

#### Scenario: Tree discovered by walking, recursively

### Requirement: §6 Version from the built binary

The contract §6 SHALL require reading `version` from the built binary (ldflags / `rootCmd.Version`); it MUST NOT be hardcoded. The committed `wt.json` sample uses the placeholder `1.4.2` because a plain `go build` reports `dev`; real producers inject the true version.

#### Scenario: Version is not hardcoded

## CI Workflow: `.github/workflows/scheduled-help-refresh.yml`

A NEW GitHub Actions workflow in shll.ai — the puller. It replaces the deleted `help-automerge.yml` as the inbound path for `help/*.json`.

### Requirement: Triggers are scheduled (daily) plus manual dispatch

The workflow SHALL trigger on `schedule` (a DAILY cron) and on `workflow_dispatch` (manual, for on-demand refreshes after a tool release). It MUST NOT add any new trigger to the deploy path.

#### Scenario: Daily and on-demand
- **GIVEN** the workflow
- **WHEN** its triggers are inspected
- **THEN** it has a `schedule:` cron firing once per day AND `workflow_dispatch`
- **AND** no `push`/deploy trigger is added (deploy stays the existing `deploy.yml` push-to-`main`)

### Requirement: Capture pipeline — brew install, help-dump, stamp, validate, commit

For each of the 7 tools the workflow SHALL:
1. install the tool via `brew install sahil87/tap/<tool>`,
2. run `<tool> help-dump`, capturing **stdout** to `help/<slug>.json` (file named by slug; the `tool` field inside carries the binary name — e.g. `help/run-kit.json` holds binary `rk`, `help/fab-kit.json` holds binary `fab`),
3. **stamp `captured_at`** (ISO-8601 UTC) into each captured file — the shll.ai-owned field the tool does not emit (§3 asymmetry),
4. validate every file with the EXISTING `sites/astro-starlight-terminal1/scripts/validate-help.mjs` on the pinned pnpm 10 + Node 22 toolchain (reusing `deploy.yml`'s `pnpm/action-setup@v4` version 10 + `actions/setup-node@v4` node-version 22 + `pnpm install --frozen-lockfile` pattern, with `cache-dependency-path` keyed on the live site's `pnpm-lock.yaml`),
5. commit `help/*.json`.

#### Scenario: A tool is captured and stamped
- **GIVEN** `wt` is installed via brew and `wt help-dump` succeeds
- **WHEN** the workflow captures its stdout
- **THEN** `help/wt.json` holds the tool-emitted `{tool, version, schema_version, root}`
- **AND** the workflow stamps a `captured_at` ISO-8601 UTC value into the file so it conforms to `schemas.ts`

#### Scenario: Validator is reused unchanged
- **GIVEN** the captured `help/*.json` files
- **WHEN** the workflow validates them
- **THEN** it invokes the existing `node scripts/validate-help.mjs` from `sites/astro-starlight-terminal1` on the pinned pnpm 10 + Node 22 toolchain
- **AND** `validate-help.mjs`, `astro-content-alias.mjs`, and `schemas.ts` are not modified

### Requirement: Commit mechanism — direct commit to `main`, gated on validation

The workflow SHALL DIRECT-COMMIT `help/*.json` to `main`, with the commit step GATED on `validate-help.mjs` passing in the same job, so a malformed capture never reaches `main` (never-commit-a-regression). It MUST NOT open a PR, enable auto-merge, or use `SHLLAI_TOKEN`. Direct commit is sound because the committer is a single trusted cron — dissolving the PR-race and the three-guard hazard that justified PR+auto-merge under push. The accepted tradeoff is that help changes ship unreviewed (the binary's own `-h` is the authority, output is schema-validated pre-commit, and merging fires the existing deploy under Constitution IV).

#### Scenario: Valid capture commits to main
- **GIVEN** all captured files pass `validate-help.mjs`
- **WHEN** the workflow reaches the commit step
- **THEN** it commits `help/*.json` directly to `main` (no PR, no auto-merge, no `SHLLAI_TOKEN`)
- **AND** the existing `deploy.yml` push-to-`main` deploy ships the updated help

#### Scenario: Malformed capture is blocked
- **GIVEN** a captured file fails `validate-help.mjs`
- **WHEN** the workflow runs
- **THEN** the commit step is gated off and the malformed file never reaches `main`

### Requirement: Off the deploy path (load-bearing)

The refresh job SHALL be deliberately separate from `deploy.yml`, so a flaky brew tap or a broken tool release breaks the REFRESH, not the landing-page deploy. `deploy.yml` MUST stay UNTOUCHED and toolchain-free on the deploy path. The site MUST keep shipping last-good committed help even if a tool release breaks. When the refresh commits to `main`, the existing `deploy.yml` push-to-`main` deploy ships it — no new deploy trigger.

#### Scenario: Broken tool release does not break deploy
- **GIVEN** a tool release that breaks `help-dump` or an unavailable brew tap
- **WHEN** the scheduled refresh runs and fails
- **THEN** `deploy.yml` is unaffected and the site continues to deploy the last-good committed help
- **AND** `deploy.yml` is byte-identical to its pre-change state (no toolchain coupling added to the deploy path)

### Requirement: Per-tool capture-failure isolation — never clobber last-good

A **capture failure** for one tool — a failed `brew install`, a non-zero `help-dump` exit, empty output, or non-JSON output — MUST NOT clobber that tool's last-good committed `help/<slug>.json`, and MUST NOT prevent the other tools from capturing. The refresh MUST keep the previously committed file rather than overwrite it with bad/empty content. The principle is: never commit a regression. A missing `help/tu.json` is the expected interim state (§7), NOT a failure.

**Scope of isolation (capture-level, not schema-level).** Isolation applies to *capture* failures (the four cases above), which are caught per-tool in the capture loop so one bad tool does not poison the others. **Schema validity is enforced collectively, not per-tool**: after capture, the existing whole-directory validator (`validate-help.mjs`) runs once over all `help/*.json` and gates the commit (see Validation-gate requirement). If a tool emits *structurally valid JSON that is schema-invalid* (e.g. a missing `root` or wrong `schema_version` — output that passes the per-tool JSON guard but fails the Zod schema), the whole-directory gate fails and the **entire commit is skipped that run** — including the other tools' fresh captures. This is an accepted tradeoff: the safety invariant (never commit a regression — a schema-invalid file never reaches `main`) is preserved, and the cost is bounded *freshness*, not correctness — the site keeps shipping last-good for **every** tool and the run self-heals once the offending tool is fixed. A per-tool schema-validation path (validating each stamped file individually before staging it) was considered and rejected as added workflow complexity not justified for a single-trusted-cron puller. <!-- clarified: schema-invalid (but valid-JSON) output gates the whole commit, not just that tool — accepted freshness-over-complexity tradeoff; safety (never-commit-a-regression) preserved. Per-tool schema validation rejected. -->

#### Scenario: One tool's capture fails, others succeed
- **GIVEN** 6 tools capture successfully and 1 tool's `help-dump` fails to capture (failed `brew install`, non-zero exit, empty output, or non-JSON output)
- **WHEN** the refresh runs
- **THEN** the failing tool's last-good committed `help/<slug>.json` is preserved unchanged
- **AND** the 6 successful captures still commit (the failing tool is skipped in the capture loop, so the whole-directory validation still passes)

#### Scenario: One tool emits schema-invalid (but valid-JSON) output
- **GIVEN** 6 tools capture valid output and 1 tool emits structurally valid JSON that fails the Zod schema
- **WHEN** the refresh runs
- **THEN** the whole-directory validator fails the job and the commit is skipped for **all** tools that run
- **AND** every tool keeps its last-good committed `help/<slug>.json` (a schema-invalid file never reaches `main` — safety preserved; freshness deferred to the next run)

#### Scenario: Missing tu is tolerated
- **GIVEN** `tu`'s `help-dump` is not yet available (no `help/tu.json`)
- **WHEN** the refresh runs
- **THEN** the absence is treated as the expected interim state, not a failure, and the run still commits the other tools' files

## Design Decisions

1. **Pull via a scheduled refresh job, deliberately OFF the deploy path**: a `schedule` + `workflow_dispatch` workflow brew-installs the tools, runs `help-dump`, stamps `captured_at`, validates, and commits.
   - *Why*: a flaky brew tap or broken tool release must break the REFRESH, not the landing-page deploy; the site keeps shipping last-good committed help. Preserves Constitution I's spirit (no build-toolchain coupling on deploy) and IV (deploy still fires only on push to `main`).
   - *Rejected*: pulling at build time inside `deploy.yml` — couples the deploy to remote tool availability and a Go/Node toolchain on the deploy path; violates Constitution I's spirit and IV.

2. **Direct commit to `main`, gated on `validate-help.mjs`**: the cron commits `help/*.json` straight to `main`, but only after the validator passes in the same job.
   - *Why*: the committer is a single trusted cron, which dissolves the PR-race and the three-guard hazard that justified PR+auto-merge under push; gating on the existing validator preserves never-commit-a-regression. Accepted tradeoff: help ships unreviewed (the binary's own `-h` is the authority; output is schema-validated pre-commit).
   - *Rejected*: PR + auto-merge — the entire apparatus existed only to serialize 7 external pushers and guard unattended-merge-to-prod; a single trusted cron needs none of it.

3. **`captured_at` is shll.ai-owned (the §3 asymmetry)**: tool output excludes `captured_at`; the puller stamps it post-capture.
   - *Why*: a tool's `help-dump` cannot know the capture time; `schemas.ts` requires `captured_at`, so the post-capture file must add it. Keeps the tool contract minimal (`{tool, version, schema_version, root}`).
   - *Rejected*: making the tool emit `captured_at` — pushes a shll.ai-owned concern into 7 repos and is not knowable at emit time.

4. **Spec owns the contract; memory consumes it (resolution (a))**: the new spec `help-dump-contract.md` owns the schema/prose; `help-collection.md` is rewritten DOWN to consume/pull and cross-links the spec.
   - *Why*: schema defined in ONE prose place (the spec) plus the `schemas.ts` code anchor — not two prose places that can drift.
   - *Rejected*: keeping the full contract in memory and adding a second copy in the spec — guarantees prose-vs-prose drift.
