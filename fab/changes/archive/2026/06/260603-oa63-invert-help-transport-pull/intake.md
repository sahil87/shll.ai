# Intake: Invert help-collection transport from PUSH to PULL

## Origin

> [Internal dispatch from `/fab-proceed` → `/fab-new`.] refactor: invert the help-collection transport from PUSH to PULL. The synthesized description below was fully decided across a prior multi-turn discussion with the user; all design decisions are confirmed, so this intake encodes them as Certain/Confident assumptions and asks zero clarifying questions.

This change inverts the transport mechanism established by the merged help-collection contract (change `xiis`) and extended by the rendering consumer (change `js1s`). Today the 7 toolkit repos PUSH help JSON into shll.ai via PR + auto-merge; this change makes shll.ai PULL it via a scheduled refresh job. It is a deliberate setup for a separate follow-on change that will ENRICH the JSON schema for a richer command-reference UI — schema evolution is painful under push (a 7-way flag-day across repos on different Cobra versions), so the pull model gives a single contract document to iterate against. THIS change is the transport inversion only; schema enrichment is explicitly out of scope.

The decisions below were all confirmed with the user during the prior discussion (recorded in the Assumptions table with that provenance).

## Why

**The problem with the current PUSH model.** Per the merged `xiis` contract, each of the 7 toolkit repos (`idea`, `hop`, `fab-kit`, `wt`, `run-kit`, `tu`, `shll`) runs CI producer code that walks its Cobra command tree, writes `help/<slug>.json`, and opens a PR into `sahil87/shll.ai` with auto-merge enabled (using the `SHLLAI_TOKEN` secret). shll.ai receives these via `.github/workflows/help-automerge.yml`, which gates auto-merge behind three guards (content / schema / actor) — required precisely because the repo is **public**, `main` is **unprotected**, and merging **auto-deploys** (`deploy.yml`). This push model is structurally complex:

1. **7-way coordination** — producer logic copy-pasted across 7 repos, each on its own Cobra version and release cadence.
2. **Tokens in 7 repos** — `SHLLAI_TOKEN` provisioned and scoped in every tool repo.
3. **PR-race-on-main reasoning** — direct push from 7 repos would race on `main`; PR + auto-merge exists to serialize, adding a workflow whose whole job is to reason about that race.
4. **Unattended-auto-merge-to-production hazard** — the entire three-guard apparatus exists only because a mixed or schema-invalid PR could otherwise ship to production unattended.

**Why invert it.**

1. **Simplify the release pipeline** — delete the per-repo producer CI, PR-opening, auto-merge wiring, and `SHLLAI_TOKEN` usage from all 7 tool repos. A tool author's ONLY remaining obligation becomes: keep `help-dump` emitting valid output.
2. **Narrow the cross-repo contract to ONE surface** — the output of the `help-dump` command. No transport, no tokens, no auto-merge timing to reason about.
3. **The forcing function for the follow-on** — the NEXT change (separate) will ENRICH the JSON schema. Under push, every schema growth is a 7-way flag-day across repos on different Cobra versions. The pull model gives a single contract document to iterate against plus a fast local iteration loop.

**What happens if we don't.** The push apparatus persists: 7 tokens, 7 producer pipelines, a public-repo auto-merge-to-prod hazard, and a schema that can only evolve via a coordinated 7-repo flag-day. The follow-on enrichment becomes substantially harder.

**Why this approach over alternatives.** The pull mechanism is a **SCHEDULED refresh job, deliberately OFF the deploy path** (rejected: pulling at build time inside `deploy.yml`, which would couple the landing-page deploy to a flaky brew tap or a broken tool release, violating Constitution I's spirit and IV). Keeping refresh off the deploy path means the site keeps shipping last-good committed help even if a tool release breaks.

## What Changes

This change touches shll.ai ONLY. The actual teardown of push producers in the 7 tool repos is tool-repo work (out of scope — this change only DOCUMENTS the teardown instruction and its safety precondition).

### 1. New spec `docs/specs/help-dump-contract.md` (the single forward contract)

This is the one document the 7 tool repos reference forever for what `help-dump` must emit. It is a **spec**, not memory. Structure: evergreen sections §1–§8 plus one bounded, dated migration section, plus an Overview and a Schema-reference cross-link.

- **§Overview** — states the tool's single obligation: "emit valid `help-dump` output; everything downstream is shll.ai's job." Anti-drift framing (the same anti-drift intent as the original contract — help is machine-generated by the binary, never hand-maintained).
- **§1 Invocation** — `<tool> help-dump`, uniform across all 7 tools. Emits a JSON envelope to **STDOUT**; **stderr empty on success**; **exit 0** on success (non-zero exit = a hard error the puller must treat as a failed capture for that tool).
- **§2 Hidden from `-h` (required nuance)** — `help-dump` MUST be `Hidden: true` (Cobra) so it never appears in the tool's own `-h`; AND it MUST filter ITSELF out of the emitted tree (it is now a `Hidden` node, so the existing filter rule in §4 covers it).
- **§3 Output schema** — reproduce the envelope + recursive Node verbatim so the doc is self-contained. **CRITICAL asymmetry: `captured_at` is shll.ai-OWNED.** The help-dump output does NOT include `captured_at`; the puller stamps it at capture time. So:
  - **TOOL-EMITTED shape** = `{tool, version, schema_version, root}` (no `captured_at`).
  - **VALIDATED POST-CAPTURE file** (what `schemas.ts` validates) = the above PLUS `captured_at`.
  State this asymmetry explicitly. `Node = {name, path, short, usage, text, commands: Node[]}`, recursive; a leaf has `commands: []`; every node carries the raw `text` AND the structured `short`/`usage`/`path`.

  Reproduce, for self-containment, the post-capture envelope (matching `sites/astro-starlight-terminal1/src/lib/schemas.ts`):
  ```jsonc
  {
    "tool": "wt",                          // invoked binary name (wt, rk, fab) — not the file slug
    "version": "1.4.2",                    // from the built binary (ldflags / rootCmd.Version)
    "captured_at": "2026-06-02T00:00:00Z", // ISO-8601 UTC — STAMPED BY THE PULLER, NOT emitted by the tool
    "schema_version": 1,                   // integer; current = 1
    "root": { "name": "wt", "path": "wt", "short": "…", "usage": "…", "text": "…", "commands": [ /* Node[] */ ] }
  }
  ```
  The tool emits everything EXCEPT the `captured_at` line.
- **§4 Filter rules** — drop Cobra's auto-generated `completion` and `help` subcommands, and any `Hidden` node (this now INCLUDES `help-dump` itself, per §2).
- **§5 Discovery & recursion** — walk `rootCmd.Commands()` programmatically; NEVER regex-parse `-h` to discover structure; full recursion to any depth.
- **§6 Version** — read from the built binary (ldflags / `rootCmd.Version`); never hardcoded. (The committed `wt.json` sample uses placeholder `1.4.2` because a plain `go build` reports `dev`; real producers inject the true version.)
- **§7 The `tu` exception** — `tu` is Node/TS and flag-based with no subcommands → a flat tree (`root.commands: []`), with the full `tu --help` output in `root.text`. **`tu`'s help-dump is IN PROGRESS, so `help/tu.json` may be MISSING during rollout — the consumer already degrades MISSING to a placeholder, so this is fine.** (Confirmed by current repo state: `help/tu.json` is absent; 6 of 7 files present.)
- **§8 Schema evolution** — `schema_version` is an integer; current = **1**. New fields MUST be added as **OPTIONAL** so tools can roll them out one at a time without a flag-day. (This section sets up the follow-on enrichment change.)
- **§Pull model — no push required (BOUNDED, DATED migration section)** — states that as of 2026-06-03 shll.ai pulls via `help-dump` and the push model is retired. Lists exactly what each tool repo can now DELETE:
  - the CI producer code (Cobra tree-walk + JSON write),
  - the PR-opening step,
  - the auto-merge wiring,
  - the `SHLLAI_TOKEN` secret/usage (user confirmed the token can be deleted).
  Carries the safety precondition: **this teardown is only actionable because the puller is already live and proven** (see the Sequencing risk in Impact). Note this section can collapse into the changelog once all 7 repos finish teardown.
- **§Schema reference** — point to `sites/astro-starlight-terminal1/src/lib/schemas.ts` as the single machine-checkable anchor; prose-vs-code MUST agree; cross-link both ways (spec ↔ schemas.ts).

Also: **add an entry to the specs index** `docs/specs/index.md` (currently has an empty table) for this new spec.

### 2. New workflow `.github/workflows/scheduled-help-refresh.yml`

A new GitHub Actions workflow in shll.ai. Triggers: **`schedule`** (cron) + **`workflow_dispatch`** (manual). It:
1. Installs the 7 tools via `brew install sahil87/tap/<tool>` (one per tool).
2. Runs the uniform `<tool> help-dump` subcommand for each, capturing **stdout** to `help/<slug>.json` (file named by slug; the `tool` field inside carries the binary name, e.g. `help/run-kit.json` holds binary `rk`, `help/fab-kit.json` holds binary `fab`).
3. **Stamps `captured_at`** (ISO-8601 UTC) into each captured file — this is the shll.ai-owned field the tool does not emit (§3 asymmetry).
4. Validates every file with the EXISTING validator `sites/astro-starlight-terminal1/scripts/validate-help.mjs` (run on the pinned pnpm 10 + Node 22 toolchain, reusing `deploy.yml`'s setup pattern).
5. Commits `help/*.json`.

**Commit mechanism = DIRECT COMMIT to `main`, gated on validation** (user-confirmed). The cron commits `help/*.json` straight to `main`, but the commit step is gated on `validate-help.mjs` passing in the same job (per the never-commit-a-regression principle in this section and assumption #12) — a malformed capture never reaches `main`. Direct commit is sound here because the committer is a single trusted cron (not 7 external repos), which dissolves the PR-race and the three-guard hazard that justified PR+auto-merge under push. The tradeoff accepted: help changes ship unreviewed — acceptable because the source (the binary's own `-h`) is itself the authority, the output is schema-validated before commit, and merging fires the existing deploy (Constitution IV). <!-- clarified: direct commit to main, gated on validate-help.mjs passing -->
**Cadence = DAILY** (`schedule:` cron, once per day) plus always-available `workflow_dispatch` for on-demand refreshes after a tool release. <!-- clarified: daily cron + workflow_dispatch -->

**OFF the deploy path (load-bearing).** The refresh job is deliberately separate from `deploy.yml` so that a flaky brew tap or a broken tool release breaks the REFRESH, not the landing-page deploy. The site keeps shipping last-good committed help. This preserves Constitution I's spirit (no build-toolchain coupling on the deploy path) and IV (deploy still fires only on push to `main` via the existing workflow). When the refresh job commits to `main`, the existing `deploy.yml` push-to-`main` deploy ships the updated help — no new deploy trigger is added (Constitution IV).

**A failed capture for one tool MUST NOT clobber that tool's last-good committed file** — if `<tool> help-dump` exits non-zero, or its output fails validation, the refresh keeps the previously committed `help/<slug>.json` rather than overwriting it with bad/empty content. (Spec to specify exact per-tool failure handling; the principle is: never commit a regression.) `tu` may legitimately have NO file yet (§7) — a missing `help/tu.json` is the expected interim state, not a failure.
