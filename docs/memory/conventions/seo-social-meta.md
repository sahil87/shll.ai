# SEO & Social-Share Meta

## Overview

How the live site (`sites/astro-starlight-terminal1`) presents in link previews (Slack, Discord, X, LinkedIn, iMessage) and search snippets. Established by change `kb1r` (2026-06-10), grounded in a live-`<head>` audit of production shll.ai.

**Division of labor — Starlight baseline + a thin site layer.** Starlight already emits ~80% of SEO hygiene by default on every page: canonical URL, `sitemap-index.xml` (referenced from `robots.txt`), per-page `<title>` + meta description, `og:title`, `og:type`, `og:url`, `og:locale`, `og:description`, `og:site_name`, and `twitter:card=summary_large_image`. The site adds only what Starlight does not: the social-share **image** meta (site-wide, via the `Head.astro` override), homepage-specific `<title>`/`og:title`/`og:type` overrides (frontmatter), and homepage JSON-LD. **Before adding any head tag, check the baseline** — the og:image set could be blindly appended after `<Default />` precisely because Starlight emits no `og:image`/`twitter:image` of its own (no dedupe concern); a tag Starlight *does* emit must instead go through a dedupe-aware mechanism (see the homepage overrides below). Everything here is build-time static markup — no client JS, no dependencies (Constitution I, VI).

## Site-wide og:image set (`Head.astro`)

`src/components/Head.astro` (the registered `components.Head` override — pattern + escaping gotcha documented in [tool-page-rubric → site chrome overrides](/conventions/tool-page-rubric.md#site-chrome-overrides-header-logo-footer-head-change-i2b0)) appends after `<Default />`, on every rendered page:

- `og:image` — **absolute** URL (`https://shll.ai/og-image.png`). OG scrapers do not resolve relative URLs, so absoluteness is load-bearing. The URL derives from `Astro.site` (`new URL('/og-image.png', Astro.site)`), never hardcoded — `site: 'https://shll.ai'` in `astro.config.mjs` is the single origin source.
- `og:image:width` 1200 / `og:image:height` 630 / `og:image:alt` (the tagline).
- `twitter:image` — same absolute URL; this is what makes the already-declared `twitter:card=summary_large_image` actually render an image instead of a bare text card (pre-`kb1r`, the asset existed but no meta referenced it).

**Redirect stubs are excluded — deliberately, not a defect.** Astro `redirects:` emit `noindex` meta-refresh stubs that do not render through Starlight's Head component, so they carry no og:image. Scrapers follow them to the canonical tool page, which carries the full set. Verified at `kb1r`: 42/42 rendered pages carry the set; the only og:image-less files were the stubs.

> **The redirect-stub SET flipped at change `3ke3` (the short URLs are now canonical pages).** Before `3ke3` the 7 stubs were the short URLs themselves (`/shll/`, `/wt/`, …), which redirected to `/tools/<tool>/overview/`. `3ke3` **promoted the short URLs to canonical real pages** (Starlight `slug:` overrides — see [tool-page-rubric](/conventions/tool-page-rubric.md)) and **reversed** the redirects: the stubs are now the **old `/tools/<tool>/*` deep URLs** — per tool, `/tools/<tool>` (bare), `/tools/<tool>/overview` → `/<tool>/`, `/tools/<tool>/readme` → `/<tool>/readme/`, `/tools/<tool>/commands` → `/<tool>/commands/`, plus one stub per committed docs/site page `/tools/<tool>/<path>` → `/<tool>/<path>/` (enumerated by `docsSiteRedirectEntries`, see [docs-site-tree → redirect enumeration](/conventions/docs-site-tree.md#the-redirect-enumeration-old-toolsslug-deep-urls--change-3ke3)). Same invariant holds: the stubs are `noindex` shells with no og:image, and scrapers follow them to the canonical `/<tool>/…` page which carries the full set. The og:image-less-stub property is unchanged in kind — only which URLs are the stubs changed.

## The OG card asset (`public/og-image.png` + `scripts/generate-og-image.mjs`)

The shared image is a **committed static asset**, exactly **1200×630** (the ~1.91:1 shape link-preview scrapers want — the prior 512×512 square rendered wrong). Composition: a dark terminal-window card in the site's own aesthetic — `terminal.css` dark palette, titlebar dots, a `$` prompt line, the `shll` wordmark, the tagline, a `shll.ai` footer line — set in JetBrains Mono from the already-declared `@fontsource/jetbrains-mono` dependency, legible at ~quarter scale (Slack/X preview sizes). The card is a fixed dark design regardless of site theme, so Constitution V (dark-mode parity) is not implicated by the asset.

**Generation is OUT of the build (Constitution VI).** `sites/astro-starlight-terminal1/scripts/generate-og-image.mjs` is a **one-off, unwired** generator: node stdlib only, it writes a self-contained HTML mock and screenshots it at 1200×630 with the Playwright-cached `chrome-headless-shell` binary already on the machine. It is NOT referenced from `package.json`, adds zero runtime or build dependencies, and exists purely for reproducibility — re-run it manually to regenerate the card, then verify with `file public/og-image.png` (must report `1200 x 630`). *Rejected*: SVG→PNG converters (none installed); adding `sharp`/`playwright` as devDependencies (Constitution VI).

## Homepage `<head>` overrides (`index.mdx` frontmatter)

`src/content/docs/index.mdx` carries frontmatter `head:` entries that override Starlight's defaults **on the homepage only**:

- `title` tag → **`shll — the AI coding toolkit`** (no ` | shll` suffix) — fixes the keyword-free `shll | shll` redundancy (page title `shll` + site-title suffix `shll`).
- `og:title` meta → same string.
- `og:type` meta → `website` (correct for a landing page; every other page keeps Starlight's default `article`, correct for docs content).

**Mechanism**: Starlight's head-merging gives frontmatter `head:` entries priority over its defaults and **dedupes** the singleton `<title>` and same-`property` metas — so the built homepage carries exactly one of each. This is the dedupe-aware path for overriding tags Starlight already emits (contrast the og:image set above, which is append-only because Starlight emits none). The visible hero H1 is unaffected — the splash hero renders from the `hero:` block, not the page title.

**Scope notes (settled at `kb1r`, don't re-litigate):** all non-homepage titles keep the `{page} | shll` suffix. The `shll | shll` title on the shll *tool's* overview page (`/shll/` since change `3ke3` — formerly `/tools/shll/overview/`; a page legitimately named after the site) is Starlight's correct default, not the homepage bug, and was deliberately left alone.

## JSON-LD: a route dispatcher in `Head.astro` (NOT frontmatter)

JSON-LD is authored as a **route dispatcher** in `src/components/Head.astro` — two mutually-exclusive branches, each emitting its own `<script type="application/ld+json">` block. JSON-LD is **inert data, not executable JS** — no Constitution I conflict.

**Placement decision (`kb1r`)**: all JSON-LD is emitted from `Head.astro` (gated on the route), serializing a plain JS object via `JSON.stringify` into `set:html`. This keeps the JSON authorable as a real object, and is safe by construction — `JSON.stringify` of these objects never produces `<` or raw HTML, so the body survives emission byte-exact (verified at `kb1r`: `JSON.parse` succeeds on the script body extracted from built HTML). *Rejected*: an `index.mdx` frontmatter `head:` entry with the JSON as a string `content:` — a large JSON blob inside YAML frontmatter is fragile and unreadable, and is exactly the MDX/YAML escaping friction the intake flagged as a drop trigger; it also can't reach per-route help-JSON data.

### Homepage branch — WebSite + SoftwareApplication (`kb1r`, UNCHANGED by `pgox`)

One block on the homepage only (gated on `Astro.url.pathname === '/'`), carrying a `@graph` of two entities: `WebSite` (name `shll`, url from `Astro.site` origin) and `SoftwareApplication` (name `shll toolkit`, `applicationCategory: DeveloperApplication`, `operatingSystem: macOS, Linux`, a free `Offer`, GitHub url).

**The homepage block is byte-for-byte unchanged by `pgox`** (a hard acceptance constraint of that change): the `isHomepage` gate, the `jsonLd` object (nodes + field order), and the site-wide og:image set are all untouched. `pgox` only *added* a second, mutually-exclusive branch alongside it.

### Per-tool branch — SoftwareApplication + BreadcrumbList (change `pgox`; root namespace, change `3ke3`)

Every **per-tool page** emits its own inert `application/ld+json` `@graph` of two nodes — a per-tool `SoftwareApplication` and a `BreadcrumbList` — mirroring the homepage `@graph` shape (one `<script>`, two entities, `JSON.stringify` + `set:html`). The two branches are mutually exclusive: a tool page can never be `/`, and `/` never matches the tool-page shapes.

> **The per-tool namespace moved to the site ROOT (change `3ke3`).** Before `3ke3` the covered pages were **2-segment** `/tools/<tool>/<page>/` and the crumb hierarchy was 4-deep. `3ke3` promoted the short URLs to canonical (the overview is now `/<tool>/`, readme/commands are `/<tool>/<page>/`), so the gate now matches **two shapes** and the coverage/breadcrumb depth split by shape (details below). Parity is preserved: exactly the overview/readme/commands pages are covered — nested docs-site pages stay uncovered, same as before.

- **Route detection — `Astro.url.pathname` split into segments, roster-gated (not `starlightRoute.id`).** The branch parses `Astro.url.pathname` (stripped of leading/trailing slashes, split on `/`) and matches **two shapes**, both gated on the shared tool-slug roster (`isToolSlug` from `src/lib/tool-slugs.ts`) — a bare `/<x>/` shape would otherwise match ANY root page (`getting-started`, `reference`, …), which is exactly why the roster gate replaced the old `/tools/`-prefix regex at `3ke3`:
  - **overview** — 1 segment `/<tool>/`, `<tool>` ∈ roster → no page crumb.
  - **readme/commands** — 2 segments `/<tool>/<page>/`, `<tool>` ∈ roster AND `<page>` ∈ `{readme, commands}` (a small `PAGE_LABELS` map) → page crumb present.
  This keeps the **same pathname-gate idiom** as the homepage branch (`pathname === '/'`) in this same file — one consistent gate idiom, not a mix with the `TocDispatcher`'s `starlightRoute.id` regexes (rejected at clarify #12 as an idiom mismatch within `Head.astro`). (The former single regex `^/tools/([^/]+)/([^/]+)/?$` is gone.)
- **`SoftwareApplication` node**: `name` = the **file slug** (`run-kit`, e.g.) — the entity names the software product/repo, matching the route + breadcrumb label + GitHub url. Since run-kit's v3.0.0 rename (change `co63`) the slug and binary **coincide** for run-kit (`run-kit`), so the old "slug `run-kit`, not the binary `rk`" caveat no longer applies here — **fab-kit** is the only tool where the node `name` (slug `fab-kit`) still differs from the binary (`fab`); see the [naming rule](/conventions/tool-page-rubric.md#rk-vs-run-kit--the-cli-identity-vs-reposection-naming-rule-change-jf3q). `description` = `root.short` read from `help/<tool>.json` (single-sourced; see below). `applicationCategory: DeveloperApplication`, `operatingSystem: 'macOS, Linux'`, a free `Offer`, `url: https://github.com/sahil87/<tool>` — the same shape as the homepage `SoftwareApplication` node for graph consistency (all seven are free macOS+Linux CLIs).
- **`BreadcrumbList` node** (crumb depth splits by page shape since `3ke3`): reflects `Home › Tools › <tool> [› <page>]`, **all `item` URLs absolute, derived from `Astro.site`** (`new URL(path, Astro.site).href`) — never hardcoded, the same absolute-URL discipline `kb1r` established for og:image (`site: 'https://shll.ai'` is the single origin source). The four crumb items:
  - Position 1 `Home` → `/`.
  - Position 2 `Tools` → **`/tools/`** — unchanged: the [`/tools` index page](/conventions/tool-page-rubric.md#tools-index-page--the-tools-directory-landing-change-pgox) stays the directory landing (it is NOT moved to root by `3ke3`), so the Tools crumb still resolves there.
  - Position 3 `<tool>` → **`/<tool>/`** — the tool's new canonical root URL (its overview). Was `/tools/<tool>/overview/` before `3ke3`.
  - Position 4 `<page>` → **`/<tool>/<page>/`** — present **only** for the readme/commands (2-segment) pages; the **overview page emits a 3-crumb list with no position-4** (the overview IS the position-3 destination). The page label comes from the small site-authored `PAGE_LABELS` map (`readme→Readme`, `commands→Commands` — `overview` is no longer in the map because the 1-segment overview shape carries no page crumb).
  The former title-cased fallback for an unmatched second segment (`pageLabel()`) was **removed** at `3ke3` — the 2-segment shape now only matches `page ∈ {readme, commands}`, so there is no unmatched-slug case left to fall back for (see the deletion note in [Design Decisions](#design-decisions)).

**Single-sourcing — the `description` comes from `help/<tool>.json` `root.short`, never hand-copied.** The binding anti-drift rule (constitution Tool-Page Depth, `vn39`, [help-collection](/conventions/help-collection.md)) applies here too: the SoftwareApplication `description` is read at build time via `repoRootFromModuleUrl(import.meta.url)` + `HelpDocSchema.parse` (the same shared libs `CommandReference`/`VersionTable`/`CommandIndex`/`ToolsIndex` use), never retyped. The llms.txt sibling (`354p`) drives its tool one-liners from the same field, so `root.short` is the one canonical one-liner.

> **Verbatim `root.short` includes the binary prefix — an intentional divergence (`pgox`; prefix VALUE flips at the corpus refresh, `co63`).** `run-kit`'s `root.short` is binary-prefixed and rendered **verbatim** in both the SoftwareApplication `description` and the `/tools` listing — currently `"rk — tmux session manager with web UI"` (from the still-committed pre-rename `help/run-kit.json`), becoming `"run-kit — tmux session manager with web UI"` after the daily puller refreshes the corpus (run-kit v3.0.0 still binary-prefixes its short, now with `run-kit —`). Either way it includes the binary prefix, and so differs from the homepage `TerminalPrompt`, which strips the prefix via `stripToolPrefix`. This is deliberate: a single verbatim source beats adding a second, divergent strip path — single-sourcing wins over cosmetic consistency. Not a bug, and the `co63` sweep did NOT hand-edit this (the `help/run-kit.json` corpus is puller-owned; the value self-corrects on the next pull).

**Missing-vs-invalid failure split — mirrors `CommandReference.astro`, NOT `VersionTable`'s build-stop.** Because the per-tool JSON-LD is **inert SEO metadata** (not a correctness-critical committed artifact like the `/tools` directory listing), the failure posture is the soft split:

- **Missing file (ENOENT)** → emit the `SoftwareApplication` node **without its `description` field** (keeping `name`/`url`/`applicationCategory`/`operatingSystem`/`offers` — all site-authored / derivable without the help JSON) and **continue the build**; the `BreadcrumbList` needs no help JSON and **always emits**. An absent help file is an expected interim state for a not-yet-landed producer; a missing description must not stop the build (resolved at clarify #10: omit description only, NOT the whole node). A non-ENOENT read error (e.g. EACCES) is a real fault and rethrows.
- **Present but schema-invalid** → `HelpDocSchema.parse` throws, wrapped with the filename, so `astro build` FAILS — a committed malformed help file is a defect that must not deploy (the `CommandReference` invalid-file contract).

> **Coverage boundary — overview/readme/commands pages only (`pgox`; root-namespace shapes since `3ke3`, known/accepted).** The gate matches only the **overview** (`/<tool>/`, 1 segment) and **readme/commands** (`/<tool>/<page>/`, 2 segments, `page ∈ {readme, commands}`) pages — exactly the reserved per-tool page set. The dynamic route `src/pages/[slug]/[...path].astro` renders **nested docs-site pages** at `/<tool>/<path>` (e.g. `/idea/install`, `/idea/advanced/hooks` — see [docs-site-tree](/conventions/docs-site-tree.md)); those pages emit **no** JSON-LD (no error, just absent). **This is NO LONGER latent — docs/site trees ARE committed.** Every tool now has a committed `content/<tool>/site/` tree (16 docs-site pages total: each tool's `install`/`workflows`, plus run-kit's `notifications`/`status-dot`), rendered at `/<tool>/<path>`, and these are the uncovered pages. The single-segment docs-site pages (`/idea/install`) do NOT collide with the overview gate because the overview gate additionally requires the segment to be a roster **tool slug** while `install` is a page path under a tool — but note a docs-site page's first path segment IS the tool slug, so `/idea/install` is 2 segments (`idea` + `install`) and `install ∉ {readme, commands}`, so it correctly falls through uncovered. Recorded as a known, accepted boundary, NOT a defect: per-tool JSON-LD covers the overview/readme/commands pages only (parity with pre-`3ke3` — this change did NOT widen coverage, a recorded non-goal). If nested docs-site JSON-LD is ever wanted, this gate is where to extend it.

## Agent-discoverability layer (`/llms.txt` + `/llms-full.txt`) — change `354p`

The **agent-facing sibling** of the SEO layer above. Where og:image/JSON-LD make the site legible to crawlers and social scrapers, the two `llmstxt.org`-convention endpoints make it legible to **coding agents**: a single-fetch index plus a full-content dump, discovered by convention at `/llms.txt` and `/llms-full.txt`. Both are **build-time Astro static endpoints** (`src/pages/llms.txt.ts`, `src/pages/llms-full.txt.ts`) returning `new Response(body, { headers: { 'Content-Type': 'text/plain; charset=utf-8' } })` — no SSR, no runtime fetch (Constitution I), zero new deps (Constitution VI). Both emit into `dist/llms.txt` / `dist/llms-full.txt`. The shared cross-boundary reads live in `src/lib/llms.ts` (`TOOLS`, `stripToolPrefix`, `toolShort`, `readHelpDoc`, `readReadmeSlice`, `renderCommandTree`, `flattenMdx`); the pure helpers are pinned by `scripts/llms.test.mjs` (`node --test`, type-stripping — same toolchain as `validate-help.mjs`/`parse-help.test.mjs`).

### `/llms.txt` — the curated index

H1 title + a one-line blockquote summary + three bulleted link sections: **Tools** (one bullet per tool → `/<tool>/`, the tool's canonical root overview URL since change `3ke3` — was `/tools/<tool>/overview/`), **Getting started** (install / overview / philosophy), **Reference** (command-index). 

- **Single-source the tool one-liners — derive, never retype (the anti-drift rule).** Each tool description is read from `help/<tool>.json` `root.short` (the canonical machine source) via `toolShort()`, which uses the `repoRootFromModuleUrl` (`help/`-anchored ascent) + `HelpDocSchema` pattern — **NOT** `parse-help.ts` (which parses raw `-h` *text*; `root.short` lives on the structured `HelpDoc` envelope). The leading `<bin> — ` prefix is **stripped** when present (`stripToolPrefix`, mirroring `terminal-toolcard.ts` — run-kit's `root.short` is binary-prefixed: `"rk — tmux session manager…"` in the still-committed pre-rename corpus, `"run-kit — …"` after the `co63`/v3.0.0 puller refresh; the strip is binary-name-agnostic, and the bullet's link text already carries the tool name). This is the same `vn39` / [Tool-Page-Depth](/conventions/tool-page-rubric.md) anti-drift rule that governs the rest of the site: the codebase already holds documented hand-copies of tool descriptions; `354p` MUST NOT add a fourth one. **Fallback chain:** missing/empty `root.short` → the tool's `overview.mdx` frontmatter `description` (read via `getCollection('docs')`, the same content the HTML pages render) → a noted-omission bullet (never an empty/`undefined` bullet, never a build-stop).

### `/llms-full.txt` — the full-content dump

Concatenates, per tool in `TOOLS` order: (a) the committed README slice at `<repo-root>/content/<tool>/README.md` — read **verbatim** (`readReadmeSlice`; already the deduced slice — do NOT re-run `extractReadme`), and (b) a `### Commands` plain-text command tree from `parse-help`/the validated `HelpDoc` (`renderCommandTree`). It THEN appends the **hand-authored MDX** sourced via `getCollection('docs')` — `getting-started/*`, `reference/command-index`, `workflows/*`, and the tool `overview.mdx` entries.

- **The content boundary — synced content PLUS site-authored MDX (intake Assumption #5, resolved the non-default way).** The backlog *recommended* mechanically-synced content only; the user resolved it to **include the hand-authored MDX too**. So `llms-full.txt` is no longer "synced-only" — an edit to a site-authored MDX page is now **also an `llms-full.txt` content change**. This coupling is **intentional, not accidental**: the synced parts (README slices + help) ride the existing daily `refresh-readme.yml` / help-refresh cascade (no new schedule), and the MDX parts change only on a human edit — the same refresh cadence as the HTML pages they mirror.
- **Flatten is applied ONLY to the MDX; README slices are emitted verbatim (load-bearing).** MDX is not plain markdown — `flattenMdx` does a *pragmatic* strip of leading frontmatter, `import` lines, and **Capitalised** JSX component tags (keeping their text children), leaving readable prose for the `text/plain` dump (exact fidelity is explicitly not required — Constitution VI; a full MDX compiler was rejected). `flattenMdx` is **NOT** applied to the README slices: they pass through `readReadmeSlice` untouched, so the `<TAB>` / `<N>` placeholder tokens the pulled READMEs carry (e.g. `content/hop/README.md`) **survive verbatim** into the dump rather than being mistaken for JSX and stripped. The boundary is: synced slice = verbatim; site MDX = flattened.

### Shared discipline with the SEO layer

- **Absolute URLs from `Astro.site`, never hardcoded** — every emitted link is site-absolute, via **two** mechanisms both keyed on the endpoint context `site` (`https://shll.ai`, the single origin source in `astro.config.mjs`): the *curated* links in `llms.txt` (tools / getting-started / reference) are **built** via `new URL(pathname, site)`; the *appended docs content* in `llms-full.txt` (README slices + flattened MDX) carries its own root-relative links (e.g. `[overview](/idea/)`, the homepage's `<a href="/idea/">` — since change `3ke3` these are the root `/<tool>/` links, formerly `/tools/<tool>/overview/`), so it is **rewritten** to absolute by `absolutize(content, origin)` — a targeted pass over markdown `](/path)` and HTML `href`/`src="/path"` forms only (already-absolute / protocol-relative / fragment / doc-relative targets, and the leading-`/`-less `<N>`-style tokens in README prose, are left untouched). This is the *same* absoluteness discipline the og:image set above relies on (OG scrapers and agents alike do not resolve relative URLs).
- **Per-tool fail-soft (skip-degrade, not build-stop)** — a tool whose README slice or help JSON is missing degrades to a noted omission and the build CONTINUES, mirroring the [help-collection per-tool skip-degrade](/conventions/help-collection.md#rendering-consumer-3-the-homepage-terminals-tool-cards-change-37ng), explicitly NOT `VersionTable`'s unconditional build-stop. (The `HelpDocSchema` read still re-throws a genuine parse/validation error — a *present-but-invalid* committed file is a defect that must not be masked — same discipline as `CommandReference`.)

### `robots.txt` left unchanged (explicit non-change)

`public/robots.txt` is **byte-unchanged**. The files are discovered by *convention* at `/llms.txt` / `/llms-full.txt`; there is no agreed `Sitemap:`-style line for them, and adding a non-standard reference risks confusing real crawlers. Starlight's existing `robots.txt` reference to `sitemap-index.xml` stays untouched.

### Honest caveat (carry it — do not oversell)

`llms.txt` is a **PROPOSED convention, not a guaranteed-consumed standard** like `robots.txt` / sitemaps. This layer is **cheap insurance and a structure-forcing function**, not a guaranteed traffic source. Recorded so a future reader does not mistake the endpoints for a load-bearing distribution channel.

### Accepted drift surface (low-severity, fails loudly)

`src/lib/llms.ts` carries the `TOOLS` 7-slug list as a hand-maintained const — a low-severity drift surface (slugs only; the descriptions themselves are single-sourced, so no *prose* hand-copy). This is consistent with the accepted hand-copies the [tool-page rubric](/conventions/tool-page-rubric.md) already records; it **fails loudly**, not silently — a stale slug makes `toolShort`/`readReadmeSlice` return `null` and surfaces a visible noted omission in the output, not a wrong-but-plausible bullet. (`help-collection`'s `TerminalPrompt` instead derives its roster from `readdirSync` over `help/` — a stronger guarantee; `354p` accepts the explicit slug list because the two endpoints also need the *order* and a stable per-tool overview-URL shape.)

## Editorial / content SEO layer — change `bees`

The third of the SEO batch (after `354p`/llms.txt and `pgox`/JSON-LD, which were *mechanical*). `bees` is the **editorial** pass — content quality, not markup. It edited only **site-authored content** under `sites/astro-starlight-terminal1/src/content/docs/` (the 7 `tools/<tool>/overview.mdx`, `getting-started/overview.md`, and the homepage `index.mdx` `cat ABOUT.md` prose) — **never** the synced `readme.mdx` slice, the generated `commands.mdx`, or any `help/<tool>.json` (Constitution § Tool-Page Depth; see [tool-page-rubric](/conventions/tool-page-rubric.md)). Zero new deps, content-only MDX/Markdown edits (Constitution I, VI).

### Meta descriptions are HAND-AUTHORED + SEO-optimized — the INVERSE of `pgox`/`354p`

This is the load-bearing contrast to record. The `pgox` JSON-LD `SoftwareApplication.description` node and the `354p` llms.txt tool one-liners are **single-sourced from `help/<tool>.json` `root.short`** (verbatim, anti-drift). The frontmatter `description` metas — the search-snippet / og:description surface — go the **opposite way**: each is a **unique, hand-authored, keyword-optimized** sentence, deliberately **NOT** downgraded to `root.short`.

- **Why the inverse decision.** A live audit at `bees` found every editable page already carried a hand-authored `description` markedly more keyword-rich than the terser `root.short` (e.g. fab-kit's `6-stage pipeline that forces AI agents to plan before they code.` vs. `root.short`'s `Fab workflow engine — single binary replacement for kit shell scripts`). The backlog *recommended* single-sourcing the metas from `help/<tool>.json`; the user resolved it the other way — **keep & editorially refine the hand-authored descriptions** (≤~155 chars, lead with the highest-value keyword, name the *job* not the binary, unique across the site). `root.short` stays the source ONLY for the `pgox` JSON-LD node and the `354p` llms.txt bullets, where it already lives.
- **So `root.short` and the meta description are two DIFFERENT strings by design.** Do not "reconcile" them — the JSON-LD/llms.txt description is the machine-canonical one-liner (single-sourced); the meta `description` is the human-optimized snippet (hand-authored). Both are correct; they serve different consumers.
- **The meta descriptions are therefore a hand-authored-prose surface — the `vn39` HARD rule binds them** (any command/flag named must exist in `help/<tool>.json`), not the report-only mode that governs the synced README slice. At `bees` the descriptions named no commands, but the rule applies if a future refinement adds one.

### Cross-tool internal linking — the `idea→fab-kit→wt→run-kit` graph (the highest-value `bees` item)

Before `bees`, the 7 tool overviews carried **zero** cross-tool links — the toolkit read as 7 disconnected islands (weak internal-link equity, weak "these tools compose" signal for crawlers and agents). `bees` wired the toolkit into a connected graph via a **`## How it fits` subsection** added to every `tools/<tool>/overview.mdx` body — a one-line-context paragraph linking the adjacent tools in the workflow chain.

- **The chain**: `idea → fab-kit → wt → run-kit` (backlog → plan → isolated worktree → dashboard), with **`tu`** (cost) and **`hop`** (repo nav) as cross-cutting, and **`shll`** as the bootstrap. Realized per-page link map: idea→{fab-kit, wt, tu}; fab-kit→{idea, wt, run-kit}; wt→{fab-kit, run-kit}; run-kit→{wt, tu}; tu→{fab-kit, run-kit}; hop→{idea, wt}; shll→{idea, fab-kit, wt, run-kit} + the install page.
- **Link form — site-absolute `/<tool>/` since change `3ke3`** (was relative `../../<tool>/overview/` at `bees`). When `bees` wired the cross-tool links it used the relative `../../<tool>/overview/` idiom (matching the then-current `[Readme](../readme/)` / `[Commands](../commands/)` sibling idiom). Change `3ke3` moved every overview to the flat slug `/<tool>/`, which **breaks relative resolution** (`../readme/` from `/idea/` would resolve to `/readme/`), so `3ke3` switched all overview links to **site-absolute**: cross-tool links → `/<tool>/`, sibling links → `/<tool>/readme/` and `/<tool>/commands/`. Targets are the canonical `/<tool>/` entry pages — the constitutional [directory-entry role of the overview](/conventions/tool-page-rubric.md#pulled-readme-slice-exception-change-w32m). The `shll` overview's bootstrap link to the install page stays root-relative `/getting-started/install/` (it points out of the tool namespace, unaffected).
- **The `getting-started/overview.md` ASCII workflow diagram is navigable too.** Its `idea → fab-kit → wt → run-kit` chain tool names (and the surrounding `tu`/`hop`/`shll` prose) are **site-absolute `/<tool>/` links** (root-relative from a `.md` page outside the tool namespace; `bees` authored these as `/tools/<tool>/overview/`, flattened to `/<tool>/` by change `3ke3`). The diagram is a clickable map, not just an illustration (this also satisfies the Constitution Accessibility SHOULD for decorative diagrams, the same way [`ld0j`](/conventions/tool-page-rubric.md#homepage-newcomer-content-blocks-hand-authored-change-ld0j) moved the homepage diagram links inline).

### Job-framed lead sentences on the overviews (the H1-substitute framing)

The bare-slug Starlight `title:` (the H1) was **not changed** — it cascades to the sidebar label and the settled [`kb1r` `shll | shll` title discipline](#homepage-head-overrides-indexmdx-frontmatter). Instead, each overview body's opening was expanded from a terse 1–2-sentence framing to a **3–4-sentence job-framed lead** ("what is `<tool>` / why use it / who it's for") that surfaces ranking keywords in the first indexable paragraph. The homepage `cat ABOUT.md` prose and the `getting-started/overview.md` intro were keyword-sharpened by **refining existing copy only** — no new claims, no new sections; the homepage `head:` overrides block, hero `tagline`, and install/`whoami` blocks were left byte-for-byte (the `ld0j` sourced-copy discipline preserved). This thickening of the overview body is the rubric change recorded in [tool-page-rubric](/conventions/tool-page-rubric.md).

## Design Decisions

- **A thin layer over Starlight's baseline, not a meta framework.** The audit showed Starlight covers most SEO hygiene already; the fix is a few appended tags in the existing Head override + two frontmatter overrides + one regenerated asset. *Rejected*: any SEO integration/plugin — no page-visible need beyond these tags (Constitution VI).
- **Append vs. override, chosen per tag.** Tags Starlight does not emit (the og:image set) are appended after `<Default />` in the Head override; tags it does emit (`title`, `og:title`, `og:type`) are overridden through frontmatter `head:` where Starlight's merge dedupes. Using the right mechanism per tag is what keeps every built page at exactly one instance of each.
- **JSON-LD lives beside the other literal-emission head injections.** `Head.astro` already owned the `set:html` literal-emission pattern (the Cloudflare beacon, change `i2b0`); the JSON-LD reuses it rather than introducing a second authoring home in frontmatter.
- **One JSON-LD authoring home, extended into a route dispatcher (change `pgox`).** Rather than add a second authoring home for per-tool structured data, `pgox` extended the existing route-gated `Head.astro` block into a dispatcher: the homepage branch stays byte-for-byte unchanged and a new, mutually-exclusive tool-page branch is added. *Why*: `Head.astro` already owns all JSON-LD via the `set:html` pattern and is the only place that can reach per-route `help/<tool>.json` data at build time; a frontmatter `head:` blob can't (it's per-page string YAML, fragile, and data-blind). The two branches gate on the same `Astro.url.pathname` idiom (homepage `=== '/'`; tool pages a pathname split gated on the tool-slug roster — the `/tools/`-prefix regex was replaced at change `3ke3`, see the roster-gate decision below) for consistency within the file. *Rejected*: `starlightRoute.id` + the `TocDispatcher` regexes (valid, but mixes idioms in this file).
- **Per-tool failure posture follows `CommandReference`, not `VersionTable` (change `pgox`).** Inert SEO metadata uses the soft missing-vs-invalid split (ENOENT → omit description + continue; invalid → build-fail) because a missing producer help file is a transient/interim state, not a deploy-blocking defect. This deliberately differs from the *same change's* `/tools` directory page, which uses `VersionTable`'s build-stop posture because an incomplete committed directory listing IS a defect. Two surfaces, two correctness criticalities — see [tool-page-rubric](/conventions/tool-page-rubric.md#tools-index-page--the-tools-directory-landing-change-pgox).
- **Roster gate replaced the `/tools/`-prefix regex (change `3ke3`).** When the per-tool namespace moved to the site root, the old `^/tools/([^/]+)/([^/]+)/?$` gate could no longer distinguish a tool page (a bare `/<x>/` matches any root route). The gate now splits `Astro.url.pathname` into segments and checks the first against the shared `isToolSlug` roster (`src/lib/tool-slugs.ts`), matching the 1-segment overview and 2-segment readme/commands shapes. *Why*: one shared source of truth for the tool slug set (same roster as `commands-toc.ts`/`readme-toc.ts`/llms), and the only correct way to tell `/idea/` (a tool) from `/getting-started/` (not). *Rejected*: a bare `([^/]+)` regex with no membership check (false-positive against root routes).
- **The `pageLabel()` title-case fallback was removed (change `3ke3`).** `pgox` carried a title-cased fallback (`slug.charAt(0).toUpperCase() + slug.slice(1)`) for an unmatched BreadcrumbList page-label slug — a minor divergence from `docs-site-sidebar.mjs`'s `titleizeTail`. `3ke3` **deleted it**: the 2-segment shape now matches only `page ∈ {readme, commands}` (both in the explicit `PAGE_LABELS` map) and the overview is the 1-segment shape (no page crumb), so no unmatched-slug case can reach a label lookup — the fallback became dead code. If nested docs-site JSON-LD is ever added (the coverage boundary above), reintroduce a label strategy for those slugs there.
- **The OG card is an artifact, its generator is a tool — only the artifact ships.** Committing the PNG keeps the build dependency-free; committing the unwired script keeps the card reproducible. Neither couples to `package.json`.
- **The agent layer is a sibling of the SEO layer, co-located here, not a new file (change `354p`).** `/llms.txt` is to coding agents what og:image/JSON-LD are to scrapers — the SAME disciplines (absolute URLs from `Astro.site`, single-source-not-hand-copy, build-time static, zero deps), a different audience. The memory was placed as a delimited section *in this file* rather than a new sibling so the crawler + agent discoverability story stays co-located (intake Assumption #6). *Rejected*: a separate `agent-discoverability.md` — would scatter one coherent "how the site presents to non-human consumers" story across two files.
- **`llms-full.txt` is coupled to site-authored MDX by design (change `354p`).** Resolving the intake's one open call the non-default way (include hand-authored MDX, not synced-only) means an MDX edit is now also an `llms-full.txt` content change. Accepted because it keeps the dump single-sourced from the same `getCollection('docs')` content the HTML pages render — no new hand-copy — and the staleness still rides the existing daily refresh. *Rejected*: synced-content-only (the backlog's recommendation) — would have omitted getting-started/workflows/philosophy prose an agent ingesting the toolkit wants. *Rejected*: a full MDX compiler pass — `flattenMdx`'s pragmatic tag/import strip is sufficient for a `text/plain` dump (Constitution VI).
- **Flatten the MDX, emit the README slices verbatim (change `354p`).** `flattenMdx` runs ONLY on the `getCollection('docs')` bodies; `readReadmeSlice` returns the committed slice untouched. This is deliberate — the pulled READMEs carry `<TAB>`/`<N>` placeholder tokens that a JSX-tag strip would corrupt, and the slice is already the canonical deduced prose. *Rejected*: a uniform flatten over both sources — would mangle the README placeholders for no benefit.
- **Meta descriptions stay hand-authored, NOT single-sourced from `root.short` (change `bees`).** The deliberate inverse of `pgox`/`354p` (which DO single-source `root.short`). *Why*: the existing hand-authored frontmatter `description`s are unique and markedly more keyword-rich than the terser `root.short`; downgrading them to the machine one-liner would *regress* the search-snippet surface. So `root.short` is the canonical machine description (JSON-LD + llms.txt), and the meta `description` is the human-optimized snippet — two strings, two consumers, both correct. *Rejected*: the backlog's recommendation to single-source the metas from `help/<tool>.json` — it would have downgraded a better surface to a worse one. (User-resolved at intake, the central SRAD question.)
- **Cross-tool linking via a `## How it fits` subsection on every overview, not a shared component (change `bees`).** The connected `idea→fab-kit→wt→run-kit` graph is realized as hand-authored MDX prose+links in each overview body, reusing the existing relative-link idiom — zero new components, zero new deps (Constitution VI). *Why*: the overview is the site-authored directory entry; one-line cross-tool context is exactly its job (Constitution § Tool-Page Depth). *Rejected*: a shared "Related tools" component — deferred as a *future mechanical* change, out of scope for an editorial pass.
