# README Extraction

## Overview

Each of the 7 tools in the toolkit (`idea`, `hop`, `fab-kit`, `wt`, `run-kit`, `tu`, `shll`) maintains its richest documentation in its own `README.md`. shll.ai **pulls** a *deduced, curated slice* of each README on a schedule, collects the slices at the **repo root** under `content/<slug>/README.md`, and renders them on each tool's dedicated **`readme` page** (`/tools/<slug>/readme`, change `4s3e` — formerly injected into `overview`).

This is the **README-prose counterpart** of [help-collection](./help-collection.md): where `help-collection` pulls the machine-generated *command reference*, this pulls authored *prose* (the "Why", "Usage", screenshots, rendered diagrams). The two are intentionally symmetric — a forward contract in `docs/specs/` + a consumer (a scheduled pull workflow + a build-time render component). README extraction is the second consumer of the help-pull's proven pull architecture (see [Sibling of the help pull](#sibling-of-the-help-pull-shared-patterns)).

The point is anti-drift: the tool repo is **canonical**; shll.ai never hand-copies README prose. A scheduled job pulls the curated slice daily and commits it, so the site's per-tool prose is fresh *by construction* — the precise drift `vn39` had to clean up (fabricated commands/flags hand-copied onto the site) cannot recur, because nothing is hand-copied. The README is rendered **verbatim** (it is the canonical source); the `help/<tool>.json` cross-check ([the `vn39` divergence reporter](#the-vn39-divergence-reporter-report-only-change-4s3e)) is a **report-only lint** (change `4s3e`) that *surfaces* a slice referencing a command/flag the tool does not have — as a non-fatal CI `::warning::` — without ever withholding the slice.

This file documents the **consume/pull side** — how shll.ai deduces, validates, collects, and renders the slice. The **forward contract** — how each tool's README MUST be structured — lives in the spec [`docs/specs/readme-extraction-contract.md`](../../specs/readme-extraction-contract.md). This memory file does **not** restate the contract — it points to it and documents the implementation.

> **The asymmetry with `help-dump`.** `help-dump` asks each tool to *emit a new artifact*. This contract mostly **constrains an artifact tools already have** — the README. There is no new subcommand and no new file for a tool author to ship; the obligation is to keep the README's top structure conformant and to commit rendered images for any diagram destined for the site. See the contract's Overview.

## The contract (where it lives)

> **Forward contract**: [`docs/specs/readme-extraction-contract.md`](../../specs/readme-extraction-contract.md) — §1 head rule, §2 tail rule (denylist; Install included), §3 image rule, §4 dark-theme producer/consumer stanzas, §5 mermaid Option A, §6 strips, §7 the `vn39` **divergence reporter** (report-only — change `4s3e`, formerly a blocking validation gate), §8 pull model (always-commit, warn-not-skip — change `4s3e`), §9 the `docs/site/` escape hatch (reserved/future — not yet implemented).

The **single machine-anchored** definition of the deduction + strip + verify behavior is `sites/astro-starlight-terminal1/src/lib/extract-readme.ts`. The prose contract MUST agree with it; on any discrepancy the prose is reconciled to match the code (the code is what the workflow and the component actually run).

## The deduction rules (as implemented)

`extract-readme.ts` exports `extractReadme(markdown)` — a **pure, dependency-free, total** function (never throws on arbitrary input) returning the extracted slice. It applies, in order:

- **Head rule (§1)** — skip a contiguous run of leading GitHub chrome from the top: the single leading **H1** (`# tool-name`), a single leading **`> blockquote`** (the `> Part of @sahil87's toolkit …` line + wrapped continuation lines), and any contiguous run of **image/badge lines** (`![alt](url)`, `[![alt](img)](href)`, `<p align=…><img …></p>`, bare `<img …>`). Blank lines interleaved with these are part of the skipped head. Skipping **stops at the first non-blank line that is none of the above** — that line begins the slice. A no-chrome README (first non-blank line is prose) is returned unchanged from the head.
- **Tail rule (§2)** — the slice ends immediately before the **first denylisted heading** after the head. Denylist: `Contributing`, `Development`, `Building`, `License`, `Acknowledgements` (case-insensitive, `##`/`###`, matched on heading text independent of position). `Install`/`Installation` is **INCLUDED** (pulled, not excluded — its accuracy is guarded by the [`vn39` gate](#the-vn39-validation-gate), not by exclusion). `Changelog`/`Roadmap`/`FAQ` are **NOT denylisted**. No denylisted heading → slice runs to end-of-file.
- **Strips (§6)** — two pure text transforms applied to the slice after the boundary cuts: (1) **mermaid fences** — every ```` ```mermaid ```` … ```` ``` ```` block removed (Starlight does not render mermaid; adding a renderer violates Constitution I/VI — see contract §5); non-mermaid fences left intact. (2) **GitHub theme-only images** — any image whose URL carries `#gh-dark-mode-only` / `#gh-light-mode-only` removed (renders wrong-theme duplicates off GitHub); plain images preserved.

The denylist, mermaid/theme-image markers, and head-chrome patterns are **named constants** (no magic strings). The module imports no npm package (Constitution VI).

## The `content/` collector

`content/` is a top-level directory at the **repo root** (sibling to `help/`, `sites/`, `fab/`, `docs/`), holding `content/<slug>/README.md` per tool. It is **not** nested under any `sites/<name>/`.

**Why the root.** Same rationale as [`help/`](./help-collection.md#the-help-collector): the slice data is project-level, not owned by any one site variant. Keeping it at the root means it **survives a live-site swap** (Constitution III — One Live Site at a Time): changing `SITE_DIR` does not require moving the collector. It is kept **distinct from `help/`** so the two data kinds — JSON command trees vs. markdown prose slices — don't overload one directory.

**Filename.** The slice file is `content/<slug>/README.md` — the directory is fixed by the contract; naming the file `README.md` keeps provenance obvious. Today **only** `README.md` is pulled and rendered; the `docs/site/*.md` siblings the contract sketches (contract §9) are a **reserved/future** extension — there is no `docs/site/` fetch or render path yet. A `content/.gitkeep` is committed so the repo-root collector exists at build time even before any tool's first successful pull.

**No slice data ships in this change.** The slices are produced by the daily workflow against live external repos; the change `w32m` ships only the *machinery*. Every tool renders the placeholder until its first successful pull.

## The `ReadmeSlice.astro` render component

`sites/astro-starlight-terminal1/src/components/ReadmeSlice.astro` (sibling to `CommandReference.astro`) reads the pulled slice at build time and renders it to static HTML. It is **transport-agnostic** — it does not care whether a PR or a cron put the file there.

- **Prop**: `tool` (the slug). The component does the read + render; page authors only pass the slug. A missing-slug prop fails the build loudly (mirrors `GithubButton`/`CommandReference`).
- **Placement (change `4s3e` — parallel page, not overview injection)**: rendered from each tool's dedicated **`readme` page** — `src/content/docs/tools/<tool>/readme.mdx` (frontmatter `title: Readme` + a `description`, `.mdx` so it can `import` the component) — which renders `<ReadmeSlice tool="<slug>" />`. Slug `/tools/<tool>/readme`, sidebar label **"Readme"**, a sibling of the generated `commands` page. `astro.config.mjs` carries a `Readme` sidebar entry per tool parallel to `Commands`; the `Reference` group + `CommandReference`/`CommandIndex` (`qemq`) are untouched. The component's *behavior* is unchanged — only its host page moved. **Superseded** the `w32m` model where `<ReadmeSlice>` was injected into each `overview.mdx` under `<GithubButton>` (removed from all 7 overviews); the overview is now a [thin directory entry](./tool-page-rubric.md#pulled-readme-slice-exception-change-w32m) and the readme page carries the tool's canonical words — separating the two authors cleanly (site-authored framing vs. the tool's own prose).
- **Build-time `fs` read via ascend-to-root (NOT glob, NOT fetch, NOT `process.cwd()`, NOT a fixed depth)**: `findRepoRoot` ascends from `import.meta.url`'s directory until it finds the directory that CONTAINS a `content/` folder, then reads `<that-root>/content/<tool>/README.md`. (Unchanged by change `4s3e` — the read path is anchored on the module URL, so moving the component's host page from `overview.mdx` to `readme.mdx` does not affect it.) This is the **identical strategy** `CommandReference.astro` uses for `help/` (anchored on `content/` instead) — see [help-collection → Resolution gotcha](./help-collection.md#rendering-consumer-commandreference): a *fixed* relative depth silently ENOENTs under `astro build` because Vite bundles the frontmatter chunk at an unstable depth, so the read must anchor on the module URL and ascend. The ascent is bounded; if no `content/` ancestor exists at all it throws a clear, build-failing error (the repo-root collector is missing — a broken cross-boundary contract, distinct from the per-tool missing-file case below).
- **Render**: the markdown string is rendered to HTML at build time via `@astrojs/markdown-remark`'s `createMarkdownProcessor` (see [Dependency reconciliation](#dependency-reconciliation-astrojsmarkdown-remark)). No client JS for primary content (Constitution I). Styling reuses the terminal `--c-*` tokens (dark-mode parity, Constitution V) with a `:focus-visible` ring (Accessibility).
- **Missing vs. invalid (two distinct failure modes)** — same discipline as `CommandReference`:
  - **MISSING** (`ENOENT`): render a neutral placeholder ("README slice not generated yet — see the GitHub README") and **let the build succeed**. A missing slice is the expected interim state until a tool's first successful pull lands.
  - **PRESENT but unreadable/invalid**: the error propagates so **`astro build` fails** loudly — a committed defect must not deploy. The two cases are never conflated.

## The `readme-toc.ts` rail builder (second consumer of the slice — change `u4di`)

The slice now drives a **second build-time consumer** besides `ReadmeSlice`: `src/lib/readme-toc.ts` builds the readme page's right-rail "On this page" ToC from the **same** `content/<tool>/README.md` slice. (The rail's *page-shape* role — why the readme page needs a custom ToC at all, the separate `ReadmeToc`/`ReadmeMobileToc` components, the dispatcher that routes the override slot — is documented in [tool-page-rubric → Right-rail ToC](./tool-page-rubric.md#right-rail-on-this-page-toc-generated-dispatcher-routed--change-u4di). This file documents only the **consume-side mechanics** against the slice.)

- **Same slice, independent render.** `readme-toc.ts` resolves the tool from a `tools/<tool>/readme` route id, reads `<repo-root>/content/<tool>/README.md` via the **same `help/`-marker `repoRootFromModuleUrl` ascent** `ReadmeSlice` uses (`lib/repo-root.ts` — anchored on `import.meta.url`, the Vite-bundle-depth-proof read path; NOT `content/`-anchored, which collides with Starlight's `src/content/`), and runs its **own** `createMarkdownProcessor({})` render — it does not share `ReadmeSlice`'s render result. This mirrors the help side, where `CommandReference` (page) and `commands-toc.ts` (rail) each read `help/<tool>.json` independently — the two component instances have no shared frontmatter, and a second render of a small markdown file is cheap.
- **What it reads: `rendered.metadata.headings`, not the HTML.** It folds the processor's heading manifest (`{ depth, slug, text }`) into a nested H2 → H3 tree (H4+ ignored; orphan H3 before any H2 attaches at top level). Failure contract mirrors `firstLevelCommands`/`ReadmeSlice`'s MISSING case: ENOENT → `[]` (page falls back to the default rail), genuine read/render error re-throws.

### Slug single-sourcing: rendered ids === ToC hrefs via ONE processor (change `u4di`)

The rail must link to the exact heading `id`s the rendered slice carries, or every link is dead. The slugs are single-sourced through **one** mechanism — the markdown processor itself — not two slug passes:

- **The render already emits ids.** `ReadmeSlice`'s `createMarkdownProcessor({})` (empty config) is NOT slug-less: the default processor runs a built-in `rehypeHeadingIds` pass (which uses `github-slugger@2.0.0` transitively) that gives every `<h2>`/`<h3>` a GitHub-style `id`, AND exposes the **same** slugs on `rendered.metadata.headings`. (The intake's "prerequisite" premise — that empty config emits no ids — was read off the config string; running it shows the opposite. `ReadmeSlice` needed **no** functional change, only a clarifying comment.)
- **Both consumers call the identical processor over the identical slice**, so `id` (from `ReadmeSlice`'s rendered HTML) and `href` (from `readme-toc.ts`'s `metadata.headings`) are **byte-identical by construction** — dedup suffixes (`-1`, `-2`) included. Verified: 0 mismatches across all 7 tools.
- **No `github-slugger` direct dependency, no second slug path (do NOT regress).** The original intake (clarification #9) planned a hand-rolled shared `github-slugger` `headingSlug` helper + a `github-slugger` package.json declaration. The implementation **superseded** that: reusing the one processor that already owns the slug (via `@astrojs/markdown-remark`, already declared+pinned at `7.1.2` — see [Dependency reconciliation](#dependency-reconciliation-astrojsmarkdown-remark)) is a **stronger single-source guarantee** than two independent slug reimplementations and adds **no** new direct dep (Constitution VI — `github-slugger` stays transitive-only). A future maintainer MUST NOT "fix" this by adding `github-slugger`, adding `rehype-slug` (redundant — the processor already slugs), or hand-parsing the markdown headings (a second code path, the exact drift the intake forbade). This parallels how `commands-toc.ts` agrees with `CommandReference`'s emitted ids via the shared `commandSlug` — here the shared source is Astro's own processor.

## The `scheduled-readme-refresh.yml` pull job

shll.ai pulls README slices via `.github/workflows/scheduled-readme-refresh.yml` — a **sibling** of `scheduled-help-refresh.yml`, deliberately **OFF the deploy path**.

- **Triggers**: a daily `schedule` cron (`41 7 * * *`, offset from help-refresh) + `workflow_dispatch` (on-demand after a README change).
- **Per-tool pipeline** (looped over all 7 tools, a slug:repo table): fetch the repo's `README.md` from `raw.githubusercontent` (main→master fallback) → run `extractReadme` (head/tail deduction + strips) → run the `findUnknownTokens` **divergence reporter** against `help/<slug>.json` → **always commit** the slice to `content/<slug>/README.md`. The extraction + reporter run via a thin CLI (`scripts/extract-readme-cli.mjs`) over the same module (see [the CLI's four exit behaviors](#the-cli-extract-readme-climjs)).
- **Commit**: a **direct commit to `main`**, using the default `GITHUB_TOKEN` with minimal `contents: write`. No PR, no auto-merge — sound because the committer is a single trusted cron (same reasoning as help-refresh). **Always commits on divergence (change `4s3e`)**: divergence emits a `::warning::` and the canonical slice is committed anyway — it is NOT gated on the cross-check (formerly: `w32m` gated the commit on the `vn39` gate passing and skipped a divergent tool).
- **Failure isolation now applies ONLY to genuine fetch/read failures (change `4s3e`)**: a tool whose README genuinely cannot be fetched (no network / 404 on all branches) keeps its last-good committed slice and does not block the others — a real failure, distinct from divergence. **Divergence is NOT a failure**: a slice that diverges from `help/<slug>.json` (or has no `help/<slug>.json` at all, e.g. `tu`) is still committed with a `::warning::`. Each fetchable tool overwrites its committed file; only an unfetchable one keeps last-good.
- **Off the deploy path (load-bearing)**: the refresh job does not deploy. When it commits to `main`, the **existing** `deploy.yml` push-to-`main` deploy ships the updated slice — no separate deploy trigger is added (Constitution IV). A flaky *fetch* therefore breaks the REFRESH, not the deploy; the site keeps shipping the last-good slice. (A *divergent* README no longer breaks the refresh — it commits with a warning — change `4s3e`.)
- **Toolchain**: pinned pnpm 10 + Node 22 (reusing the help-refresh / `deploy.yml` setup pattern).

## The `vn39` divergence reporter (report-only, change `4s3e`)

Pulled prose WILL contain command/flag examples — exactly what the [`vn39` binding rule](./help-collection.md#hand-written-prose-must-not-contradict-helpjson-the-binding-rule) polices ("site prose MUST NOT reference commands/flags absent from `help/<tool>.json`"). The pull job runs each slice through this cross-check, but as of change `4s3e` the cross-check is a **report-only divergence reporter, never a publish gate** — the slice is always committed; divergence is surfaced, not censored.

- **The README is canonical and rendered verbatim; divergence is a repo-level lint, never a publish gate (change `4s3e`).** This resolves a contradiction in the `w32m` design: a *blocking* gate that **rejects** the canonical README when it diverges from `help-dump` makes `help-dump` the de-facto authority — the projection refusing to display the thing it projects (the architecture's constraint #2 is that the tool README is canonical). You cannot hold both "README is canonical" and "README must pass validation before we trust it." So: a pulled slice (incl. its Install section) referencing a command/flag absent from `help/<tool>.json` emits a non-fatal CI `::warning::` (a repo-level lint), and the **canonical slice is committed and rendered anyway**. The fix belongs in the **tool's README** (the source of truth), never a silent withholding on the shll.ai side — *you do not protect a system from its own declared source of truth*.
  - **The accepted tradeoff**: a genuinely fabricated command can appear on shll.ai for up to one refresh cycle (≤24h) until the tool README is corrected — the precise harm `vn39` guarded against, now consciously accepted in favor of canonical-source consistency and full tool coverage (under `w32m`'s blocking gate, 5 of 7 tools — hop/fab-kit/run-kit/shll/tu — were silently withheld after the first refresh).
- **Two consumers, two modes (do NOT conflate — see [help-collection](./help-collection.md#hand-written-prose-must-not-contradict-helpjson-the-binding-rule)).** The `vn39` rule remains a **hard rule** for *hand-written* site prose (which MUST NOT cite commands/flags absent from `help/<tool>.json`). It is **report-only** ONLY for the *canonical, mechanically-synced* README slice. The same detector serves both consumers; only the *consequence* differs by consumer.
- **The detector is unchanged; only its consequence flipped at the CLI call site (change `4s3e`).** `findUnknownTokens(slice, helpDoc)` in `extract-readme.ts` is **byte-for-byte unchanged** — a pure helper that, given a slice and a parsed `help/<tool>.json` tree, returns the set of referenced command/flag tokens absent from the tree. What changed is the *call site* in `extract-readme-cli.mjs`: a non-empty result now warns + still writes + exits 0, rather than failing the pull. The **same function** backs both the unit test and the workflow CLI, so detection cannot drift (the very class of bug `vn39` itself fixed). Command-path truth comes from the `help/<tool>.json` tree; flag truth from the build-time `parseHelp` decomposition the command reference already trusts. (False-positive tuning of the detector — Cobra `completion`/`help`, the `h ou<TAB>` completion-demo idiom, per-subcommand flag scoping — is deferred to a separate follow-up; a noisy-but-non-fatal warning is tolerable until tuned.)
- **The `childrenOf` positional-arg fix (load-bearing — don't regress).** A naive verifier grows the command path through *every* bare word after the binary, which flags a known leaf command followed by a positional arg (`shll install mytool`) as an "unknown subcommand". The implemented `helpFacts` carries a **parent→children map** (`childrenOf`); the token walk descends only into known children and **stops at a known leaf** (everything after a leaf is treated as args), flagging a token only when the current node HAS children and the token isn't one of them. The test pins both sides: `<known-leaf-command> <positional-arg>` is NOT flagged (`shll install mytool`, `wt create feature`, `hop shell-init zsh`, `hop config add somedir`, `hop clone myrepo`), while true positives STILL flag (`shll shell-install`, `wt summon`, `hop config bogus`).

## The CLI (`extract-readme-cli.mjs`)

`scripts/extract-readme-cli.mjs` is the thin CLI the workflow runs over `extract-readme.ts` — `node scripts/extract-readme-cli.mjs <slug> <raw-readme-path> --out <path>`. It is the single place where the report-only *consequence* lives (the detector itself is consequence-free). Its **four exit behaviors** (change `4s3e`):

1. **Missing/unreadable INPUT README → error (exit non-zero), no slice written.** There is nothing to render, so report-only does not apply. This is the one genuine error path.
2. **Missing/unreadable `help/<slug>.json` → "unverified" `::warning::` + still write the slice + exit 0.** Verification cannot run, but the README is canonical, so it is committed unverified rather than withheld (the `tu` case — no `help/tu.json`).
3. **Divergence (non-empty `findUnknownTokens`) → `::warning::` listing the unknown tokens + still write the slice + exit 0.** The fix belongs in the tool README, not the site.
4. **Clean slice → write + exit 0.**

Only behavior 1 is non-zero; behaviors 2–4 always produce a slice. This is what lets the workflow commit every fetchable tool's slice without a per-tool special case.

## The extraction test

`sites/astro-starlight-terminal1/scripts/extract-readme.test.mjs` is a native `node --test` (type-stripping — the same toolchain as `validate-help.mjs`/`parse-help.test.mjs`), 21 cases covering: head (chrome skip + no-chrome passthrough), tail (denylist stop, Install kept, Changelog/Roadmap/FAQ kept, no-denylist→EOF), mermaid-strip (mermaid removed, bash kept), theme-image-strip (both `#gh-*` removed, plain kept), and the **reporter** (unknown token incl. the `shll shell-install` case; clean slice passes against a real `help/*.json`; the `childrenOf` positional-arg regression cases). The suite exercises `findUnknownTokens` **directly** (asserting on the returned token lists), not the CLI's exit code — so the change `4s3e` report-only flip touched only the test file's doc/header comment (now describing the detector as a report-only reporter, not a blocking gate), not any assertion. The new CLI-level exit-0-on-divergence behavior has no unit test (the CLI had none) and is verified out-of-band by a manual divergence→exit-0 run per Test Integrity.

This follows the precedent `qemq` set for `parse-help.ts`: a pure, dependency-free, build-time text transform pinned by a native `node --test` (see [help-collection → build-time `parseHelp`](./help-collection.md#rendering-consumer-commandreference)). README extraction is the same class of problem (parse pulled text at build time, no new dependency) and reuses the precedent rather than inventing a parallel one.

> **A full `astro build` is also a gating check.** It is the only thing that catches the phantom-dependency class of bug (a bare import of an undeclared-but-transitive package resolves in `node --test` but fails Vite/Rollup at build) — see [Dependency reconciliation](#dependency-reconciliation-astrojsmarkdown-remark).

## Dependency reconciliation (`@astrojs/markdown-remark`)

Rendering an in-memory markdown string read by `fs` (the contract-mandated read path) needs a markdown→HTML step. The component uses `@astrojs/markdown-remark`'s `createMarkdownProcessor`, **declared explicitly** in the site `package.json` pinned to `7.1.2` (the exact version `astro@6.3.3` core depends on directly; also a dep of `@astrojs/starlight`).

**Honest reconciliation with Constitution VI.** This is a **build-time** dependency **already pulled transitively** by astro/starlight. Declaring it explicitly makes an EXISTING dep **importable**, not a NEW dep — no new runtime dependency, no new transitive weight, no version split. The declaration is required because **under strict pnpm a transitive dep is NOT hoisted** to the site's top-level `node_modules`, so a bare `import '@astrojs/markdown-remark'` does not resolve and `astro build` fails for the whole site (the component renders on all 7 `readme` pages). This was caught only at full `astro build` (it resolved fine under `node --test`).

> This is **NOT** the `z`-from-`astro:content` case (see [help-collection → Zod module](./help-collection.md#zod-schema-module-the-machine-checkable-contract)): `astro:content` is a Vite **virtual module** Astro injects (needs no `package.json` entry), whereas an npm package import does.

## Sibling of the help pull (shared patterns)

README extraction is the **second consumer** of the pull architecture [help-collection](./help-collection.md) proved. Both reuse, now exercised by two data kinds:

| Shared pattern | help-collection | readme-extraction |
|----------------|-----------------|-------------------|
| Daily scheduled job, off deploy path | `scheduled-help-refresh.yml` | `scheduled-readme-refresh.yml` (sibling) |
| Repo-root data surviving a live-site swap | `help/<slug>.json` | `content/<slug>/README.md` |
| Direct-commit-to-`main` | gated on Zod `validate-help.mjs` | **always commits** (change `4s3e`) — `findUnknownTokens` (`vn39`) is a report-only divergence reporter, not a commit gate |
| Per-tool failure isolation (keep last-good) | per-tool capture (capture failure) | per-tool **fetch failure only** (change `4s3e`) — divergence is NOT isolated, it commits with a warning |
| Ascend-to-root `import.meta.url` build-time read | `CommandReference` → `help/` | `ReadmeSlice` → `content/` |
| missing→placeholder / present-but-invalid→build-fail | `CommandReference` | `ReadmeSlice` |
| Pure, dependency-free, native-test-pinned build-time parse | `parse-help.ts` (`qemq`) | `extract-readme.ts` |

They are kept **distinct** (not one merged workflow) because each is a different data kind with a different gate and different failure semantics — see [Design Decisions](#design-decisions).

## Design Decisions

- **Sibling workflow, not extend `scheduled-help-refresh.yml` (change `w32m`).** The README pull is a distinct data kind (markdown slices → `content/`) with a distinct gate (the `vn39` command/flag cross-check vs. the Zod schema validation) and distinct failure semantics; a sibling keeps each workflow single-purpose, leaves help-refresh untouched (lower blast radius), and matches the producer/consumer symmetry. *Rejected*: extending the existing workflow — would overload one job with two unrelated data kinds and two gates, and couple their failure isolation.
- **Render markdown via `@astrojs/markdown-remark`, declared explicitly (Option B) (change `w32m`).** The `fs`-read path needs a string→HTML step; `@astrojs/markdown-remark` is already in the tree transitively, so declaring it (pinned to astro core's version) makes the existing build-time dep importable under strict pnpm — no new runtime dep, no new transitive weight (Constitution VI honored honestly). *Rejected*: a new `marked`/`markdown-it` dep (genuinely new — Constitution VI); a glob content collection / `import.meta.glob` (the contract forbids it for the read path, and `content/` lives OUTSIDE `src/`, so a Starlight content collection can't reach it without large churn that contradicts the locked overview-injection design); a hand-rolled markdown→HTML renderer (too lossy for full README prose).
- **~~Inject into `overview.mdx`, not a new page (change `w32m`).~~ Parallel `readme` page, thin overview (revised, change `4s3e`).** `w32m` injected `<ReadmeSlice>` into each `overview.mdx` under `<GithubButton>` to keep page count low. That collides two authors on one page: site-authored framing AND the canonical synced slice with no boundary, and both "pitch the tool" (a double-pitch — the README opens with a tagline + "Why X?", as does a hand-written overview). `4s3e` moved the slice to a **parallel per-tool `readme` page** (`/tools/<tool>/readme`, sibling of `commands`) and thinned the overview to a directory entry. This separates the two authors cleanly (overview = site-authored framing/nav; readme = the tool's canonical words), matches the existing multi-page Starlight model, and follows `qemq`'s precedent (the generated command reference got its own `commands` page, not an overview injection). *Rejected*: keep injecting into overview (double-pitch, unclear ownership). The cross-tool `Reference` axis (`qemq`) is still untouched — README prose stays on the per-tool axis.
- **Report, don't block — the README is canonical (change `4s3e`).** Resolves the "README is canonical vs. validate-before-trust" contradiction baked into `w32m`'s blocking gate. A gate that withholds the canonical README on divergence makes `help-dump` the de-facto authority and (observed live) left 5/7 tools invisible. So divergence → warn + write + exit 0; the canonical slice is always committed/rendered; you fix the source of truth (the tool README), you do not censor it on the site. *Rejected*: keep blocking (status quo, contradicts canonical, hides 5/7 tools); remove the detector entirely (loses the useful drift signal and fully reintroduces the `vn39` failure). Accepted tradeoff: a fabricated command can show for ≤1 refresh cycle (≤24h).
- **Install is INCLUDED; the cross-check is a reporter, not a guard (change `w32m`; reframed `4s3e`).** A per-tool install section carries legit tool-specific detail; it is pulled (not excluded). Under `w32m` the `vn39` gate was the *sole guard* on pulled-install accuracy (blocked on divergence); under `4s3e` it is an accuracy *reporter* — a divergent install section still commits with a `::warning::`. The global quick-start ("install the whole toolkit") and a per-tool install ("install just this tool") coexist, framed differently — both can be simultaneously correct.
- **`vn39` verifier is a shared pure helper, now a reporter (change `w32m`; consequence flipped `4s3e`).** The same cross-check backs both the unit test and the workflow CLI; one implementation avoids the drift class `vn39` itself fixed. The detector logic is unchanged across `4s3e` — only the CLI call site's consequence flipped (warn vs. fail). The `childrenOf` parent→children walk prevents the positional-arg false positive (`shll install mytool`). *Rejected*: a bash-only grep gate in the workflow (would diverge from the tested logic).
- **Constitution amendment backs this (change `w32m` v2.1.0; reframed `4s3e` v2.1.1 PATCH).** The site hosting deep synced prose required amending `constitution.md` v2.0.0 → v2.1.0 (the **Tool-Page Depth** constraint). `4s3e` reframed that constraint (v2.1.0 → v2.1.1, a PATCH — the deep-synced-content principle is unchanged; only the gate behavior block→report and page placement overview→readme change). The anti-drift value of the old "thin directory" stance is preserved and made explicit — content is single-sourced and mechanically synced, never hand-copied. See [tool-page-rubric](./tool-page-rubric.md#pulled-readme-slice-exception-change-w32m).
- **Reuse the one markdown processor for slugs, not a hand-rolled `github-slugger` helper (change `u4di`).** The readme rail needs heading slugs that equal `ReadmeSlice`'s rendered heading `id`s. The intake planned a shared `github-slugger` helper consumed by both sides; the implementation instead has **both** consumers call the SAME `createMarkdownProcessor({})` over the SAME slice, so `id === href` by construction (the processor's built-in `rehypeHeadingIds` owns the slug, and `metadata.headings` exposes it). *Why*: one source is a stronger guarantee than two slug reimplementations that could drift, and it adds **no** direct dep — `@astrojs/markdown-remark` is already declared+pinned, so `github-slugger` stays transitive-only (Constitution VI). *Rejected*: the intake's hand-rolled `github-slugger` helper + a direct `github-slugger` declaration (a second code path + an unnecessary direct dep); `rehype-slug` (redundant — the default processor already slugs); hand-parsing markdown headings in `readme-toc.ts` (the second slug path the intake itself forbade).
- **`readme-toc.ts` re-renders the slice independently, not via `ReadmeSlice`'s result (change `u4di`).** The rail builder runs its own processor render and reads `metadata.headings` rather than threading `ReadmeSlice`'s render through `Astro.locals`. *Why*: the dispatcher-routed ToC component and `ReadmeSlice` are separate component instances with no shared frontmatter; this mirrors the help side (`CommandReference` and `commands-toc.ts` each read `help/*.json` independently), and a second render of a small markdown file is cheap. *Rejected*: cross-component `Astro.locals` threading — fragile coupling for no benefit.
