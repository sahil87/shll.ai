# Tool Page Rubric

> **Live-site mismatch — read first.** The body of this rubric below describes the **non-live tailwind site** (`sites/astro-tailwind-terminal1`): single-page tool entries at `src/content/tools/{name}.md`, frontmatter validated by the `tools` zod schema in `src/content.config.ts`, and sidebar coupling via `src/data/tools.ts`. **That site is no longer live.** The live site (per `SITE_DIR` in `.github/workflows/deploy.yml`, swap `fbb046f`, 2026-05-31) is **Starlight** (`sites/astro-starlight-terminal1`): tools are **multi-page** (`src/content/docs/tools/<tool>/{overview,install,commands,workflows}.{md,mdx}`), the sidebar is **hardcoded in `astro.config.mjs`** (no `src/data/`). Fully reconciling this rubric's body to Starlight is a separate concern (the rubric predates the swap); this file currently carries the Starlight-aware additions below (the [Command reference exception](#generated-command-reference-exception) and onward, including the [site chrome overrides](#site-chrome-overrides-header-logo-footer-head-change-i2b0)).

## Overview

Every tool documented at `src/content/tools/{name}.md` follows the same shape. The rubric is short on purpose — these pages are "directory entries" pointing to each tool's full README on GitHub, not full docs.

This pattern is observable across all seven tool pages (`idea.md`, `hop.md`, `fab-kit.md`, `wt.md`, `run-kit.md`, `tu.md`, `shll.md`) and is the expected shape for any new tool added to the toolkit.

## Requirements

Every tool page MUST contain the following sections, in order:

1. **Frontmatter** — `title` (the tool name) and `description` (one sentence, ≤140 chars, the elevator pitch). MUST satisfy the `tools` collection schema in `src/content.config.ts` (zod: `{ title: string, description: string }`).
2. **Opening paragraph** — One short paragraph (1-2 sentences) describing what the tool is. SHALL NOT exceed two sentences.
3. **`## Install`** — A `bash` code block with the `brew install sahil87/tap/{tool}` line and any required shell-init eval (e.g., `eval "$(tool shell-init zsh)"`).
4. **`## At a glance`** — A `bash` code block with 4-6 representative commands and inline `# comment` annotations. Followed by a bulleted list of distinguishing properties (3-6 bullets).
5. **`## Full docs`** — One sentence pointing to the GitHub README, followed by `**→ [github.com/sahil87/{tool}](https://github.com/sahil87/{tool})**` as the link.

Tool pages SHALL NOT contain **hand-written**:

- Long-form command reference (every flag, every subcommand) — **except** the *generated* Command reference described in [the exception below](#generated-command-reference-exception). This rule still stands for hand-written content; the exception is narrowly for binary-generated reference.
- Architecture diagrams, Screenshots, or deep long-form prose — **except** the *mechanically-synced* README slice described in [the pulled-README-slice exception below](#pulled-readme-slice-exception-change-w32m). The old blanket bans on diagrams/screenshots/depth applied to **hand-copied** content; they no longer apply to content pulled-and-synced from the tool's canonical repo.
- Changelog or version history (hand-written; a tool's own README `## Changelog`, if present, may travel into the pulled slice — it is not denylisted by the extraction contract).

> **Stance revised (change `w32m`, constitution v2.1.0; refined `4s3e`, v2.1.1).** The earlier "site is a thin directory / link out for depth / no screenshots / no diagrams" stance is **superseded** by the constitution's **Tool-Page Depth** constraint ([`constitution.md`](../../../fab/project/constitution.md) v2.1.1). Tool pages MAY now host deep per-tool prose, referenced screenshots, and rendered diagrams — **provided** the content is mechanically synced from the canonical tool repo (README slice today; `docs/site/` reserved/future), never hand-copied. The anti-drift *value* behind the old stance is preserved and made explicit: single-source + mechanical sync (the producer repo stays canonical), not thinness.
>
> **The overview is thin again — but for a DIFFERENT reason than the original stance (change `4s3e`).** The original "short pages" stance kept the overview thin because *depth lived on GitHub* (link out). Under `4s3e` the **overview is once more a thin directory entry** (`<GithubButton>` + a 1–2 sentence framing + nav links to readme/commands/[install]/[workflows]), but depth is now **ON the site** — on the dedicated [`readme` page](#pulled-readme-slice-exception-change-w32m) (sourced from the canonical README), not on GitHub. Do not mistake the thin overview for a return to "link out for depth": depth moved to a sibling synced page, not off-site. The `vn39` cross-check is now **report-only** for the pulled slice (it surfaces divergence as a CI warning, it does not block the canonical README) — a hard rule only for hand-written prose. Both generated/synced exceptions below realize this (each as a dedicated sibling page).

## Generated Command reference (exception)

The one permitted exception to "SHALL NOT contain long-form command reference" is a **generated** CLI command reference, sourced from `help/<slug>.json` (see [help-collection](./help-collection.md)). On the **live Starlight site** it renders as each tool's dedicated **`commands` page** (`sites/astro-starlight-terminal1/src/content/docs/tools/<tool>/commands.{md,mdx}`), filling Starlight's existing "commands … coming soon" slot.

This is permitted precisely because it is **generated, not hand-written** — single-sourced from the binary's own `-h` output, so it cannot drift from the tool the way a hand-copied reference would. The anti-drift intent of the "SHALL NOT" rule is preserved: hand-maintained long-form reference is still forbidden; only binary-generated, single-sourced reference is allowed.

**Placement decision (now realized, change `js1s`).** The reference renders as a **dedicated `commands` page per tool** on the live Starlight site (multi-page docs model), chosen over an expandable `<details>` block on the `overview` page — the per-page model is the idiomatic Starlight shape and fills the existing empty `commands` slot.

The realized form: each tool has `src/content/docs/tools/<tool>/commands.mdx` (frontmatter `title: Commands` + a `description`) that imports `src/components/CommandReference.astro` and renders `<CommandReference tool="<tool>" />`. The component reads + validates + renders `help/<slug>.json` at build time (see [help-collection → Rendering Consumer](./help-collection.md#rendering-consumer-commandreference)). Pages are `.mdx` (not `.md`) precisely so they can `import` the component.

**Generated replaces hand-written.** idea and fab-kit previously carried hand-written `commands.md` prose; both were **removed** and replaced by the generated `commands.mdx` (a `.md` and `.mdx` at the same slug would collide in Starlight). The curated prose is not lost — its canonical home becomes each command's cobra `Long` field, which flows back through the producer into `help/<slug>.json` and onto the site automatically (tracked as idea backlog `e3rk`, out of scope here). Net effect: **no hand-written command-reference prose remains on any tool page**; the only command reference is the binary-generated one.

**Enriched/structured render + cross-tool index (change `qemq`).** The generated reference surface is now two surfaces, both still single-sourced from `help/*.json` (so the anti-drift guarantee holds):

1. The per-tool `commands` page no longer renders a flat raw `-h` blob — `CommandReference.astro` decomposes each node's captured `text` at build time (via `src/lib/parse-help.ts`) into a **structured view**: command path + copy, description, copyable usage, a flags table with type/required/global badges and per-row copy, a per-command flag filter, and a "show raw" `<details>` fallback (raw stays authoritative). Per-command `-h/--help` rows are suppressed, paired with a once-per-page universal-help note.
2. A new **cross-tool command index** at `/reference/command-index` (in a new "Reference" sidebar group) flattens every command path + real flag across all tools into one searchable list.

Both run at build time (Constitution I) and the parse is **display-only** — it never derives the command tree (still sourced from JSON `commands[]`), so it does not violate the help-dump contract §5 nor the anti-drift intent of this exception. Mechanics live in [help-collection → Rendering Consumer](./help-collection.md#rendering-consumer-commandreference).

## Homepage version block (build-time from `help/*.json` — change `jf3q`)

The homepage `$ shll version` terminal block (`sites/astro-starlight-terminal1/src/content/docs/index.mdx`) MUST source its per-tool version numbers from `help/<slug>.json` at build time — they SHALL NOT be hand-typed. This **extends the mechanical-sync principle** beyond the generated `commands` page and the pulled `readme` slice to the homepage version dump: any site-displayed version number is a synced value, never a hand-copied one.

**Why it became a rule (the drift it caught).** The block previously hard-typed all 7 tool versions; the `jf3q` audit found **every one** stale, and `wt`'s was a *fabricated* `v1.4.2` lifted from a `wt` planning-doc placeholder (real: `v0.0.16`). This is the exact hand-copy-vs-mechanical-sync trap the constitution's [Tool-Page Depth](../../../fab/project/constitution.md) constraint warns against — version strings drift on every release when hand-maintained.

**Realized form.** A NEW build-time component `src/components/VersionTable.astro` renders the block. It reads each rostered tool's `version` field from the synced `help/<slug>.json` (the same scheduled-puller source the `commands`/`readme` pages consume — see [help-collection](./help-collection.md)), normalizes the `v` prefix (prepend `v` if absent — `help/fab-kit.json` = `2.1.1`, `help/tu.json` = `0.4.17` lack it; the rest carry it), and emits the **same** terminal `shell-line` markup the homepage previously hand-wrote (label col + `shell-dim` version + `[git]` link, column-aligned under `white-space: pre`). `index.mdx` imports it and renders `<VersionTable />` between the `$ shll version` prompt and the cursor line.

- **Site-authored data stays IN the component, NEVER from JSON**: the roster, display order, display labels, route links, and repo URLs. **Only the `version` string is sourced from JSON.** This keeps the homepage site-authored framing while versions self-correct — and prevents the producer repo from dictating site presentation. (Rejected at intake: pulling labels/order from JSON.)
- **Self-correcting**: when a future scheduled-puller commit bumps a `version` in `help/*.json`, the next rebuild reflects it with **zero source edit**.
- **Mirrors `CommandIndex.astro`'s read+validate pattern** — `repoRootFromModuleUrl(import.meta.url)` (`src/lib/repo-root.ts`) + `HelpDocSchema.parse` (`src/lib/schemas.ts`; the `version` field is `HelpDocSchema`-required). It **reuses both shared libs, no reimplementation** (consistent with the two-consumer posture in [help-collection](./help-collection.md#rendering-consumer-commandreference)).
- **Build-stopping on missing/invalid JSON** (mirrors `CommandIndex.astro`): a missing or schema-invalid `help/<slug>.json` throws with a descriptive error naming the offending file — a stale/missing-version defect MUST NOT deploy.
- It is a **build-time read** (Constitution I — no runtime fetch, no new dependency Constitution VI) and emits **unchanged markup**, so dark-mode parity (Constitution V) holds for free.

### `rk` vs `run-kit` — the CLI-identity vs repo/section naming rule (change `jf3q`)

run-kit's **binary and brew-formula identity is `rk`** — the tool prints `rk` in its own `shll version` row and its formula is `rk.rb`. `run-kit` is **only** the GitHub repo / site-section name. CONVENTION for hand-authored site prose:

- Use the **binary identity `rk`** wherever prose names a CLI a user *types* OR a token the tool itself *prints* — a version-dump row, an install-output line, a command invocation.
- Reserve **`run-kit`** for the **repo / section** reference: the `/run-kit` route slug, the `github.com/sahil87/run-kit` repo URL, and the directory/nav section label all correctly stay `run-kit` (changing them would break routing/directory framing).

The `VersionTable` realizes exactly this: it renders the run-kit row with display label **`rk`** while keeping route `/run-kit` + repo URL `github.com/sahil87/run-kit`. This is the binding distinction the `jf3q` audit applied across `index.mdx` and the `workflows` pages.

> **Hand-authored prose accuracy baseline (reinforced, `jf3q`).** Hand-authored site prose MUST match each tool's own repo — commands, flags, and stage count included (this is the [`vn39` hard rule for hand-written prose](#pulled-readme-slice-exception-change-w32m) above; see also [help-collection](./help-collection.md#hand-written-prose-must-not-contradict-helpjson-the-binding-rule)). The `jf3q` audit is precedent: it corrected a batch of prose errors against ground truth — fab-kit is a **6-stage** pipeline (intake → apply → review → hydrate → ship → review-PR, **no spec stage**); hop grammar is `hop <selection> <action>` (`hop --all pull`, `hop ls --trees` — no `hop pull`/`hop status`); `wt delete --stale` (not `wt list --stale`); `idea list` takes flags only with no positional filter and idea has **no tag concept**; bare `tu` shows **today**; and `fab change new` creates the folder + `.status.yaml` while the `/fab-new` skill writes `intake.md`.

## Pulled README slice (exception, change `w32m`)

The second permitted exception to the hand-written bans is a **mechanically-synced README slice** — deep prose, referenced screenshots, and rendered diagrams pulled from the tool's canonical README. It is permitted for the **same reason** as the generated Command reference: it is **synced, not hand-written** — single-sourced from the tool's own repo and refreshed daily, so it cannot drift the way a hand-copied page would. The anti-drift intent of the "SHALL NOT" rules is preserved; only the *mechanism* (mechanical sync) is what makes depth safe.

This is the prose counterpart to the generated Command reference (which is the *command* counterpart). Together they realize the constitution's [Tool-Page Depth](../../../fab/project/constitution.md) constraint (v2.1.1 — reframed from v2.1.0 by change `4s3e`): the site can be deep, because depth is single-sourced and synced. Both now render as **dedicated sibling pages** (`commands` + `readme`), not injected into the overview.

**Realized form (render placement revised, change `4s3e`).** A daily pull workflow deduces a curated slice from each tool's README (skip leading chrome; stop before footer chrome; strip mermaid + GitHub theme-only images), runs it through the `vn39` command/flag **divergence reporter** (report-only — change `4s3e`, see below), and **always commits** it to the repo-root collector `content/<slug>/README.md`. The slice renders on a **parallel per-tool `readme` page** — `src/content/docs/tools/<tool>/readme.mdx` (frontmatter `title: Readme`, sidebar label "Readme", slug `/tools/<tool>/readme`) — that renders `<ReadmeSlice tool="<slug>" />`. This is a **new generated/synced page type, a sibling of the generated `commands` page** (the command counterpart). `ReadmeSlice.astro` is a build-time component that reads the slice via the ascend-to-root `import.meta.url` pattern and renders markdown→HTML at build time (Constitution I), with missing→placeholder / present-but-invalid→build-fail discipline.

> **Superseded `w32m` injection (change `4s3e`).** `w32m` injected `<ReadmeSlice>` into each `overview.mdx` under `<GithubButton>`. That is **reverted** — `<ReadmeSlice>` is removed from all 7 overviews and the synced slice lives on the dedicated `readme` page. This separates the two authors: the overview is **site-authored framing**; the readme page is the tool's **canonical own words**. It follows `qemq`'s precedent (the generated command reference got its own `commands` page, not an overview injection).

**The depth gate is report-only for pulled prose (change `4s3e`).** The `vn39` command/flag cross-check is a **non-fatal reporter** for the canonical, mechanically-synced slice — divergence emits a CI `::warning::` and the canonical README is committed/rendered **verbatim** anyway (the README is canonical; you fix the tool repo, not censor it on the site). The `vn39` rule stays a **hard rule** only for *hand-written* site prose. Do not conflate the two consumers — see [help-collection](./help-collection.md#hand-written-prose-must-not-contradict-helpjson-the-binding-rule) and [readme-extraction → the divergence reporter](./readme-extraction.md#the-vn39-divergence-reporter-report-only-change-4s3e).

Mechanics live in [readme-extraction](./readme-extraction.md); the forward contract is [`docs/specs/readme-extraction-contract.md`](../../specs/readme-extraction-contract.md). The slice is rendered on the **per-tool axis** (the `readme` page); the cross-tool `Reference` axis (`qemq`) is a separate surface and is untouched.

**Coexistence with install content.** A pulled `Install` section (it is INCLUDED in the slice, not excluded) is canonical for "install just this tool + its specifics"; the global `getting-started/install` quick-start stays canonical for "install the whole toolkit." Both ship, framed differently — accepted as legitimate, since both can be simultaneously correct; the `vn39` cross-check (now a reporter, not a guard — change `4s3e`) surfaces but does not block a divergent pulled install's command accuracy.

> **No site-authored `install`/`workflows` static pages (change `ng8c`).** The live site formerly carried **hand-authored** `install.md` + `workflows.md` static pages for `idea` and `fab-kit` (`src/content/docs/tools/<tool>/`). Those were **site-authored prose with no canonical source** — exactly the hand-copied drift this rubric's Tool-Page-Depth stance forbids — and were **removed**. `install` and `workflows` are no longer site-owned reserved slugs; the reserved set is now exactly **`overview`, `readme`, `commands`** (the hand-authored overview + the two generated/synced pages). A tool that wants an install guide or workflows page publishes it as `docs/site/install.md` / `docs/site/workflows.md` in its own repo, rendered (mechanically synced, not hand-copied) at `/tools/<slug>/install|workflows` via the [docs/site tree](./docs-site-tree.md). The thin overview's nav links to readme/commands stay; install/workflows bullets were dropped (a future `docs/site` install page surfaces automatically via the generated sidebar group).

## Right-rail "On this page" ToC (generated, dispatcher-routed — change `u4di`)

Both **generated/synced** sibling pages — the `commands` page and the `readme` page — carry content Starlight's native right-rail "On this page" ToC **cannot see**, so each needs a custom build-time ToC that fills the rail. The native ToC is built from the `.mdx` file's own heading AST at compile time, but these `.mdx` files contain only a single component call (`<CommandReference .../>` / `<ReadmeSlice .../>`); the real navigable structure lives in a runtime string the AST never sees (the commands page renders `<details>/<summary>`, not headings; the readme slice's `##`/`###` headings live inside a `set:html` string). Result: the two **deepest** pages on the site would otherwise have an empty native rail — a usability regression relative to every other page. The fix mirrors per-source: each page builds its rail from the page's own source of truth (`help/<tool>.json` for commands; `content/<tool>/README.md` for readme).

**The README ToC (`readme` page).** The readme page's rail is sourced from the same `content/<tool>/README.md` slice [`ReadmeSlice`](./readme-extraction.md#the-readmesliceastro-render-component) renders, as a **nested H2 → H3 tree** (matching the site's `tableOfContents: { minHeadingLevel: 2, maxHeadingLevel: 3 }`). The pieces, all in `sites/astro-starlight-terminal1`:

- **`src/lib/readme-toc.ts`** (build-time helper, the README sibling of `commands-toc.ts`) — detects a `tools/<tool>/readme` route id (`README_ROUTE_RE = /^tools\/([^/]+)\/readme$/`, exported `toolFromReadmeRouteId`), reads the slice via the **`help/`-marker `repoRootFromModuleUrl` ascent** (`lib/repo-root.ts`, the same ascent `ReadmeSlice` uses — anchored on the module URL, NOT a fixed depth, NOT `content/` which collides with Starlight's `src/content/`), re-renders it with `createMarkdownProcessor({})`, reads `rendered.metadata.headings`, and folds the H2/H3 entries into a nested `TocHeading` tree (`{ text, slug, depth, children }`; H4+ ignored; an orphan H3 before any H2 attaches at top level rather than crashing). Failure contract mirrors `firstLevelCommands`: ENOENT → `[]` (page falls back to the default ToC), genuine errors re-throw.
- **`src/components/ReadmeToc.astro` + `ReadmeMobileToc.astro`** (NEW, **separate** from the commands components — the intake mandated separate components, not an extension of `CommandsToc`/`CommandsMobileToc`). Desktop emits a `<starlight-readme-toc>` element wrapping a labelled `<nav>` + "On this page" `<h2>` + a nested H2/H3 `<a href="#{slug}">` list; mobile emits a `<readme-mobile-toc>` `<details>` dropdown mirroring `CommandsMobileToc`'s frame. Both render Starlight's `<Default />` on an empty tree. The static nested list is fully usable with JS disabled (Constitution I); progressive-enhancement scroll-spy (`IntersectionObserver`) tracks **both** levels — it highlights the in-view H3 **and** its parent H2 (`aria-current="true"` on both). This is simpler than the `<details>`-based commands scroll-spy (real headings, no expand-on-click), but observes two heading levels rather than the commands page's flat first-level list.
- **Slug single-sourcing (do not "fix" this).** Both the rendered heading `id`s (`ReadmeSlice`) and the ToC `href`s (`readme-toc.ts`) come from the SAME `createMarkdownProcessor({})` render of the SAME slice, so `href === id` holds **by construction** (verified: 0 mismatches across all 7 tools, dedup suffixes included). NO `github-slugger` direct dependency was declared — see [readme-extraction → Slug single-sourcing](./readme-extraction.md#slug-single-sourcing-rendered-ids--toc-hrefs-via-one-processor-change-u4di) for the full rationale; a future maintainer MUST NOT add `github-slugger` or a second slug path.

**The dispatcher pattern (reusable convention).** Starlight's ToC override slots are **global and singular** — there is exactly one `components.TableOfContents` and one `components.MobileTableOfContents`. Before `u4di` those slots pointed straight at `CommandsToc`/`CommandsMobileToc`. `u4di` introduces a **route dispatcher** so the single slot can fan out by page:

- `src/components/TocDispatcher.astro` + `MobileTocDispatcher.astro` (NEW) are now the registered override slots in `astro.config.mjs`. Each inspects `Astro.locals.starlightRoute.id` and renders `CommandsToc` for `tools/*/commands`, `ReadmeToc` for `tools/*/readme`, else Starlight's `<Default />` (reusing `toolFromRouteId` + `toolFromReadmeRouteId`; the two route regexes are mutually exclusive). Commands-page output is preserved **byte-for-byte** — the dispatcher is a transparent pass-through for commands routes.
- **Convention going forward**: the single ToC override slot is now a dispatch point. The **next** ToC variant (a third generated/synced page type) MUST extend the dispatcher with another route branch — NOT re-add a competing override slot (there is only one) and NOT fall-through-chain among the custom components (rejected at intake: implicit, hard-to-trace routing spread across components). Routing stays central and traceable in the two dispatchers.

**Terminal styling.** `starlight-readme-toc` is added to the existing `terminal.css` ToC selector groups (the `# ` heading prefix, `> ` active marker, mono link colors — shared by `starlight-toc`/`starlight-commands-toc`), plus an H3-child indent. Dark-mode parity (Constitution V) follows for free from the shared `--c-*` variables that flip with `data-theme` — no per-component theme branch.

## Site chrome overrides: header logo, Footer, Head (change `i2b0`)

Beyond the ToC dispatcher slots, the live Starlight site's `components:` block in `astro.config.mjs` now overrides **`Footer`** and **`Head`** as well (so the block registers four overrides: `TableOfContents`, `MobileTableOfContents`, `Footer`, `Head`). All site chrome lives in `sites/astro-starlight-terminal1`.

**Header logo — the run-kit grayscale hexagon.** `logo.src` in `astro.config.mjs` points at `src/assets/logo.svg` (mirrored verbatim from `sahil87/run-kit` `assets/logo.svg`, carrying a provenance comment — there is no auto-sync pipeline, so it is hand-updated if the source changes), with `replacesTitle: false` retained (the hexagon sits BESIDE the "shll" wordmark, not replacing it). The SVG's hardcoded grayscale palette (`#b4b4b4 … #2a2a2a`) is a deliberate **dual-theme-by-palette** design — it reads correctly in both light and dark mode with NO `currentColor`, CSS filter, or theme-toggle mechanism. This satisfies Constitution V (Dark Mode Parity) by palette, not by mechanism; do NOT "fix" it to `currentColor` (that would discard the intentional 3D shading that makes the hexagon read as a cube). The old `prompt.svg` (terminal-prompt chevron) is deleted.

**Footer override — render `<Default />`, then APPEND (never discard).** `src/components/Footer.astro` adds a `© Sahil Ahuja 2026` line site-wide. Starlight's single `Footer` override slot REPLACES the built-in footer — which carries the prev/next pagination (and edit-link / last-updated). To add footer chrome **without losing pagination**, the override renders the built-in `<Default />` first, then appends the copyright `<div>`; it MUST NOT discard `<Default />`. Version note: installed `@astrojs/starlight` **0.39.2**'s default `Footer.astro` takes NO props and renders NO `<slot />` (it self-renders the pagination/edit-link/last-updated from virtual modules + `Astro.locals`), so the version-correct override is a **bare `<Default />`** — no `{...Astro.props}`, no child slot. The copyright color comes from a theme-aware `--c-*` token (`var(--c-fg-dim)` + `var(--sl-text-xs)` mono, from `terminal.css`), so dark-mode parity is automatic (Constitution V) — no hardcoded color.

**Head override — emit a LITERAL attribute value via `set:html` (reusable gotcha).** `src/components/Head.astro` injects a site-wide `<head>` tag (here the Cloudflare Web Analytics beacon — see [build-deploy/deployment](../build-deploy/deployment.md)). The pattern + its WHY: site-wide `<head>` injection that must emit a **literal, un-escaped attribute value** does NOT go through Starlight's `head:` config array — that array renders each entry as `<Tag {...attrs}>` and **Astro HTML-escapes attribute values**, so a JSON attribute like Cloudflare's `data-cf-beacon='{"token": "..."}'` comes out with `&quot;` entities (browsers decode it back at runtime, but it is not the literal tag). Instead, override `Head.astro`: render `<Default />` (still emits Starlight's title/meta/canonical/favicon/fonts and any `head:` config entries), then append the literal tag via `<Fragment set:html={...} />`. Same bare-`<Default />` version note as Footer applies (0.39.2's default Head takes no props/slot — it maps over `Astro.locals.starlightRoute.head`). This `head:`-escaping gotcha is worth recording for any future literal-attribute head injection.

## Per-tool GitHub affordance (live Starlight site)

Every tool **overview** page on the live Starlight site (`sites/astro-starlight-terminal1/src/content/docs/tools/<tool>/overview.mdx`) MUST render a top-of-page GitHub affordance: `<GithubButton tool="<slug>" />`, just under the H1. The component (`src/components/GithubButton.astro`, change `vn39`) takes a `tool` slug prop and links to `https://github.com/sahil87/{tool}` — build-time only (no client JS, Constitution I), styled with the terminal `--c-*` tokens (dark-mode parity, Constitution V), with a visible `:focus-visible` ring (Accessibility). It mirrors `CommandReference.astro`'s conventions (`not-content`, scoped `<style>`, frontmatter `interface Props`, missing-slug build guard).

**`.md` → `.mdx` for overviews.** Because importing an Astro component requires MDX, all 7 tool overviews are `.mdx` (not `.md`), mirroring the existing `commands.mdx`. The import path from `src/content/docs/tools/<tool>/` to the component is `../../../../components/GithubButton.astro` (4 `../`). Starlight sidebar slugs (`tools/<tool>/overview`) are extension-agnostic, so the rename does not touch `astro.config.mjs`.

**Redundancy note.** The rubric-mandated bottom-of-page `**→ [github.com/sahil87/{tool}]**` README pointer (where present) now coexists with the top button. This is intentional — the top button is the persistent "jump to repo" affordance; the footer pointer is the "deepest reference / full README" link in footer prose context. `idea` and `fab-kit` overviews carry only the top button (no footer pointer), so there is no duplication there.

## Bullet Style

Bullets in the "At a glance" section MUST use the pattern: **bold short claim** — em-dash — short explanation. Examples from existing pages:

- **Plain Markdown, not a database** — the backlog is a checked-in file.
- **Substring navigation** — `h ou<TAB>` matches `outbox`.
- **One-shot install** — idempotent and safe to re-run.

Rationale: scannable on mobile, parallel structure across the toolkit, easy to extend.

## Sidebar Coupling

Every new tool page MUST also have a corresponding entry in `src/data/tools.ts` (`{ slug, label, blurb }`). See [astro-config](../site/astro-config.md). Adding a page without an entry leaves the page unreachable from the sidebar AND missing from the home-page tree-list (both read from `tools.ts`).

## Design Decisions

- **~~Short pages, not deep docs.~~ Deep, but synced — not hand-copied (revised, change `w32m`, constitution v2.1.0; render placement revised, change `4s3e`, v2.1.1).** The original stance ("the site is a directory; the READMEs are the destination; duplicating them here invites drift") was correct about the *drift* but wrong to conclude *thinness*. The drift it feared came from **hand-copying**, not from depth. The site may now host deep per-tool content because that content is **mechanically synced** from the canonical repo (the [pulled README slice](#pulled-readme-slice-exception-change-w32m)), never hand-copied — so it is fresh by construction and cannot rot. A visitor SHOULD now be able to understand a tool deeply *on the site* without clicking out to GitHub; the tool repo stays canonical (it is where docs are authored), and the daily pull keeps the site in sync. **The overview is thin again (change `4s3e`)** — but unlike the original "link out for depth" thinness, the depth now lives on the site's dedicated `readme` page (sourced from the canonical README), not on GitHub. The thin overview is a directory entry (framing + nav); the depth is one click away *on the site*. *Rejected*: injecting the slice into the overview (the `w32m` model — collides site framing with the canonical slice, double-pitches the tool).
- **Brew install line in every page.** Even though `shll install` installs everything, individual brew lines let visitors install one tool without buying into the whole toolkit.
- **`At a glance`, not `Usage`.** The section is deliberately a teaser, not a tutorial. The name signals "skim this, then read the full README."
- **One dispatch point, not N override slots (change `u4di`).** Starlight gives exactly one `TableOfContents`/`MobileTableOfContents` override slot. Rather than have each generated page type contend for that single slot, a thin `TocDispatcher`/`MobileTocDispatcher` owns it and routes by `Astro.locals.starlightRoute.id` to the per-page ToC (commands → `CommandsToc`, readme → `ReadmeToc`, else `<Default />`). *Why*: a single, traceable routing point; commands behavior is preserved byte-for-byte; the next ToC variant extends the dispatcher with a branch instead of needing a (nonexistent) second slot. *Rejected*: fall-through chaining among the custom components — implicit routing spread across components, harder to trace.
- **Generated/synced pages get a generated rail from their own source (change `u4di`).** A page whose body is a single component call has no headings in the `.mdx` AST, so Starlight's native rail is empty. Each such page builds its own ToC from the page's source of truth (`help/*.json` for commands, `content/<tool>/README.md` for readme) at build time, with a PE scroll-spy enhancing a static list. *Why*: the deepest pages on the site otherwise have the emptiest rail. The readme rail single-sources its slugs through the SAME `createMarkdownProcessor({})` render `ReadmeSlice` uses (`href === id` by construction), so **no `github-slugger` direct dep and no second slug path** — see [readme-extraction](./readme-extraction.md#slug-single-sourcing-rendered-ids--toc-hrefs-via-one-processor-change-u4di). *Rejected*: a hand-rolled shared `github-slugger` helper (the original intake plan) — a second slug code path that could drift, and a direct dep with no need beyond the already-declared `@astrojs/markdown-remark` (Constitution VI).
