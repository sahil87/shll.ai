# Help Collection

## Overview

Each of the 7 tools in the toolkit (`idea`, `hop`, `fab-kit`, `wt`, `run-kit`, `tu`, `shll`) emits its own `-h`/`--help` output as a structured JSON document via a uniform `<tool> help-dump` subcommand. shll.ai **pulls** those documents on a schedule, collects them at the **repo root** under `help/<slug>.json`, and renders them as a generated command reference on the site.

The point is anti-drift: help text is **machine-generated by the binary**, so capturing it from the live binary means the site's command reference is as fresh as the last refresh *by construction* — there is no hand-maintained copy to rot. This is what makes a generated command reference safe where a hand-copied one would violate the [tool-page rubric](./tool-page-rubric.md).

This file documents the **consume/pull side** — how shll.ai pulls, validates, collects, and renders the help documents. The **forward contract** — what each tool's `help-dump` MUST emit — lives in the spec [`docs/specs/help-dump-contract.md`](../../specs/help-dump-contract.md). The schema is defined in exactly two places: that spec (prose) and `sites/astro-starlight-terminal1/src/lib/schemas.ts` (the machine-checkable code anchor). This memory file does **not** restate the full schema — it points to the contract and the anchor.

> **Sibling consumer (change `w32m`).** The pull architecture this file documents now has a **second consumer**: [README extraction](./readme-extraction.md) pulls a curated *prose slice* of each tool's README (the prose counterpart to this *command reference*). It reuses the same patterns proven here — a **daily scheduled job off the deploy path** (`scheduled-readme-refresh.yml`, sibling of `scheduled-help-refresh.yml`), **repo-root data surviving a live-site swap** (`content/<slug>/README.md`, sibling of `help/<slug>.json`), the **ascend-to-root `import.meta.url` build-time read**, the **missing→placeholder / present-but-invalid→build-fail** discipline, and the **`vn39` command/flag cross-check** below — now run on pulled README prose too, but as a **report-only divergence reporter** for that consumer (change `4s3e`: the canonical README is rendered verbatim; divergence warns, never blocks), while it stays a **hard rule** for hand-written prose (see [the two modes](#hand-written-prose-must-not-contradict-helpjson-the-binding-rule)). The two pulls are kept as **distinct sibling workflows** (different data kinds, different gates) rather than one merged job. The README extraction logic also follows the [`parseHelp` precedent](#rendering-consumer-commandreference) — a pure, dependency-free, native-test-pinned build-time parse — see [readme-extraction](./readme-extraction.md).

> **History.** The contract and Zod module landed in change `xiis`; the rendering consumer in change `js1s`. Change `oa63` (2026-06-03) **inverted the transport from PUSH to PULL** — the prior model (7 tool repos opening auto-merged PRs into shll.ai) is retired in favor of a scheduled refresh job that brew-installs the tools and runs `help-dump`. See the Changelog.

## Hand-written prose must not contradict `help/*.json` (the binding rule)

The `help/*.json` documents are the machine-generated source of truth for **command and flag names**, not just the input to the generated `CommandReference`. Any hand-written prose on the site (install snippets, "at a glance" examples, workflow recipes) **MUST NOT** reference a CLI command or flag that is absent from the relevant `help/<tool>.json`. The enforcement check is a grep-zero gate over `sites/<live-site>/src/content` for known-fabricated tokens, plus a per-command cross-check against the tool's help tree.

> **TWO consumers, TWO modes — do NOT conflate (change `4s3e`).** The cross-check (`findUnknownTokens` against `help/<tool>.json`) has **two callers with deliberately different consequences**:
> 1. **Hand-written site prose → HARD rule (unchanged).** Site-authored content (overview framing, install snippets, "at a glance", workflow recipes) MUST NOT cite commands/flags absent from `help/<tool>.json`. A violation is a defect to fix in the prose. This is the original `vn39` rule and is **unchanged**.
> 2. **Pulled README slice → REPORT-ONLY lint (change `4s3e`).** The mechanically-synced README slice is the tool's **canonical** content, rendered **verbatim**. Divergence from `help/<tool>.json` is surfaced as a non-fatal CI `::warning::` and the slice is committed/rendered anyway — the fix belongs in the tool's README (the source of truth), not in withholding it on the site. See [readme-extraction → the divergence reporter](./readme-extraction.md#the-vn39-divergence-reporter-report-only-change-4s3e).
>
> Same detector, opposite consequences: a hand-written contradiction is a bug to fix before it ships; a pulled-prose divergence ships (canonical) with a warning. The distinction is *who authored the prose* — site author (must be correct up front) vs. tool author (canonical, corrected at the source).

This rule was established by change `vn39`, which found the live site documenting commands/flags that never existed: `shll doctor`, `shll list`, `shll shell-install` (a legacy alias, not a real command — the canonical command is `shll shell-setup`), `wt create --from-idea`, `fab change new --from-idea`, `idea list --tag`, and `fab sync` (only `fab hook sync` exists). All were removed or replaced with verified equivalents. The canonical "install everything" sequence is single-sourced to the `shll` quick-start: `brew install sahil87/tap/shll` → `shll install` → `shll shell-setup --trust-tap` → `exec $SHELL`.

> **Known residual (out of `vn39` scope, follow-up).** A whole-tree sweep also flagged pre-existing unverified commands on lines `vn39` did not touch: `fab init` and `fab kit sync` (`tools/fab-kit/install.md` — absent from `help/fab-kit.json`), and `hop outbox …` / `hop status --all` (`hop/overview.mdx`, `workflows/daily-flow.md` — `outbox`/`status` absent from `help/hop.json`). `help/tu.json` does not exist yet, so `tu` command claims cannot be machine-verified. A future command-accuracy pass should reconcile these.

## The contract (where it lives)

A single JSON document per tool — an **envelope** (`{tool, version, captured_at, schema_version, root}`) wrapping a recursive **Node** tree (`{name, path, short, usage, text, commands: Node[]}`). The full, self-contained definition — including the `captured_at` asymmetry (tool-emitted output omits it; the puller stamps it) — is the forward contract:

> **Forward contract**: [`docs/specs/help-dump-contract.md`](../../specs/help-dump-contract.md) — §1 invocation, §3 output schema, §4 filter rules, §5 discovery, §6 version, §7 the `tu` exception, §8 schema evolution.

The **file** is named by the tool's repo/site slug, even where the binary differs: `help/run-kit.json` (binary `rk`), `help/fab-kit.json` (binary `fab`). The `tool` field inside carries the binary name.

## Zod Schema Module (the machine-checkable contract)

The schema is defined once in `sites/astro-starlight-terminal1/src/lib/schemas.ts` (the **live** site per `SITE_DIR` in `.github/workflows/deploy.yml`) and exported (`HelpDocSchema`, `NodeSchema`):

- It imports `z` from `astro:content` — Starlight provides zod **transitively**, so this contract adds **NO new dependency** and needs **NO repo-root Node toolchain**. The repo root holds only the `help/*.json` data files; there is **no repo-root `package.json`** (Constitution II, VI).
- The recursive `commands` field is expressed with `z.lazy` (a Node references itself).
- It is the **single** machine-checkable definition of the contract — the puller's validation gate, the standalone validator, and the `CommandReference` loader all validate against it; there is no second, separately-maintained shape. The prose contract (`help-dump-contract.md` §3) MUST agree with this module; on any discrepancy, `schemas.ts` is authoritative for machine validation.

### Validating samples

`sites/astro-starlight-terminal1/scripts/validate-help.mjs` loads every `help/*.json` at the repo root and validates each against `HelpDocSchema`, exiting non-zero on failure. Run it via the live site's pnpm-installed toolchain:

```bash
cd sites/astro-starlight-terminal1
pnpm install --frozen-lockfile   # once
node scripts/validate-help.mjs
```

Because the schema module imports the `astro:content` virtual module (which only resolves inside an Astro build), the validator registers a tiny resolve hook (`scripts/astro-content-alias.mjs`) that aliases `astro:content` → `astro/zod` — the same `z` Astro re-exports — so the standalone validator imports the SAME schema module with no duplicated shape. The validator imports the `.ts` schema directly and relies on Node's native **type-stripping**, which is on by default (no flag) from **Node 22.18** onward (it existed behind `--experimental-strip-types` from 22.6). The site is pinned to Node 22 in both `deploy.yml` and the scheduled refresh workflow, which resolves to the latest 22.x — well past 22.18 — so this holds in CI.

## The `help/` Collector

`help/` is a top-level directory at the **repo root** (sibling to `sites/`, `fab/`, `docs/`), holding `help/<slug>.json` per tool. It is **not** nested under any `sites/<name>/`.

**Why the root.** The help data is project-level, not owned by any one site variant. Keeping it at the root means it **survives a live-site swap** (Constitution III — One Live Site at a Time): changing `SITE_DIR` to a different site under `sites/` does not require moving or duplicating the collector. This is the deliberate read of Constitution II (Multi-Site Isolation) — the data is shared, the *sites* are isolated.

### Cross-boundary read (by design)

The Zod module — and the `CommandReference.astro` component — live **inside** `sites/astro-starlight-terminal1/src/`, while the `help/*.json` data lives at the repo root. So the component reads from **outside** its site directory, up and out to `<repo-root>/help/`. This is the **intended** design, not a violation of site isolation: the data is project-level by deliberate placement, and only the *reading* site reaches into it. `<repo-root>/help/*.json` is an expected input, not an anomaly. The implemented read mechanism is detailed in [Rendering Consumer](#rendering-consumer-commandreference).

## Rendering Consumer (CommandReference)

The consume side — deferred as a follow-up by the original contract — now exists, implemented in change `js1s`. It is `sites/astro-starlight-terminal1/src/components/CommandReference.astro`, the **first importer** of `src/lib/schemas.ts` and the first reader of `help/*.json`. It is **transport-agnostic** — it does not care whether a PR or a cron put the file there.

- **Prop**: `tool` (the slug, e.g. `"wt"`). The component does the read + validate + render; page authors only pass the slug.
- **Placement**: rendered from each tool's `commands` page — `src/content/docs/tools/<tool>/commands.mdx` — which imports the component and renders `<CommandReference tool="<tool>" />`. All 7 tools have a `commands` page wired (idea/fab-kit's prior hand-written `commands.md` was removed in favor of the generated `.mdx`); the sidebar in `astro.config.mjs` lists a `Commands` entry for each. Today 6 of 7 tools have data committed (`fab-kit`, `hop`, `idea`, `run-kit`, `shll`, `wt`), so those render the real reference; only `tu` is still missing (`help/tu.json`) and renders the placeholder until its producer lands.
- **Build-time `fs` read (NOT glob, NOT fetch, NOT `process.cwd()`)**: the component reads the file with Node `fs` in its frontmatter (which runs during `astro build`), keeping the render static (Constitution I). The path is anchored on the module via `import.meta.url`.
  - **Resolution gotcha (load-bearing)**: a *fixed* relative depth (e.g. `../../../../help`) does **NOT** survive `astro build`. Vite bundles the component frontmatter into a chunk at an unstable depth (observed: `dist/.prerender/chunks/`), so the `..` count measured from the source file (`src/components/`) under-shoots at build time and the read silently ENOENTs — the page degrades to the placeholder even when data exists. The robust fix the component uses (`findRepoRoot`): **ascend from `import.meta.url`'s directory until a `help/` directory is found**, and read `<that-root>/help/<tool>.json`. This anchors on the module URL (not `process.cwd()`, which varies by invocation) yet is correct in both `astro dev` (source location) and `astro build` (bundled location), and survives changes to Astro's output layout. The ascent is a **bounded** loop (capped at a generous ancestor count); if no `help/` ancestor exists at all it throws a clear, build-failing error — that signals a broken cross-boundary contract, a distinct condition from the per-tool missing-file case below (which degrades to a placeholder, not a build failure). `import.meta.glob` is *not* usable here: Vite constrains it to the project-root `fs.allow`, which excludes files outside the site dir.
- **Validation**: `HelpDocSchema.parse()` from `src/lib/schemas.ts` — the same single contract shape, no second copy.
- **Missing vs. invalid (the two distinct failure modes)**:
  - **MISSING** (`ENOENT`, caught specifically): render a neutral placeholder ("Command reference not generated yet — see the GitHub README", linking to the tool's GitHub) and **let the build succeed**. A missing file is the expected interim state while producers land over weeks (e.g. `help/tu.json` while `tu`'s `help-dump` is in progress — see contract §7).
  - **PRESENT but schema-invalid** (or malformed JSON): the parse error propagates (wrapped with the offending filename) so **`astro build` fails** loudly and non-zero. A committed-but-malformed help file is a real defect that must not deploy. The two cases are never conflated — ENOENT is caught; everything else throws.
- **Render**: the recursive tree from `doc.root` (via `Astro.self`) — nested `commands[]` nest visually; a leaf (`commands: []`) renders no children. Collapsibles use native `<details>`/`<summary>` (keyboard + screen-reader semantics for free, zero JS). Styling reuses the terminal `--c-*` tokens so dark-mode parity follows Starlight's `data-theme` flip with no per-component script. Per node, the body is the **structured view** below (change `qemq`), not a raw-text-only `<pre>`.
- **Build-time `parseHelp` decomposition (change `qemq`)**: each node's raw `text` is decomposed at build time by the pure, dependency-free `parseHelp(text)` in `src/lib/parse-help.ts` into `{description, usage, examples, flags[], globalFlags[]}`. It anchors ONLY on known Cobra section headers; the `description` is everything before the first anchor, preserved verbatim (so hand-written `Long` blocks — hop/shll — survive untouched). The flag grammar handles value placeholders that may contain spaces, splits a trailing `(default …)` into its own field, and detects `(required)`. Backed by `scripts/parse-help.test.mjs` (native `node --test`, type-stripping — same toolchain as `validate-help.mjs`), which asserts **zero ragged flag lines** across all committed `help/*.json` plus the named edge cases. This pure/dependency-free/native-test-pinned build-time-parse shape is the **precedent** the README extraction module (`extract-readme.ts`, change `w32m`) follows — see [readme-extraction](./readme-extraction.md).
- **Structured per-node view (change `qemq`)**: `CommandReference.astro` renders the parsed parts as: the `path` + copy button, a description block, copyable usage line(s), a **flags table** (name · type/required/global badges · description, each row copyable), a **per-command flag filter** input, and a **"show raw" `<details>` toggle** with the verbatim `-h` text. The raw text remains the **authoritative fallback** — for prose-only nodes (empty `flags`) the description/raw is the primary content. Per-command `-h, --help` rows are **suppressed** from the table; this is paired with a **single universal-help note** (rendered once per page, not per command) stating `-h`/`--help` work on every command and `-v`/`--version` at the tool root — the note preserves that the affordance is universal while removing the visual repetition. The filter is progressive-enhancement client JS over already-static rows.
- **Cross-tool command index consumer (change `qemq`)**: a second consumer of the same data + `parseHelp` — `src/components/CommandIndex.astro`, rendered at `src/content/docs/reference/command-index.mdx` (slug `/reference/command-index`, in a new "Reference" sidebar group added to `astro.config.mjs`). At build time it reads all `help/*.json` (reusing the `findRepoRoot` ascent pattern — duplicated, not extracted, to leave `CommandReference`'s read path untouched) and emits a flat searchable list of every **command path** and every **real flag** across tools (Global Flags included; `-h`/`--help`/`-v`/`--version` excluded — the universal-help note carries that fact; prose-only roots listed as commands). A client-side search filters the pre-rendered static rows (progressive enhancement only). Each entry deep-links to the owning tool's `commands` page.
- **Display-only vs. spec §5 structure (the boundary — record explicitly)**: `parseHelp` is **DISPLAY-ONLY** and runs at **BUILD TIME** (Constitution I). It does NOT derive the command **tree structure** — that still comes from the JSON `commands[]`. So it does **not** conflict with [contract](../../specs/help-dump-contract.md) §5, which forbids the **PRODUCER** parsing `-h` for tree discovery (a producer-side obligation). The forward contract and `schemas.ts` are **UNCHANGED**: this change was purely consume-side. Future readers should not mistake the consume-side display parse for a §5 violation.
- **No new dependency**: relies only on Astro/Starlight, the existing zod-via-`astro:content`, native `<details>`, plain-TS string parsing in `parse-help.ts`, and existing CSS (Constitution VI).

## Pull Mechanism (the scheduled refresh job)

shll.ai pulls help via `.github/workflows/scheduled-help-refresh.yml` — a scheduled refresh job, deliberately **OFF the deploy path**.

- **Triggers**: a **daily** `schedule` cron plus `workflow_dispatch` (for on-demand refreshes after a tool release).
- **Per-tool pipeline** (looped over all 7 tools): `brew install sahil87/tap/<slug>` → run `<tool> help-dump` capturing **stdout** → **stamp `captured_at`** (ISO-8601 UTC — the shll.ai-owned field the tool does not emit; see contract §3) → validate → commit. The file is named by slug (`help/<slug>.json`); the binary name lives in the `tool` field (`help/run-kit.json` holds binary `rk`, `help/fab-kit.json` holds `fab`).
- **Validation gate**: the job runs the existing `node scripts/validate-help.mjs` on the pinned pnpm 10 + Node 22 toolchain (reusing `deploy.yml`'s `pnpm/action-setup@v4` v10 + `actions/setup-node@v4` node 22 + `pnpm install --frozen-lockfile` pattern, cache keyed on the live site's lockfile).
- **Commit**: a **direct commit to `main`**, **gated on `validate-help.mjs` passing** in the same job — so a malformed capture never reaches `main` (never-commit-a-regression). It uses the default `GITHUB_TOKEN` with a minimal `contents: write` permission. **No PR, no auto-merge, no `SHLLAI_TOKEN`.** Direct commit is sound because the committer is a single trusted cron — which dissolves the PR-race and the three-guard hazard that a 7-external-pusher push model required. The accepted tradeoff is that help ships unreviewed (the binary's own `-h` is the authority, output is schema-validated pre-commit).
- **Per-tool capture-failure isolation**: a non-zero `help-dump` exit, an empty/garbage capture, a non-JSON capture, or a failed install for one tool MUST NOT clobber that tool's last-good committed `help/<slug>.json`, nor block the other tools. The job captures each tool into a temp file and only overwrites the committed file on a successful capture; a failing tool keeps its last-good copy and the others proceed. A **missing `help/tu.json`** is the expected interim state (`tu`'s `help-dump` is in progress — contract §7), not a failure. **Schema validity is enforced collectively, not per-tool**: the whole-directory `validate-help.mjs` gate (above) runs once over all files, so a tool emitting *valid-JSON-but-schema-invalid* output gates off the **whole** commit that run (every tool keeps last-good; the run self-heals next time). This is an accepted freshness-over-complexity tradeoff — safety (never-commit-a-regression) is preserved; a per-tool schema-validation path was rejected as unjustified complexity for a single-trusted-cron puller.
- **Off the deploy path (load-bearing)**: the refresh job does not deploy. When it commits to `main`, the **existing** `deploy.yml` push-to-`main` deploy ships the updated help — **no separate deploy trigger is added** (Constitution IV). A flaky brew tap or a broken tool release therefore breaks the REFRESH, not the deploy; the site keeps shipping last-good committed help. `deploy.yml` stays untouched and toolchain-free on the deploy path (Constitution I's spirit — no build-toolchain coupling on deploy).

## Design Decisions

- **Pull via a scheduled refresh job, OFF the deploy path (change `oa63`).** A `schedule` + `workflow_dispatch` workflow brew-installs the tools, runs `help-dump`, stamps `captured_at`, validates, and commits — kept off the deploy path so a flaky brew tap or broken tool release breaks the REFRESH, not the landing-page deploy (the site keeps shipping last-good help). *Rejected*: pulling at build time inside `deploy.yml` — couples the deploy to remote tool availability and a Go/Node toolchain on the deploy path; violates Constitution I's spirit and IV.
- **Direct commit to `main`, gated on `validate-help.mjs` (change `oa63`).** The committer is a single trusted cron, which dissolves the PR-race and the three-guard hazard that justified PR + auto-merge under push; gating on the existing validator preserves never-commit-a-regression. Accepted tradeoff: help ships unreviewed (the binary's own `-h` is the authority; output is schema-validated pre-commit). *Rejected*: PR + auto-merge — the entire apparatus existed only to serialize 7 external pushers and guard unattended-merge-to-prod; a single trusted cron needs none of it.
- **`captured_at` is shll.ai-owned (the §3 asymmetry).** Tool output excludes `captured_at`; the puller stamps it post-capture, because a tool's `help-dump` cannot know the capture time and `schemas.ts` requires it. Keeps the tool contract minimal (`{tool, version, schema_version, root}`). *Rejected*: making the tool emit `captured_at` — pushes a shll.ai-owned concern into 7 repos and is not knowable at emit time.
- **The spec owns the contract; this memory consumes it (change `oa63`, resolution (a)).** The schema/prose contract lives in `docs/specs/help-dump-contract.md`; this file is the consume/pull documentation and cross-links it. The schema is defined in one prose place (the spec) plus the `schemas.ts` code anchor — not two prose places that can drift. *Rejected*: keeping the full contract here AND adding a copy in the spec — guarantees prose-vs-prose drift.
- **Raw `text` + structured fields per node (not text-only).** Cobra hands `name`/`short`/`usage`/`path` for free; carrying them lets the site render a collapsible tree without re-parsing `text`. *Rejected*: text-only — would force first-line parsing for labels; brittle, loses framework-provided structure.
- **`help/` at repo root, not under `sites/`.** Project-level data that must survive a live-site swap (Constitution II + III). *Rejected*: per-site `src/content/help/` — ties the contract to one variant, breaks on swap.
- **Zod schema pinned inside the live Starlight site.** One machine-checkable definition that the validator and the loader both use — prevents prose-vs-code drift. Placed in the live site because Astro/Starlight already provides `z` via `astro:content` (no new dependency, no repo-root toolchain). *Rejected*: (a) prose-only schema — could diverge from the running validation; (b) Zod module at repo root — would require the first repo-root `package.json` and a zod dependency, contradicting Constitution II/VI.
- **Build-time `-h` parse is display-only, never structural (change `qemq`).** The `parseHelp` decomposition enriches how a node's captured `text` is *rendered* (flags table, badges, copy, filter, cross-tool index) but never derives the command tree — that stays sourced from JSON `commands[]`. This keeps the consume side compliant with contract §5 (which binds the *producer's* tree discovery, not site-side display parsing) and leaves the forward contract + `schemas.ts` untouched. The verbatim raw `text` remains the authority behind a "show raw" toggle, so a future Cobra-format change degrades to raw, not breakage (the unit test pins current behavior). *Rejected*: deriving any tree structure from parsed `-h` text (would cross into §5's producer obligation and duplicate the JSON tree).
- **Ascend-to-`help/` for the build-time read, not a fixed relative depth (change `js1s`).** The intuitive `../../../../help` (counted from the component source) breaks under `astro build`: Vite bundles the frontmatter into a chunk at a deeper, unstable path, so the fixed depth resolves to the wrong directory and the read silently ENOENTs — the page wrongly degrades to the placeholder. Ascending from `import.meta.url` until a `help/` directory is found is correct in both dev and build and is resilient to Astro's output layout. *Rejected*: fixed relative depth (wrong at build time); `process.cwd()` (varies by invocation, the spec forbade it); `import.meta.glob` (Vite's project-root `fs.allow` blocks files outside the site dir).
