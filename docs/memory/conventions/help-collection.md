# Help Collection

## Overview

Each of the 7 tools in the toolkit (`idea`, `hop`, `fab-kit`, `wt`, `run-kit`, `tu`, `shll`) emits its own `-h`/`--help` output as a structured JSON document. Those documents are collected at the **shll.ai repo root** under `help/<slug>.json` and become the single source for a generated command reference on the site.

The point is anti-drift: help text is **machine-generated by the binary**, so capturing it at build time means the site's command reference is as fresh as the last build *by construction* — there is no hand-maintained copy to rot. This is what makes a generated command reference safe where a hand-copied one would violate the [tool-page rubric](./tool-page-rubric.md).

This file is the authoritative contract. The 7 sibling tool repos build their producers against it; the consume-side `CommandReference` component (now implemented — see [Rendering Consumer](#rendering-consumer-commandreference)) reads the same `help/*.json` and validates against the same Zod schema.

> **Scope note.** This documents the *contract* — the schema, the collector, the push/receive flow — **and** the rendering consumer that closes the loop. The `CommandReference` component and the per-tool `commands` pages were the deferred follow-up (change `js1s`); they now exist and are described in [Rendering Consumer](#rendering-consumer-commandreference) below.

## Hand-written prose must not contradict `help/*.json` (the binding rule)

The `help/*.json` documents are the machine-generated source of truth for **command and flag names**, not just the input to the generated `CommandReference`. Any hand-written prose on the site (install snippets, "at a glance" examples, workflow recipes) **MUST NOT** reference a CLI command or flag that is absent from the relevant `help/<tool>.json`. The enforcement check is a grep-zero gate over `sites/<live-site>/src/content` for known-fabricated tokens, plus a per-command cross-check against the tool's help tree.

This was established by change `vn39`, which found the live site documenting commands/flags that never existed: `shll doctor`, `shll list`, `shll shell-install` (a legacy alias, not a real command — the canonical command is `shll shell-setup`), `wt create --from-idea`, `fab change new --from-idea`, `idea list --tag`, and `fab sync` (only `fab hook sync` exists). All were removed or replaced with verified equivalents. The canonical "install everything" sequence is single-sourced to the `shll` quick-start: `brew install sahil87/tap/shll` → `shll install` → `shll shell-setup --trust-tap` → `exec $SHELL`.

> **Known residual (out of `vn39` scope, follow-up).** A whole-tree sweep also flagged pre-existing unverified commands on lines `vn39` did not touch: `fab init` and `fab kit sync` (`tools/fab-kit/install.md` — absent from `help/fab-kit.json`), and `hop outbox …` / `hop status --all` (`hop/overview.mdx`, `workflows/daily-flow.md` — `outbox`/`status` absent from `help/hop.json`). `help/tu.json` does not exist yet, so `tu` command claims cannot be machine-verified. A future command-accuracy pass should reconcile these.

## The `help.json` Schema

A single JSON document per tool, an **envelope** wrapping a recursive **Node** tree.

```jsonc
{
  "tool": "wt",                            // invoked binary name (e.g. "rk", "fab") — not the file slug
  "version": "1.4.2",                      // from the built binary (ldflags / rootCmd.Version) — NOT hardcoded
  "captured_at": "2026-06-02T00:00:00Z",   // ISO-8601 UTC, stamped at capture
  "schema_version": 1,                     // integer; lets the contract evolve without a flag-day across 8 repos
  "root": {                                // recursive Node
    "name": "wt",                          // command name at this level
    "path": "wt",                          // full invocation path (e.g. "rk riff") — drives the tree label
    "short": "Git worktree management — …", // one-line description (Cobra Short)
    "usage": "wt [command]",               // usage line
    "text": "<raw -h output, byte-for-byte, newlines preserved>",
    "commands": [ /* Node[], recursive; empty array = leaf */ ]
  }
}
```

- `Node = { name, path, short, usage, text, commands: Node[] }`, recursive. A leaf command has `commands: []`.
- Every node carries both the raw `text` *and* the structured `short`/`usage`/`path`. The structured fields come free from Cobra and let the site render a collapsible tree and headers **without re-parsing the `text` blob**; `text` stays the authoritative, terminal-faithful raw output. The mild redundancy is accepted on purpose.

### Envelope field semantics

| Field | Rule |
|-------|------|
| `tool` | The invoked binary name (`wt`, `rk`, `fab`) — **not** necessarily the repo/file slug. |
| `version` | The version reported by the **built binary**. SHALL NOT be hardcoded by the producer. |
| `captured_at` | ISO-8601 UTC timestamp, stamped at capture time. |
| `schema_version` | The integer `1` for this contract revision. |

The **file** is named by the tool's repo/site slug, even where the binary differs: `help/run-kit.json` (binary `rk`), `help/fab-kit.json` (binary `fab`). The `tool` field inside carries the binary name.

## Zod Schema Module (the machine-checkable contract)

The schema is defined once in `sites/astro-starlight-terminal1/src/lib/schemas.ts` (the **live** site per `SITE_DIR` in `.github/workflows/deploy.yml`) and exported (`HelpDocSchema`, `NodeSchema`):

- It imports `z` from `astro:content` — Starlight provides zod **transitively**, so this contract adds **NO new dependency** and needs **NO repo-root Node toolchain**. The repo root holds only the `help/*.json` data files; there is **no repo-root `package.json`** (Constitution II, VI).
- The recursive `commands` field is expressed with `z.lazy` (a Node references itself).
- It is the **single** definition of the contract — both producers and the follow-up loader validate against it; there is no second, separately-maintained shape.

### Validating samples

`sites/astro-starlight-terminal1/scripts/validate-help.mjs` loads every `help/*.json` at the repo root and validates each against `HelpDocSchema`, exiting non-zero on failure. Run it via the live site's pnpm-installed toolchain:

```bash
cd sites/astro-starlight-terminal1
pnpm install --frozen-lockfile   # once
node scripts/validate-help.mjs
```

Because the schema module imports the `astro:content` virtual module (which only resolves inside an Astro build), the validator registers a tiny resolve hook (`scripts/astro-content-alias.mjs`) that aliases `astro:content` → `astro/zod` — the same `z` Astro re-exports — so the standalone validator imports the SAME schema module with no duplicated shape. The validator imports the `.ts` schema directly and relies on Node's native **type-stripping**, which is on by default (no flag) from **Node 22.18** onward (it existed behind `--experimental-strip-types` from 22.6). The site is pinned to Node 22 in both `deploy.yml` and the receiving workflow, which resolves to the latest 22.x — well past 22.18 — so this holds in CI.

## The `help/` Collector

`help/` is a top-level directory at the **repo root** (sibling to `sites/`, `fab/`, `docs/`), holding `help/<slug>.json` per tool. It is **not** nested under any `sites/<name>/`.

**Why the root.** The help data is project-level, not owned by any one site variant. Keeping it at the root means it **survives a live-site swap** (Constitution III — One Live Site at a Time): changing `SITE_DIR` to a different site under `sites/` does not require moving or duplicating the collector. This is the deliberate read of Constitution II (Multi-Site Isolation) — the data is shared, the *sites* are isolated.

### Cross-boundary read (by design)

The Zod module — and the `CommandReference.astro` component — live **inside** `sites/astro-starlight-terminal1/src/`, while the `help/*.json` data lives at the repo root. So the component reads from **outside** its site directory, up and out to `<repo-root>/help/`. This is the **intended** design, not a violation of site isolation: the data is project-level by deliberate placement, and only the *reading* site reaches into it. `<repo-root>/help/*.json` is an expected input, not an anomaly. The implemented read mechanism is detailed in [Rendering Consumer](#rendering-consumer-commandreference).

## Rendering Consumer (CommandReference)

The consume side — deferred as a follow-up by the original contract — now exists, implemented in change `js1s`. It is `sites/astro-starlight-terminal1/src/components/CommandReference.astro`, the **first importer** of `src/lib/schemas.ts` and the first reader of `help/*.json`.

- **Prop**: `tool` (the slug, e.g. `"wt"`). The component does the read + validate + render; page authors only pass the slug.
- **Placement**: rendered from each tool's `commands` page — `src/content/docs/tools/<tool>/commands.mdx` — which imports the component and renders `<CommandReference tool="<tool>" />`. All 7 tools have a `commands` page wired (idea/fab-kit's prior hand-written `commands.md` was removed in favor of the generated `.mdx`); the sidebar in `astro.config.mjs` lists a `Commands` entry for each. Today only `wt` has data (`help/wt.json`), so wt renders the real reference and the other 6 render the placeholder until their producer lands.
- **Build-time `fs` read (NOT glob, NOT fetch, NOT `process.cwd()`)**: the component reads the file with Node `fs` in its frontmatter (which runs during `astro build`), keeping the render static (Constitution I). The path is anchored on the module via `import.meta.url`.
  - **Resolution gotcha (load-bearing)**: a *fixed* relative depth (e.g. `../../../../help`) does **NOT** survive `astro build`. Vite bundles the component frontmatter into a chunk at an unstable depth (observed: `dist/.prerender/chunks/`), so the `..` count measured from the source file (`src/components/`) under-shoots at build time and the read silently ENOENTs — the page degrades to the placeholder even when data exists. The robust fix the component uses (`findRepoRoot`): **ascend from `import.meta.url`'s directory until a `help/` directory is found**, and read `<that-root>/help/<tool>.json`. This anchors on the module URL (not `process.cwd()`, which varies by invocation) yet is correct in both `astro dev` (source location) and `astro build` (bundled location), and survives changes to Astro's output layout. The ascent is a **bounded** loop (capped at a generous ancestor count); if no `help/` ancestor exists at all it throws a clear, build-failing error — that signals a broken cross-boundary contract, a distinct condition from the per-tool missing-file case below (which degrades to a placeholder, not a build failure). `import.meta.glob` is *not* usable here: Vite constrains it to the project-root `fs.allow`, which excludes files outside the site dir.
- **Validation**: `HelpDocSchema.parse()` from `src/lib/schemas.ts` — the same single contract shape, no second copy.
- **Missing vs. invalid (the two distinct failure modes)**:
  - **MISSING** (`ENOENT`, caught specifically): render a neutral placeholder ("Command reference not generated yet — see the GitHub README", linking to the tool's GitHub) and **let the build succeed**. A missing file is the expected interim state while producers land over weeks.
  - **PRESENT but schema-invalid** (or malformed JSON): the parse error propagates (wrapped with the offending filename) so **`astro build` fails** loudly and non-zero. A committed-but-malformed help file is a real defect that must not deploy. The two cases are never conflated — ENOENT is caught; everything else throws.
- **Render**: the recursive tree from `doc.root` — the root's raw `text` in a `<pre>`, then each `root.commands[]` recursively. Each node shows `path`, `short`, and raw `text` verbatim (whitespace/newlines preserved in `<pre>`). Nested `commands[]` nest visually; a leaf (`commands: []`) renders no children. Collapsibles use native `<details>`/`<summary>` (keyboard + screen-reader semantics for free, zero JS). Styling reuses the terminal `--c-*` tokens so dark-mode parity follows Starlight's `data-theme` flip with no per-component script.
- **No new dependency**: relies only on Astro/Starlight, the existing zod-via-`astro:content`, native `<details>`, and existing CSS.

## Producer Rules (the 7 tool repos)

Every producer follows these rules (the 7 are seeded as `fab/backlog.md` items in their own repos and built by their own pipelines):

1. **Discover the tree programmatically** via the CLI framework — Cobra: walk `rootCmd.Commands()` recursively. **Never** regex-parse `-h` text to discover structure.
2. **Filter noise**: drop Cobra's auto-generated `completion` and `help` subcommands and any `cmd.Hidden == true` node.
3. **Version from the binary**: read `version` from the built binary (ldflags / `rootCmd.Version`); never hardcode it. (The committed `wt.json` sample uses a placeholder `1.4.2` because a plain `go build` reports `dev`; real producers inject the true version.)
4. **Full recursion**: capture the top-level command and **all** subcommands, to any depth (matches the `rk riff -h` motivating case).
5. **`tu` is the documented exception**: it is Node/TS and flag-based with no subcommands → a flat tree with `root.commands: []`, captured by a bespoke producer that puts the full `tu --help` output in `root.text`. (6 tools are Cobra/Go; only `tu` is Node.)

Producers are **per-repo and framework-native** — there is **no shared library**. A Cobra tree-walk is ~40 frozen lines; copy-paste across 6 Go repos is cheaper than a versioned shared module (which would need `go get` coordination across repos split on different Cobra versions), and `tu` is Node and would not share Go code anyway.

## Push & Receive Flow

### Producers push via PR + auto-merge

Each tool's CI, **after build**, runs its producer, writes `help/<slug>.json`, validates that the JSON parses, then **opens a pull request into `sahil87/shll.ai` with auto-merge enabled** — **NOT a direct push to `main`**.

- **Auth**: the existing **`SHLLAI_TOKEN`** repo secret (already present in all 7 repos), scoped to `contents` + `pull-request` write on shll.ai.
- **Why PR, not push**: a direct push from 7 repos **races on `main`** — near-simultaneous CI runs produce non-fast-forward rejections / clobbers. PR + auto-merge **serializes** merges and yields a reviewable `help.json` diff for free. The cost is one small workflow in shll.ai (see below).

### Receiving side (this repo)

`.github/workflows/help-automerge.yml` triggers on `pull_request` events with a `paths: ['help/**']` filter. **The path filter controls only whether the workflow *triggers* — it does NOT decide merge eligibility.** That distinction matters because this repo is **public**, `main` is **unprotected**, and a merge to `main` **auto-deploys** (`deploy.yml`). A single PR can touch `help/**` *and* other paths in the same diff (a "mixed" diff), which still trips the trigger. So enabling auto-merge on every triggered PR would let a mixed diff — or a schema-invalid help file — auto-merge and ship to production unattended.

What actually makes unattended merge safe are **three guards**, all of which must pass before the workflow enables auto-merge (`gh pr merge --auto`):

1. **Content guard (MUST)** — enumerate the PR's changed files (`gh pr view --json files`); if **any** file is outside `help/`, the workflow does **not** enable auto-merge. It exits 0 (a no-op, not a failure) so the mixed PR stays **open for manual review**.
2. **Schema validation gate (MUST)** — check out the PR head and run the contract validator (`scripts/validate-help.mjs`) against the proposed `help/*.json` on the site's pinned toolchain (pnpm 10 + Node 22, reusing `deploy.yml`'s setup). If any file fails schema conformance the step **fails**, so the workflow never reaches the enable-auto-merge step (and the failed check guards a manual merge too).
3. **Actor guard (SHOULD, defense-in-depth)** — the PR author must equal the trusted producer identity (`TRUSTED_AUTHOR: sahil87`, the `SHLLAI_TOKEN` owner), parameterized as a workflow `env` constant. Fork PRs already receive a read-only token and cannot self-enable auto-merge; this rejects stray/other-author PRs early.

The workflow uses `pull_request` (NOT `pull_request_target`), so fork PRs run with a read-only token and never execute privileged logic against untrusted head code. It is **inert** until producers begin opening PRs — its presence does not break the existing deploy or require all 7 producers to exist.

No separate deploy trigger is added: under Constitution IV, merging the help PR to `main` already fires the existing `deploy.yml` push-to-`main` deploy, which ships the updated help.

## Design Decisions

- **Raw `text` + structured fields per node (not text-only).** Cobra hands `name`/`short`/`usage`/`path` for free; carrying them lets the site render a collapsible tree without re-parsing `text`. *Rejected*: text-only — would force first-line parsing for labels; brittle, loses framework-provided structure.
- **`help/` at repo root, not under `sites/`.** Project-level data that must survive a live-site swap (Constitution II + III). *Rejected*: per-site `src/content/help/` — ties the contract to one variant, breaks on swap.
- **Zod schema pinned now, inside the live Starlight site; render later.** One machine-checkable definition that producers validate against AND the follow-up loader imports — prevents prose-vs-code drift. Placed in the live site because Astro/Starlight already provides `z` via `astro:content` (no new dependency, no repo-root toolchain). *Rejected*: (a) prose-only-now / Zod-with-loader — loader schema could diverge from what producers were told; (b) Zod module at repo root — would require the first repo-root `package.json` and a zod dependency, contradicting Constitution II/VI.
- **Producers push via PR + auto-merge (not direct push, not site-pulls-at-build).** Direct push races on `main`; fetch-at-build would couple the deploy to remote availability and need a Go/Node toolchain in shll.ai CI. PR + auto-merge serializes, stays reviewable, and reuses the existing `SHLLAI_TOKEN`. *Rejected*: direct push (race, no review); fetch-at-build (couples deploy to remote + toolchains).
- **Receiving workflow enables auto-merge only; reuse the existing deploy.** Constitution IV already deploys on push to `main`. *Rejected*: a dedicated deploy-on-merge workflow — redundant with the existing push-to-`main` deploy.
- **Auto-merge is gated by content + validation + actor guards, not just the path trigger.** On a public repo with unprotected, auto-deploying `main`, a `paths: ['help/**']` filter only controls *triggering* — a mixed diff (help/** plus other paths) still trips it, and an unconditional `gh pr merge --auto` would ship that, or a schema-invalid help file, unattended. So auto-merge is enabled only when (1) every changed file is under `help/`, (2) the help JSON passes the Zod validator, and (3) the author is the trusted producer. *Rejected*: relying on the path filter alone — it does not constrain *what else* a triggering PR changes, nor whether the help payload is valid.
- **Per-repo, framework-native producers — no shared library.** A Cobra tree-walk is ~40 frozen lines; copy-paste beats a versioned shared module needing cross-repo `go get` coordination. `tu` is Node and wouldn't share Go code anyway.
- **Ascend-to-`help/` for the build-time read, not a fixed relative depth (change `js1s`).** The intuitive `../../../../help` (counted from the component source) breaks under `astro build`: Vite bundles the frontmatter into a chunk at a deeper, unstable path, so the fixed depth resolves to the wrong directory and the read silently ENOENTs — the page wrongly degrades to the placeholder. Ascending from `import.meta.url` until a `help/` directory is found is correct in both dev and build and is resilient to Astro's output layout. *Rejected*: fixed relative depth (wrong at build time); `process.cwd()` (varies by invocation, the spec forbade it); `import.meta.glob` (Vite's project-root `fs.allow` blocks files outside the site dir).
