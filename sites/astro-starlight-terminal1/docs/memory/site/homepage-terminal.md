# Homepage Interactive Terminal

## Overview

The homepage hero (`src/content/docs/index.mdx`) is a terminal transcript that **looks** interactive. Change `9vbo` makes the final prompt line **actually typeable** — keystrokes echo, Enter runs a command against a static in-page map, output prints in the same styled stream — layered as a **progressive enhancement** so nothing regresses without JS. The terminal SKIN (JetBrains Mono, phosphor-amber `--c-*` palette, `.shell-*` classes) shipped earlier in `260517-pdsp-terminal-skin`; this change adds behavior on top of that skin (reusing its classes verbatim) plus **one** deliberate visual addition — a `.terminal-window` frame around the transcript. Change `n23o` layers real shell affordances onto input handling (§ Shell affordances); change `23xc` makes the interactivity **discoverable above the fold** (§ Above-the-fold activation pass); change `by18` makes it **usable on touch devices** (§ Touch support); change `cuur` polishes the **command experience** (did-you-mean, `help <command>`, a cancellable navigation beat) and makes its **output accessible** (live-region announcements, reduced-motion gate) (§ Command polish & accessible output); change `o33t` lands the **delight pass** the backlog sequenced last — 33 new unlisted GNU-utils easter eggs (stateless one-shots, light logic, three animated streams) on new streamer + live-region-noise infrastructure (§ GNU-utils delight pass); change `cdbr` adds the **sanctioned full-roster reveal** — the `cheatsheet` command mapping all 52 keys in five groups behind a runtime anti-drift coverage check, pointed to by the one sanctioned help-footer change (§ The full-roster cheatsheet); ## The progressive-enhancement boundary (load-bearing)

The static `<pre class="shell-session">` transcript in `index.mdx` is the **no-JS source of truth** — crawlers, no-JS, and pre-hydration paint see the full hand-written transcript verbatim, including the version-block `<a>` links and the final blinking `$ ▊` line. Nothing regresses without JS.

`src/components/TerminalPrompt.astro` is a **client island** following the `Diagram.astro` precedent (frontmatter comment + a single `<script>` module island). With JS on, it:

1. Locates the final prompt line via the **`data-terminal-prompt`** attribute (a marker on the last `.shell-line` in `index.mdx`), not positional assumptions — keeping the static markup authoritative.
2. **Removes** that static `$ ▊` line, prints the greeting line (change `23xc`, § Above-the-fold activation pass), and emits the first live prompt in its place: a `.shell-line` containing a `.shell-prompt` `$` and a focusable `<span class="shell-input" contenteditable="true">` input region — `contenteditable="true"` plus an explicit plain-text paste handler, NOT `plaintext-only` (inconsistently supported; see § Accessibility).
3. On **Enter** (since `by18` via the shared `commitLine(true)` helper — § Touch support): trims the line, freezes the just-entered input into static echoed text (strips `contenteditable`/`role`/aria/listener/`.shell-input`), dispatches the command, appends output spans to the **same** `<pre>` stream, and emits a fresh prompt.

**No autofocus on page load (deliberate).** `freshPrompt(focus = true)` defaults to focusing, but the initial activation calls `freshPrompt(false)` — auto-focusing on load would steal focus and scroll the hero out of view (disruptive for keyboard/SR users). Focus moves to the prompt only **after** the user runs a command (Enter / `clear`). This was a Should-fix finding addressed in the review stage.

### `theme` syncs with Starlight (does not reinvent persistence)

`setTheme` locates the header `starlight-theme-select select`, sets `select.value` to the target, and dispatches a bubbling `change` event — so the header toggle UI, `<html data-theme>`, and `localStorage` all update through Starlight's own `onThemeChange`. It MUST NOT flip `data-theme` directly nor reinvent persistence. No-arg toggles the effective theme (read from `document.documentElement.dataset.theme`); `dark`/`light` sets it; any other arg prints `usage: theme [dark|light]`. A direct `data-theme` flip exists only as a fallback if the header select is absent.

The `onKeydown` branch order is: Ctrl-combos → ↑/↓ → Tab → Enter → native fall-through. (Since `by18` the Enter branch is just `e.preventDefault(); commitLine(true);` — the commit sequence itself lives in the shared `commitLine` helper, § Touch support. Since `kd5e` a **game-mode branch sits above all of these** — after the `dismissIdleHint()`/`stopReplay()` first statements, before every branch listed — owning the keys while a `snake` game is active: § The terminal toys.)

**The exactly-one-trailing-prompt invariant (load-bearing).** The most fragile part of this change. Ctrl-L and Ctrl-C are prompt-emitting paths **outside** the commit flow (`commitLine` — Enter and, since `by18`, command-bar chips), so each must emit exactly one trailing prompt itself — never two, never zero. The Tab multiple-match listing deliberately does NOT commit/freeze the line (so it adds no prompt-emitting path at all).

### Command history (↑ / ↓ recall)

- **State at `initTerminal` scope** (one history per terminal instance, NOT inside `freshPrompt` which runs per prompt): `history: string[]` of committed, non-empty, trimmed **raw** lines + a `historyCursor` ranging `[0, history.length]`, where `length` is the "blank draft" slot past the newest entry. ↑ (`navigateHistory(-1)`) walks toward 0; ↓ (`navigateHistory(1)`) walks toward `length`, where it restores a **blank** line (drafting a new command), not the newest entry. Caret to end via `caretToEnd()`. Because the prompt is enforced single-line (paste flattened, `aria-multiline=false`), ↑/↓ drive history unconditionally rather than caret movement.
- **`ignoredups`** (bash behavior): on Enter commit a line is pushed only if it differs from the immediately previous entry; the cursor then resets to `history.length`. Ctrl-C also resets the cursor to the blank-draft slot (so the next ↑ starts from the newest entry).
- **sessionStorage persistence** under the named key `shll:terminal:history` (deliberately NOT `localStorage` — a refresh keeps recent commands, but a new browser session starts clean). Read once at init via `loadHistory()`, written on each commit via `saveHistory()`. **All** access is try/catch-guarded: private-mode / disabled-storage / quota degrades silently to in-memory-only and never throws, and a malformed / non-array payload coerces to `[]` (the parsed array is also filtered to strings).

### Tab-completion (bash-like)

`completeInput()` completes the token under edit. First token → `COMMANDS` keys; second token → `TOOLS` when the first token is a tool-arg command (`cd` / `open` / `man` — and `play`, since change `jf9k` — the `TOOL_ARG_COMMANDS` list). Resolution over the candidates matching the typed fragment:

- **single match** → fill it (`fillToken` rejoins the line, preserving any `cd `/`open `/`man ` prefix), caret to end.
- **longest common prefix > typed** → fill the shared prefix (partial completion), no listing.
- **multiple matches, no LCP gain** → `printBeforePrompt({ text: matches.join('  '), classes: 'shell-out' })` lists the candidates ABOVE the still-live input — WITHOUT freezing the line or emitting a new prompt (input text + caret untouched). It uses `printBeforePrompt` (insert before the live prompt line), NOT `print` (append to end of `session`): `print` would drop the listing BELOW the live prompt — the prompt would no longer be the trailing line. This is the chosen path (over freeze→reseed) precisely because it adds no prompt-emitting path, keeping the one-trailing-prompt invariant trivially intact.
- **no match** → no-op (input unchanged, nothing printed).

### Control keys (Ctrl-L, Ctrl-C)

Detected only on an unmodified Ctrl combo (`e.ctrlKey && !shift && !alt && !meta`) so e.g. Ctrl-Shift-C copy is left to the browser; other Ctrl combos fall through to native handling.

- **Ctrl-L** → `preventDefault()` (Ctrl-L otherwise focuses the address bar), reuse `clear()` (which deliberately does NOT emit a prompt itself), then exactly one `freshPrompt()`.
- **Ctrl-C** → `preventDefault()`, `freezeInput('^C')` (freeze the live line with a trailing `^C` like a real shell aborting a line), discard the typed input (do **not** run it), reset `historyCursor`, then one `freshPrompt()`. Empty input still freezes `$ ^C` + one prompt.

### `freezeInput(suffix?)` helper

The Enter-branch line tear-down (live input → static echoed text: strip `contenteditable`/`role`/`aria-multiline`/listeners/`shell-input` class, drop the block cursor) was **extracted** from the inline Enter logic into a shared `freezeInput(suffix = '')` helper, reused by both Enter (commit, no suffix) and Ctrl-C (cancel, `'^C'` suffix) so the freeze semantics can never drift between them. The optional `suffix` is appended to the echoed text.

(Pre-existing observation surfaced during `by18`, out of scope and harmless: `freezeInput` has always left the `data-terminal-prompt` attribute on the frozen line — since `9vbo`, because `freshPrompt` sets it on every live line. The one-trailing-prompt invariant is properly characterized by the **single contenteditable input** being the session's last line; every live-prompt lookup goes through `input.closest('[data-terminal-prompt]')`, never a bare attribute query, so stale attributes on frozen lines are never matched.)

## Above-the-fold activation pass (change `23xc`)

On a common ~1280×750 laptop viewport the live prompt sat **below the fold** (baseline measurement: Starlight's splash hero `padding-block` resolved to ~91px each side; the live prompt landed at y≈876 against a 750px fold) — the terminal, the site's signature interaction, read as a decorative screenshot. Change `23xc` makes the interactivity discoverable with three combined levers, all activation-time, zero new dependencies, `index.mdx` byte-identical. It explicitly sequences **before** the queued polish items `[by18]` (touch), `[cuur]` (command UX + a11y), `[o33t]` (delight) — they polish a surface visitors must first be able to see.

### Hero rhythm tightening (CSS-only, splash-scoped)

`terminal.css` overrides scoped via **`[data-has-hero]`** — Starlight's own splash-page attribute on `<html>`, present on hero pages only — so doc pages render with unchanged spacing, and the extra attribute outranks Starlight's `:where()`-scoped component rules without `!important`. Values: `.hero` `padding-block: 3rem 1.5rem`, `.hero .stack` `gap: 1.5rem`, `.terminal-window` `margin-top: 0.75rem` (tuned by in-browser measurement at 1280×750). The base `.terminal-window`/`.shell-session` margin rules still apply on non-hero pages — they are not shadowed.

### Resting-state top anchor (scroll geometry, not content)

Until the first prompt-emitting interaction the session viewport is **top-anchored**: the greeting line is the first visible line, the live `$` prompt sits directly below it, and the boot transcript stays in the DOM above, reachable by scrolling up — exactly like a real terminal after `clear`.

- `anchorToGreeting(greetingEl)` computes the greeting's offset within the scrollable session (bounding-rect delta + `scrollTop` − the session's top padding) and assigns `session.scrollTop` directly — instant, no smooth scrolling (trivially motion-safe). A `scrollTop`-only approach is **mathematically insufficient**: the content below the greeting (~2 lines) is far shorter than the ~325px viewport, so max scroll (≈108px) cannot reach the greeting's offset (≈400px). The function therefore extends the session's **inline `padding-bottom`** by exactly the deficit — the blank rows a real terminal shows after `clear`. This is scroll geometry, not content: the live prompt remains the session's **last DOM child**, so the exactly-one-trailing-prompt invariant is untouched.
- **Re-anchored once after `document.fonts.ready`** (JetBrains Mono loads async and shifts line metrics), guarded on still-`resting` AND the user not having scrolled away from the anchored position (`|scrollTop − anchoredScrollTop| < 2`) — never yanking a user-initiated scroll.
- **`exitResting()`** — called from every prompt-emitting path: `commitLine` (Enter and, since `by18`, command-bar chip taps) plus the Ctrl-L and Ctrl-C branches of `onKeydown` — flips the `resting` flag and clears the inline filler; the original bottom-pinned behavior (`scrollToBottom` after `print`/`freshPrompt`) resumes unchanged for the rest of the session.
- **No-JS**: the static transcript renders at browser-default `scrollTop = 0` exactly as before — the anchor is island-only.

### Activation-time greeting line

Printed by the island at activation — after `promptLine.remove()`, before `freshPrompt(false)` — one dim line (classes `shell-out shell-dim`, named `GREETING` constant):

```
seven small CLIs that force agents to plan first. type 'help' or 'ls'.
```

The copy deliberately omits the literal "shll" / the verbatim hero tagline — the tagline renders directly above the terminal in the tightened hero, and the shorter copy keeps the tail invitation (`type 'help' or 'ls'.`) visible under the session's `white-space: pre` on narrower laptops. Island-printed only: the static no-JS transcript stays byte-identical (the progressive-enhancement source of truth).

### Idle ghost hint (one-shot, visual-only)

A one-shot timer (`HINT_DELAY_MS = 4000`) armed at activation. After 4 s without interaction, `showIdleHint()` appends a **visual-only** `aria-hidden="true"` span (class `shell-ghost`, copy `HINT_TEXT`) to the live prompt line **after** the block cursor, fish-autosuggestion style: `$ ▊try 'ls' ⏎`.

- It is never inside the contenteditable input — never part of the textbox's accessible name/value, can never be submitted by Enter, and **never focuses the input** (the deliberate `9vbo` no-autofocus decision stands — the hint draws the eye, it does not steal focus).
- Types in character-by-character via `setInterval` (`HINT_TYPE_MS = 70`) editing the span's `textContent` in place — deliberately NOT `print()`/`scrollToBottom()`, so the typing never moves the scroll position. Under `prefers-reduced-motion: reduce` (checked via `window.matchMedia`) the full text appears statically — no typing interval, still dim, still dismissable.
- `dismissIdleHint()` is a one-shot latch (`hintSpent`): interaction **before** the timer fires cancels it; **after**, it removes the span and clears a mid-animation interval; either way the hint never returns this page view (no re-arm, no storage — it returns on the next page load until the visitor interacts). Wired as the **first statement of `onKeydown`** (before branch dispatch, so Tab as the very first keystroke dismisses the ghost before completion logic runs), into `onFocus`, and at the top of the terminal-surface `onClick` before its link/selection early-returns (a link click or in-progress text selection still counts as interaction).
- Skin: `.shell-ghost` is `color: var(--c-fg-faint)` + `user-select: none` — both themes for free via the shared variable.

### Pre-existing autofocus bug fixed

Baseline measurement found `document.activeElement` was the live input **on page load**: `freshPrompt`'s unconditional `caretToEnd()` placed a selection range inside the contenteditable, which gives it focus in Chromium — silently violating the documented `9vbo` no-autofocus decision. `caretToEnd()` is now **gated to the focusing path** (`focus = true`); the click-to-focus and Tab paths re-place the caret themselves. The implementation now matches the documented invariant (typing before clicking/tabbing no longer reaches the input — the documented intended behavior).

## Touch support (change `by18`)

Before `by18` the terminal was keyboard/click only — on phones the interaction `23xc` made visible above the fold didn't work (the idle hint taunts `try 'ls' ⏎` at users who can't type it). Change `by18` adds two complementary levers — tap-to-focus hardening and an on-screen command bar — both island-only, zero new dependencies, `index.mdx` byte-identical.

### Tap-to-focus rides the synthesized click (no parallel touch path)

Browsers synthesize a `click` after a tap on non-interactive elements, and `focus()` inside that handler is gesture-qualified — it summons the soft keyboard on iOS Safari / Android Chrome. So tap-to-focus reuses the **existing `onClick` surface handler**, hardened with **`touch-action: manipulation` on `.terminal-window`** (`terminal.css`): drops the double-tap-to-zoom heuristics that can delay or swallow the synthesized click, and prevents accidental zoom on rapid chip taps — pan/scroll gestures unaffected, no behavior change for mouse users. A `touchend` fallback was **deliberately NOT built**: the intake mandated verify-first, not speculative code, and Chromium touch-emulation verification passed 40/40 Playwright checks (tap focuses the input via `activeElement`, link taps still navigate, chips dispatch, media-query visibility, keyboard operation, idle-hint/resting interplay). The existing bails (links, active text selection) keep working under touch; a third bail was added for the command bar (below).

### Shared commit path: `commitLine(focusNext)`

The Enter-branch commit sequence in `onKeydown` — `exitResting()` → read+trim the raw line → `freezeInput()` → empty-line short-circuit (fresh prompt only) → `ignoredups` history push + `saveHistory()` → `historyCursor` reset → `run(raw)` → exactly one `freshPrompt(focusNext)` — was **extracted** into a shared `commitLine(focusNext: boolean)` helper (same extraction precedent as `freezeInput(suffix?)` in `n23o`). Enter calls `commitLine(true)` (focus follows command execution — the desired keyboard behavior); the chip path calls `commitLine(false)`. Every committed line — typed or tapped — flows through one sequence, so commit semantics can never drift and the exactly-one-trailing-prompt invariant holds **by construction** on the chip path.

### On-screen command bar (touch-primary devices only)

`injectCommandBar()` runs at activation (after the click-surface wiring) and appends a `.terminal-cmdbar` (`role="group"`, `aria-label="quick commands"`) as the **last child of `.terminal-window`** — below the `pre.shell-session` scroll viewport, reading as a keyboard-accessory row on the terminal's bottom edge, adjacent to where the OS keyboard rises. It holds four native `<button type="button">` chips whose `data-cmd` comes from the module-scope **`CHIP_COMMANDS`** roster (`ls`, `help`, `version`, `install` — `install` included because it is the site's primary CTA; the chip dispatches the existing command's **real** `/getting-started/install/` navigation). One **delegated** `click` listener on the bar (`onChipClick` resolves `closest('button.terminal-chip')`), not four per-button listeners.

- **Island-injected, never static markup** — with JS off the chips would be dead buttons, violating the progressive-enhancement boundary (greeting-line precedent, `23xc`); `index.mdx` stays byte-identical. If the `.terminal-window` wrapper is absent the bar is **skipped gracefully** (no throw; tap-to-focus unaffected — chips appended inside the `pre` would corrupt the transcript stream).
- **Living OUTSIDE `pre.shell-session`**, the bar leaves the resting-state top anchor, the `scrollToBottom` geometry, and the live-prompt-last-DOM-child invariant untouched.
- **A chip tap = full interaction semantics**: `dismissIdleHint()` (a one-shot latch, so the surface handler's own dismissal can never double-fire) → set the input text to `data-cmd` → `commitLine(false)`. Chip-run commands enter the same `history[]` (↑/↓ recall and the `history` command see them; `ignoredups` + sessionStorage apply identically).
- **The chip path does NOT focus the input** (`focusNext = false` — load-bearing): focusing would summon the soft keyboard over the output the user just asked for; a chip user is in touch mode, and the keyboard appears only when they tap the prompt itself. To keep that true against event bubbling, the window-surface `onClick` gained a `.terminal-cmdbar` **early-return bail** (placed after `dismissIdleHint()`, mirroring the existing link bail) so the bubbled chip click never reaches the focus affordance.
- **Visibility is CSS-only**: `.terminal-cmdbar { display: none }` by default, revealed as a wrapping flex row only under `@media (hover: none) and (pointer: coarse)` — the touch-primary signal. The bar shows on phones/tablets at any width and **never on desktop** (narrow desktop windows keep the full keyboard affordances; "not appear on desktop" was chosen over "render but redundant").
- **Skin via `--c-*` only** (Constitution V, both themes for free): `var(--c-surface)` bar with a `1px solid var(--c-border)` top border (the titlebar's chrome language); transparent bordered chips with `var(--c-fg)` text, `font: inherit` (buttons don't inherit the mono font) and `cursor: pointer` (overriding the surface's `cursor: text`); `:active` → `var(--c-surface-2)`; visible `:focus-visible` outline in `var(--c-accent)`. No animation — nothing new to gate behind `prefers-reduced-motion`.

## Command polish & accessible output (change `cuur`)

After `23xc`/`by18` made the terminal discoverable and reachable, the command experience itself still had rough edges (a typo dead-ended; `help` was all-or-nothing; `cd` yanked you off the page on the same tick as Enter) and everything `print()` appended was **silent for screen-reader users** — a WCAG 4.1.3-shaped failure on the site's signature feature. Change `cuur` is the core-polish pass the backlog sequences before `[o33t]` (delight): five small, additive levers in the island + one stylesheet block + one new lib module, zero new dependencies, `index.mdx` byte-identical.

### Did-you-mean suggester (`src/lib/terminal-suggest.ts`)

A new **dependency-free** module exporting `damerauLevenshtein(a, b): number` and `suggestCommand(input, candidates): string | null`. Extracted to `src/lib/` (NOT inlined in the island) so it is unit-testable under the existing `node --test scripts/*.test.mjs` pattern; Vite bundles it into the client island.

- **Algorithm**: Damerau-Levenshtein in its **optimal-string-alignment** form — an ADJACENT TRANSPOSITION counts as 1 edit, so the classic fat-finger typo class (`hlep`→`help`, `verison`→`version`) scores 1 where plain Levenshtein would score 2 (and would miss them at the short-input threshold). Full (m+1)×(n+1) matrix — inputs are command tokens, so it's cheap.
- **Threshold**: max distance **1 when `input.length <= 3`, else 2** — the short-input clamp stops absurd matches like `vi`→`cd` (distance 2 on a 2-char token is a different word, not a typo). Input is lowercased before matching.
- **Tie-break**: lowest distance wins; on equal distance, the EARLIER candidate in iteration order wins (a strict `<` comparison — a later candidate only displaces a strictly closer one). No candidate within threshold → `null`.
- **Candidates at both call sites**: `Object.keys(COMMANDS)` — hidden eggs INCLUDED (a near-miss egg like `forune`→`fortune` rewards the curiosity the `help` footer invites; the list itself still never reveals them). Single source of truth for "what is a command".
- **Wiring in `run()`'s not-found branch**: a suggestion replaces the `type 'help'` tail on the same line (`command not found: instal — did you mean 'install'?`); `null` keeps the existing line unchanged.
- **Unit-tested**: `scripts/terminal-suggest.test.mjs` (`node --test`, native TS type-stripping import of the `.ts` module — same pattern as `extract-readme.test.mjs`), 11 tests pinning the contract: transposition=1, classic Levenshtein cases, the acceptance pair `instal`→`install`, an egg candidate (`forune`→`fortune`), the short-input clamp (`vi`→`null`, `lss`→`ls`), distance 2 for >3-char inputs, no-match→`null`, both tie-break directions, lower-distance-beats-order, and lowercasing.

### `help <command>` — argument-aware help

A module-scope `HELP_DETAIL: Record<string, Line[]>` (built by a `helpDetail(usage, detail)` factory beside `SYNOPSIS`) carries per-command detail in the man-page shape: one usage line (`shell-out`) + one dim elaboration line (`shell-out shell-dim`), both indented. **EVERY key in `COMMANDS` has an entry — listed commands AND hidden eggs**: `help sudo` answers once you've found `sudo`, but the bare list never enumerates the eggs (answering a direct question is not advertising — the discovery ethos stands).

- **Dispatch**: bare `help` prints the existing short list UNCHANGED (detail lives behind the argument, so the list stays scannable); `help <arg>` resolves via `helpFor(arg.toLowerCase())`.
- **`helpFor` resolution order** (deliberate): `HELP_DETAIL` lookup first — so `shll` (both a command and a tool) lands on its command entry, never the tool branch — then the tool check, then the suggester.
- **Tool name** (in `TOOLS`, no command entry): points sideways — `help: no help for 'hop' — try 'man hop'` (tools are documented by `man`, not `help`).
- **Unknown arg**: `help: no help for 'xyz'` + the same suggester tail as the not-found branch when a candidate exists (`— did you mean '…'?`) — one matcher, two call sites, no second fuzzy-match implementation to drift.

### Intentional navigation beat (`navigateWithBeat`)

`cd`/`open`/`install` previously called `window.location.assign` synchronously on Enter — instant navigation off a playful exploration surface read as a misclick, yanking the visitor away before the `opening …` line even registered. One shared helper `navigateWithBeat(route, lines)` now serves all three:

1. Prints the context lines first — `cd`/`open` prepend the tool's `SYNOPSIS` line ("context before motion"); `install` keeps its single line — then `opening <a href>{route}</a> … (Ctrl-C to cancel)` as a **real clickable anchor** (`html: true`, the same trusted-static-string pattern as `man`/`ls`; classes `shell-out shell-dim`, today's `opening` skin).
2. Schedules `window.location.assign(route)` via `window.setTimeout` with **`NAV_BEAT_MS = 900`** (a named constant beside `HINT_DELAY_MS`).
3. **Ctrl-C cancels**: the pending timer id (`pendingNav`) lives at `initTerminal` scope; the existing Ctrl-C branch in `onKeydown` clears it before `freezeInput('^C')` — `^C` + a fresh prompt then read exactly like aborting a command in a real shell, and you stay on the page. This is what makes the beat *intentional* rather than laggy.
4. The clickable anchor is the impatient path (click through immediately); chip taps (`install` chip, `by18`) flow through `commitLine → run → navigateWithBeat` and inherit the beat + tappable link (touch users have no Ctrl-C but gain the anchor).
5. **`pendingNav` is deliberately NOT cleared by `commitLine`** — a new command committed during the beat lets the scheduled navigation fire (accepted + documented in a code comment: the beat is short and the printed line already said where it's headed). Known deferred nice-to-have: a nav-during-beat does not clear the *previous* nav's timer either (a second `cd` within 900 ms briefly holds two timers — harmless in practice since the first navigation unloads the page; `o33t` shipped without this tightening, so it remains open).
6. The beat is a pure `setTimeout` — **timing, not animation** — so there is no `prefers-reduced-motion` interaction.
7. Empty/invalid `cd`/`open` args short-circuit with usage / `no such tool` BEFORE the helper — no timer is ever scheduled.

### `aria-live` output announcements

At activation — island-only; the no-JS static transcript is inert and needs nothing — the island sets **`aria-live="polite"` + `aria-atomic="false"` on `pre.shell-session`**, BEFORE the greeting prints (so the greeting announces once on load — the right SR introduction to an interactive region). Everything appended by `print()`/`printBeforePrompt()` is thereafter announced after the user's keystroke settles; `atomic=false` announces only the appended nodes, never re-reads the whole transcript.

- **Noise control**: `freshPrompt()` marks each new prompt's `$` span (`.shell-prompt`) **`aria-hidden="true"`** — every fresh prompt line is an appended node, so an exposed `$` would be announced after every command. The input's existing `aria-label` already carries the prompt semantics; the block cursor span was aria-hidden already.
- **What stays silent, by construction**: the aria-hidden idle ghost hint (hidden additions aren't announced); `clear`/Ctrl-L (`replaceChildren` removals aren't announced). The Ctrl-C `^C` suffix IS a text addition — announcing it is correct cancel feedback.
- **Known accepted trade-off**: screen readers may announce typed characters twice (once as typing echo, once if the frozen echo line registers as an addition). A parallel visually-hidden mirror region was **rejected at intake** (duplicate DOM, drift risk; user-confirmed, intake assumption #6) — the session `pre` itself is the live region.

### Reduced-motion CSS gate

The `cuur` intake audited every motion source; exactly **two unconditional animations** existed, both CSS (`terminal.css` previously had NO `prefers-reduced-motion` block at all):

| Motion source | Where | Status |
|---|---|---|
| `shell-blink` cursor blink (static skin + live `.shell-input-cursor.is-active`) | `terminal.css` | **Fixed by `cuur`** — was unconditional |
| `terminal-blink` doc-page first-paragraph `▊` cursor | `terminal.css` | **Fixed by `cuur`** — was unconditional |
| Idle ghost hint typing (`23xc`) | island JS | Already safe — static text under `reduce` |
| Resting anchor / `scrollToBottom` | island JS | Already safe — instant assignment, no smooth scrolling |
| Hover/focus/`:active` color changes; nav beat | CSS / `setTimeout` | Not motion |

The fix is **one `@media (prefers-reduced-motion: reduce)` block** in `terminal.css`: `animation: none` for `.shell-session .shell-cursor` + `.sl-markdown-content > p:first-of-type::after`, and a restated `.shell-session .shell-input-cursor.is-active { animation: none; opacity: 1; }` (restated at the base rule's own two-class specificity — it would otherwise outrank the gate and keep blinking while focused). Cursors stay **VISIBLE, just steady** — full opacity when `.is-active` (focus still reads as "live"), the existing 0.35 idle opacity from the unchanged base rule otherwise; the doc-page `▊` likewise steady. Only `animation`/opacity touched — colors stay on `--c-*` vars, both themes for free (Constitution V).

## GNU-utils delight pass (change `o33t`)

After `23xc`/`by18`/`n23o`/`cuur` the terminal was discoverable, reachable, shell-like, and accessible — but its command surface was thin (~18 keys): almost everything a real terminal user instinctively types (`pwd`, `uname`, `make`, `vim`, `tar`, `yes`, `rm -rf /`) dead-ended on `command not found` — an invitation revoked. Change `o33t` (backlog `[o33t]`, deliberately sequenced last) grows `COMMANDS` to 51 keys with **33 new unlisted easter eggs** plus the infrastructure they ride on. Pipes, a virtual filesystem, and all filter commands (`wc`/`sort`/`cat`/…) were split to the speculative draft `260610-42my-terminal-pipes-virtual-filesystem` and are NOT here; `top`/`htop` (needs in-place line rewriting the print model doesn't have) and the shareable transcript (re-logged as backlog `[tx5p]`; since landed as change `tx5p` — § The share→replay loop) are likewise out.

### Curation rule and roster

Every egg must do at least one of: **teach the toolkit**, **reward terminal-culture recognition**, or **demo interactivity** — no bare error stubs without a punchline (user-approved rule from the originating 2026-06-10 discussion). The bare `help` list, `CHIP_COMMANDS`, greeting, and ghost hint are **byte-identical** to pre-change: every new command is an unlisted egg, discovered organically, answering `help <cmd>` and `man <cmd>` via its `HELP_DETAIL` entry (the cuur convention — every `COMMANDS` key has one).

### The `Object.hasOwn` own-property-guard idiom (review-cycle lesson, load-bearing)

A plain-object record keyed by **user input** must never be read bare: an unguarded `record[name]` walks the prototype chain. Pre-rework, `echo $constructor` printed Object's source, and `man constructor` / `help constructor` / a bare `__proto__` command returned an inherited, truthy, non-conforming member — `print()` threw BEFORE `freshPrompt` could run, leaving the terminal with **zero prompts** (bricked until reload — the one-trailing-prompt invariant's worst failure mode). Review cycle 1 added `Object.hasOwn(record, key) ? record[key] : undefined` at **all four** user-keyed lookups — `expandVars`'s env read, the `man` `HELP_DETAIL` bridge, `helpFor`, and `run()`'s `COMMANDS` dispatch — so prototype-chain names hit the normal not-found branches. One idiom at all four sites (ES2022, comfortably in-baseline; no `hasOwnProperty.call` fallback). **Any future record lookup keyed by user input MUST use this guard.**

### The line streamer (Tier C engine)

`initTerminal`-scope `activeStream` (interval id) + `streamFollowup` (pending onDone timer, the rm-deluxe beat) with `startStream(lines, { intervalMs, onDone? })` / `stopStream()`, living beside cuur's `pendingNav`. The contract:

- **At most one stream**: `startStream` first calls `stopStream()`.
- Lines are emitted **one per tick via `printBeforePrompt()`** — output lands above the live prompt, so the exactly-one-trailing-prompt invariant holds **by construction** (the Tab ambiguous-listing precedent). `onDone` (if any) runs after the last line.
- **Reduced motion**: no interval — all lines print at once and `onDone` runs immediately (the `23xc` ghost-hint precedent: streams are timing, but their visual effect is motion; reduce gets the content without the cadence). This built-in dump is the engine's DEFAULT, not a mandate: a handler MAY branch on `prefersReducedMotion()` BEFORE streaming and print a designed static substitute instead — `yes` swaps in its `YES_REDUCE_COUNT` variant, `play` (change `jf9k`) prints only its settled `endFrame` (§ The illustrated shorts), and `cmatrix` (change `kd5e`) prints one static `CMATRIX_REDUCE_LINES` frame block (§ The terminal toys).
- **Three kill paths**: the **Ctrl-C** branch calls `stopStream()` beside its `pendingNav` clear (the frozen `^C` + fresh prompt + halted output read exactly like killing a foreground process); the **Ctrl-L** branch calls it (wiping a screen `yes` keeps flooding would un-clear it instantly; the `clear` command inherits the same kill via commitLine); and **`commitLine`** calls it before `run()` — placed AFTER the empty-line short-circuit, so a bare Enter during `yes` does NOT kill the stream, just like a real shell. `stopStream()` clears BOTH ids, so Ctrl-C aborts the rm-deluxe followup beat too.
- **Deliberate contrast with `pendingNav`**: `commitLine` kills streams but does NOT clear `pendingNav` — the nav beat is 900 ms and already announced its destination; streams are long-lived and would interleave with the new command's output. The asymmetry is documented at both sites.
- Frame lines typically carry `ariaHidden: true`; the closing summary line is announced. The one exception: `tail`'s log lines are announced (slow cadence, meaningful content).

**`printBeforePrompt` gained a no-live-prompt append fallback** (gated on `input.isContentEditable`): reduced-motion streams run synchronously inside `run()`, when the previous input is frozen but still carries its stale `data-terminal-prompt` attribute — a bare `closest()` lookup would insert output ABOVE the just-echoed command. With no LIVE prompt the function appends, exactly where `print()` would land the line. Two supporting extractions: `makeLineEl(ln)` (line-element construction shared by `print()` and `printBeforePrompt()` — where `ariaHidden` is honored) and `prefersReducedMotion()` (one media-query helper for the streamer, `yes`, rm-deluxe, and the `23xc` ghost hint, refactored onto it).

### `Line.ariaHidden` and the announcement policy

`Line` gains an optional `ariaHidden?: boolean`; `makeLineEl` sets `aria-hidden="true"` on the element when true. Policy: **ASCII art and rapid stream frames are announcement garbage** to the cuur live region — each art/animated command hides its frame/art lines and announces exactly **one readable summary line** instead. (The rule is per command OUTPUT; its one sanctioned multi-moment extension is snake's input-owning game session, change `kd5e` — three announced moments, board rewrites still hidden: § The terminal toys.) ### The anti-drift contract (load-bearing)

The handler **recomputes coverage at runtime on every run** via `buildCheatsheet(CHEATSHEET_GROUPS, CHEATSHEET_ALIASES, Object.keys(COMMANDS))`:

- **`covered`** = every group entry key ∪ every alias key; **`missing`** = `COMMANDS` keys not in `covered` → appended as a final **`uncategorized`** group (bare keys, `COMMANDS` declaration order, the exported `UNCATEGORIZED` const). ## The share→replay loop (change `tx5p`)

After `37ng` the terminal was a 60-command destination, but the fun was a dead end — a delighted visitor had no way to *show* anyone (the share idea `o33t` descoped and re-logged as `[tx5p]`). Change `tx5p` converts play into reach with two halves that close one loop: a **`share` command** that copies the visible session as a self-advertising plain-text block, and a **`#play=` deep-link replay** that auto-types and runs a pre-baked command sequence on load. `share` emits the very `#play=` link the replay engine consumes, so a pasted transcript advertises a link that reproduces the session. Hash-only state — no server, no POST, no paste service (Constitution I); clipboard + URL are the whole mechanism, zero new deps (Constitution VI); `index.mdx` byte-identical; `terminal.css` untouched (no new styled surface, no new focusable UI — `share` is a command, replay is non-interactive output).

### The `share` serializer contract

`collectTranscriptLines()` (island-side) walks every `span.shell-line` in **DOM order** by `textContent` — the export mirrors what the EYE sees, so visually-present `aria-hidden` art rows (the `shll` splash, the `sl` train) ARE included (their SR-noise control is a live-region concern, not a visual one). A LIVE prompt line is excluded, gated on `input.isContentEditable` (the `printBeforePrompt` gate — frozen lines retain a stale `data-terminal-prompt` attribute); during `run()` the previous input is already frozen, so in practice every line is captured including the just-echoed `$ share`, and the draft text / ghost-hint span can never leak. The pure lib's `serializeTranscript(lineTexts, {playLink?})` assembles the block: per-line **trailing**-whitespace trim (leading kept), `SHARE_HEADER` first (`# captured from the shll.ai terminal — yes, the homepage is a real shell.` — site's voice, authored at apply, the o33t reversible-copy precedent), the **bare `$` live-prompt line appended by the lib itself** (the exactly-one-trailing-prompt invariant carried into the export — the rule lives inside the tested module, and during `run()` the append is positionally always correct), the literal `SHARE_FOOTER` (`# replayed from https://shll.ai` — backlog-literal brand copy), and — only when a `playLink` is given — a second `# replay it: {link}` footer line.

### Clipboard: async API → execCommand fallback → honest failure

`copyShareText` tries `navigator.clipboard.writeText` (share always runs from a user gesture — Enter or a chip tap — so transient activation is present); where the API is absent or rejects, `copyViaExecCommand` appends a readonly `position: fixed; opacity: 0` textarea, `select()`s it, and runs `document.execCommand('copy')`. **Removal + focus restore run in a `finally`** (review hardening): an invisible focused textarea left in the DOM on a `select()`/`execCommand` throw would swallow every subsequent keystroke. Focus restore is **GENERIC** — whatever element held focus before the copy gets it back (`document.activeElement` captured up front, restored only when it was a connected `HTMLElement` other than `body` — never *initiating* focus, so a chip-path share where `body` held focus keeps it), with `caretToEnd()` re-placed only for the contenteditable prompt (a blur resets the caret — the rm-deluxe conditional-restore precedent). Both paths failing resolves `false`, never throws (the sessionStorage try/catch discipline); the handler then prints `clipboard unavailable — here's the transcript, copy it by hand:` followed by the block's lines in-terminal (`shell-out shell-dim`) — never a silent no-op.

The handler serializes synchronously inside `run()` but the copy resolves async — by then `commitLine` has emitted the fresh prompt, so the confirmation (`transcript copied — paste it anywhere.`) and the link line land via `printBeforePrompt` above it (the `sha256sum` placement precedent). The printed `replay link: {link}` line is **plain selectable text, deliberately NOT an `html: true` anchor** — the href would embed user-derived content (the commands the visitor typed); the trusted-static-string pattern of `man`/`ls`/`toolNavLine` does not extend to user-derived hrefs. Both the printed link and the link footer are built from `location.origin + location.pathname` (works on previews/dev) + `buildPlayHash(sessionCommands)`; only the `# replayed from` footer stays the literal brand domain. With zero recorded replayable commands the hash is `''` and the link line AND link footer are omitted — the transcript still copies.

### The `#play=` grammar (lib: `parsePlayHash`)

Parsed at activation — AFTER the greeting, the resting anchor, and `armIdleHint()` settle — from the **RAW fragment via `new URL(location.href).hash`, NOT `location.hash`** (longstanding Firefox behavior returns `location.hash` percent-decoded, which would break the contract below two ways: an encoded `%2C` inside an arg would arrive as a raw separator, and tokens would be double-decoded — review cycle 1). Grammar: `#play=` + comma- OR semicolon-separated command tokens. Tokens are split on the raw separators FIRST, then `decodeURIComponent`-decoded **per token** in a guarded try/catch — an encoded `%2C` inside an argument survives as a literal comma, and a malformed %-sequence drops THAT token only, never the whole sequence (the sessionStorage discipline). Trimmed, empties dropped, non-replayable tokens skipped SILENTLY (no error lines), survivors capped at `REPLAY_CAP = 10` (the cap counts SURVIVORS — skipped tokens consume no slots). No hash / non-play hash / zero survivors → `[]` → `startReplay` no-ops, byte-for-byte today's load. The hash is deliberately left in place (no `replaceState`) — a reload replays again; a deep link is replayable by definition.

### The shared replayable predicate (`isReplayable` — the hasOwn idiom inside the lib)

A command is replayable iff its `firstWord` (first whitespace-delimited token, LOWERCASED — matching `run()`'s dispatch case-folding, so `LS` records and replays consistently while the token itself stays verbatim) is an **own** key of `COMMANDS` via `Object.hasOwn` (the o33t idiom is MANDATORY — the hash is user-controlled input keying a record lookup; `#play=constructor`/`__proto__`/`toString` replay nothing) AND is not in **`REPLAY_DENY`** — `['cd', 'open', 'install', 'share']` at tx5p (user-confirmed, intake clarification #15), grown to **five entries by change `kd5e`: `'snake'` joins** (an unrequested input-owning game is the input-side version of the navigation yank the charter prevents; `cmatrix`/`cowsay` replay faithfully — § The terminal toys): a URL-controlled sequence must never fire `window.location.assign` mid-replay and yank the visitor off the page they were just handed a link to, and a gesture-less replayed `share` would only hit the clipboard permission wall. Everything else — `clear`, `theme`, the eggs, the animated streams — replays faithfully. Deliberately unlike cdbr's `commandKeys: string[]` decoupling, the lib takes the `COMMANDS` record and applies `Object.hasOwn` INSIDE — so the prototype-chain guard itself is directly pinned by the test suite. **One predicate, two call sites** (the `commitLine` recording and the hash parse) — recording and parsing can never drift, so a generated link replays exactly what it claims. (Since change `4vkd` that contract has exactly one named exception — the post-demo share link, whose tail is dropped by the queue-replacement semantics: § The scripted demo/tour.)

### The replay engine

`initTerminal`-scope state beside the streamer: `replayQueue: ReplayStep[]` (since change `4vkd` — steps `{ narration?, command }`; tx5p shipped a bare `string[]` queue), `replayTimer` (pending start-delay or inter-step gap), `replayTyper` (active per-character typing interval), plus the `4vkd` per-sequence state `replayGapMs`/`replayOnDone`/`replayEpoch` (§ The scripted demo/tour). `startReplay(commands)` is the `#play=` entry — since `4vkd` it maps bare tokens to narration-less steps and delegates, byte-identically, to the internal `startSequence(steps, { gapMs?, onDone? })` (pre-`4vkd` all of the following lived in `startReplay` directly). The sequence start:

- no-ops on an empty list; otherwise **stops any in-flight sequence first and bumps `replayEpoch`** (change `4vkd` — starting a machine sequence REPLACES the previous one) and **dismisses the idle ghost hint** (machine interaction is still interaction; the one-shot latch never re-arms — the hint must not type over a replay);
- under **`prefersReducedMotion()`**: each step's narration prints, its command is filled at once and committed via `commitLine(false)`, back-to-back, **fully synchronously** — no per-char typing, no inter-step gaps, and no start delay either (the whole sequence resolves instantly; the streams a replayed command starts already print all-at-once under reduce). Nothing is ever in flight on this path, so the kill listener below is never installed. Since `4vkd` the loop is epoch-guarded between steps, conditionally focus-preserving per step, and deferred by one `queueMicrotask` when started inside `run()` (§ The scripted demo/tour);
- otherwise installs the **document-level capture-phase `keydown` kill listener** (§ The kill switch), captures the per-sequence `replayGapMs`/`replayOnDone`, and schedules `replayNext` after `REPLAY_START_DELAY_MS = 600` (lets the greeting print and the resting anchor settle).

`replayNext` first prints the step's narration line(s) when present (demo steps only — announced `shell-out shell-comment` via `printBeforePrompt`, change `4vkd`; `#play=` steps carry none), then types the command character-by-character into the live `input.textContent` at `REPLAY_TYPE_MS = 70` (the `HINT_TYPE_MS` cadence — "the existing typing cadence"), then commits via **`commitLine(false)`** — the by18 chip path: full commit semantics (history push, `sessionCommands` recording, stream kill, `exitResting`, fresh prompt) with NO focus steal — then waits the per-sequence `replayGapMs` (`REPLAY_GAP_MS = 700` for bare replays; `DEMO_GAP_MS = 1400` for the demo — change `4vkd`) before the next, after first yielding if the committed command started its own sequence (the `replayEpoch` guard, § The scripted demo/tour). On natural completion it captures `replayOnDone`, runs `stopReplay()`, then invokes the hook (the demo's closing CTA — change `4vkd`; `undefined` for bare replays). A replayed stream-starter (`yes`, `tail`, `sl`, rm-deluxe) runs for the gap window; the next command's `commitLine` kills it — the existing commit-kills-stream contract, no special-casing. All four cadences are named island constants per the `HINT_*`/`NAV_BEAT_MS` convention (`REPLAY_CAP` lives in the lib, shared by parse and build). A defensive empty-queue branch in `replayNext` calls `stopReplay()` (normally unreachable — natural completion stops after the last commit) so cleanup is unconditional and the document listener can never be orphaned (review hardening).

**Focus: preservation, not initiation (the 23xc no-autofocus lineage).** Replay never calls `focus()`/`scrollIntoView` to *initiate* focus, and page scroll is untouched (the session's internal bottom-pinning after each commit is normal post-interaction behavior). But if the user clicks/Tabs into the input *mid-replay*, the next commit's `freezeInput()` strips `contenteditable` from the focused element and focus would silently fall to `body` — so the engine captures `document.activeElement === input` before its commit and restores focus + `caretToEnd()` onto the fresh prompt after it ONLY in that case (the rm-deluxe conditional-restore precedent at the wipe site; preserving user-established focus is not focus-stealing).

### The kill switch (`stopReplay`)

A replay is interruptible like a paste-bomb. `stopReplay()` empties the queue, clears the typing interval and the pending start/gap timer, clears the `replayOnDone` completion hook (change `4vkd` — an interrupted tour prints no closing CTA), and removes the document-level listener; it is idempotent and cheap, so call sites need no `replayActive` flag. Wired into:

1. The **document-level `keydown` listener** — installed by `startSequence` (the engine entry every animated machine sequence passes through, bare replay or demo; pre-`4vkd` the install lived in `startReplay` directly), removed by `stopReplay`, registered AND removed with **`{ capture: true }`** (an intermediate handler calling `stopPropagation()` — e.g. a search dialog — must not be able to swallow the interrupt; review hardening). This listener is load-bearing, not belt-and-braces: replay never focuses the input, so on a canonical `#play=` load `document.activeElement` is `body` and the input-scoped `onKeydown` can never fire — without it NO keystroke (Ctrl-C included) could stop a replay (review cycle 1 must-fix). It exists only while a replay is in flight — zero cost idle.
2. The input's **`onKeydown` first statements** (immediately after `dismissIdleHint()`, before branch dispatch — the placement precedent), so any keystroke ⊇ Ctrl-C interrupts when the input IS focused.
3. The **chip-tap handler** (`onChipClick`) — the touch analogue.
4. The input's **`paste` handler** — a mouse-driven context-menu paste is an interaction too.

**`commitLine` does NOT call `stopReplay`** — replay commits through `commitLine` itself: user action kills the replay; the replay's own machinery must not (the deliberate asymmetry, documented in-code, mirroring the `pendingNav` contrast). Interrupting mid-word freezes whatever was typed — the next user action deals with the partial line exactly as if hand-typed. **The one machine path that stops a sequence (change `4vkd`)**: a machine-committed `demo`/`tour` calls `startSequence` inside `commitLine`'s `run()`, which `stopReplay`s the outer sequence and replaces it (the queue-replacement semantics; the outer continuation yields on the `replayEpoch` guard) — replacement by a new sequence, still never `commitLine` itself.

### Recording: what the link contains (`sessionCommands`)

A new `initTerminal`-scope `sessionCommands: string[]` records, in `commitLine` (after the history push, before `stopStream`), each committed raw line iff `isReplayable(raw, COMMANDS)` — nav commands and `share` itself fail the predicate (`REPLAY_DENY`) and are never recorded. Deliberately NOT `history[]` (sessionStorage-persisted across page views — it would not match the visible transcript) and never persisted anywhere (page-view-scoped; hash-only state). `buildPlayHash` builds `#play=` + the **first `REPLAY_CAP` commands in commit order** (the transcript reads top-down and the replay should too), each `encodeURIComponent`-encoded, comma-joined; `''` on an empty list. Recording pushes every predicate-passing commit and `buildPlayHash` caps — one cap site, in the tested lib. Build→parse round-trips for any replayable input.

### The step-generalized engine (`startSequence`)

The tx5p replay engine is generalized from a queue of bare command strings to a queue of **steps** — `ReplayStep = { narration?: string[]; command: string }` (a new island type beside `Line`/`Ctx`):

- **`startReplay(commands)` keeps its signature** and becomes the narration-less mapper: it converts `#play=` tokens to `{ command }` steps and delegates — the bare-replay path is behaviorally byte-identical (same cadences, gaps, start delay, `commitLine(false)` commits, conditional focus capture/restore, kill-listener lifecycle, recording).
- **`startSequence(steps, { gapMs?, onDone? })`** is the internal engine entry (the `startStream(lines, { intervalMs, onDone? })` options-shape precedent): it stops any in-flight sequence first (the `startStream`-stops-previous precedent — **starting a machine sequence REPLACES the previous one**), increments `replayEpoch`, dismisses the idle hint, and — on the animated path — captures the per-sequence `replayGapMs`/`replayOnDone`, installs the document-level kill listener (which therefore now lives in `startSequence`, not `startReplay`), and schedules at `REPLAY_START_DELAY_MS = 600` (both entry paths — a typed `demo` starts 600 ms after its opening line prints).
- New `initTerminal`-scope engine state: **`replayGapMs`** (per-sequence inter-step gap — `REPLAY_GAP_MS = 700` default; the demo passes **`DEMO_GAP_MS = 1400`**, a named constant beside the other cadences: a demo step prints narration plus a multi-line tool card the visitor must actually *read*, where replay's 700 is tuned for already-seen content), **`replayOnDone`** (the natural-completion hook), and **`replayEpoch`** (below).
- **Narration prints before typing**: `replayNext` prints the step's narration line(s) via `printBeforePrompt` — classes `shell-out shell-comment`, **no `ariaHidden`** (the narration IS the story and is announced to the live region; the `tail` announced-exception precedent) — landing above the live prompt, so the exactly-one-trailing-prompt invariant holds by construction. Then the command types at `REPLAY_TYPE_MS = 70` and commits via `commitLine(false)` as before.
- **The `replayEpoch` re-entrancy guard**: a machine-committed command can start its OWN sequence synchronously inside `commitLine` (`demo`/`tour` — `startSequence` stops the outer sequence and takes over the queue/timers/listener). The outer continuation captures the epoch before its commit and yields when it changed — without the guard it would double-schedule against the new sequence's timers. Applied on BOTH the animated and reduced-motion paths. Consequence: **a replayed `demo` (`#play=demo,fortune`) replaces the queue and the surviving tokens after `demo` are dropped** (documented in code); `demo` while a demo runs restarts it.
- **Completion**: after the last step's commit `replayNext` captures `replayOnDone`, runs `stopReplay()` (cleanup — which clears the hook), then invokes the captured hook. So **the closing CTA prints on natural completion ONLY**: an interrupted tour earns no pitch; already-printed narration stays and the partial line freezes like a hand-typed abort (the stream-frame precedent). All four tx5p kill paths (document-level capture-phase listener, `onKeydown` first statements, chip taps, paste) are inherited unchanged; `commitLine` still deliberately does not stop a sequence (§ The kill switch).

### `DEMO_SCRIPT` — the tour content

A module-scope const beside the other rosters (the `SYNOPSIS`/`FAKE_ENV`/`CHEATSHEET_GROUPS` precedent), shaped `{ opening: Line; steps: ReplayStep[]; closing: Line[] }`. The opening line **self-announces interruptibility** — `# the shll toolkit in ~60 seconds — any key bails out.` (the o33t honest-machinery ethos: self-identifying machinery). Five steps with commands `idea`, `fab`, `wt`, `rk`, `tu` — the **binary-alias keys** where they exist (shorter to watch being typed; same card as their primaries); `hop` is omitted to keep the tour tight at five steps — each preceded by one `#`-prefixed narration line (`# 1/5 — it starts with an idea. capture it before it evaporates:` …). The closing block names the **workflow**, not all seven binaries (`# that's the loop: capture → plan → isolate → watch → account.`) and lands the conversion beat: `# get it: type 'install' ⏎ — or click …` with a **printed clickable anchor built from `ROUTE_INSTALL`** (`html: true` — the `man`/`ls`/`toolNavLine` trusted-static-string pattern: a static route constant, never user-derived). Copy authored at apply in the site's voice (the o33t reversible-copy precedent); every line within the ~74-char width discipline (the GREETING/`CHEAT_LINE_WIDTH` precedent — longer lines clip into horizontal scroll under `white-space: pre`).

**The handler**: `demoHandler` prints `DEMO_SCRIPT.opening` immediately via `print` — NOT a returned `Line[]`, because under reduced motion `startSequence` resolves the whole tour synchronously inside the handler call and a returned opening would print after the entire tour — then calls `startSequence(DEMO_SCRIPT.steps, { gapMs: DEMO_GAP_MS, onDone: printDemoClosing })`. `printDemoClosing` prints the closing block via `printBeforePrompt` above the final prompt.

**The tour NEVER auto-navigates** (user-confirmed): a machine-fired `window.location.assign` would yank the visitor off the page mid-read — the exact hostility `REPLAY_DENY` exists to prevent — and would make `demo` itself non-replayable. The printed anchor + typed invitation are the ending; `window.location` is never touched.

### tx5p composition — `demo` is replayable, with one named fidelity exception

`demo`/`tour` are deliberately **NOT in `REPLAY_DENY`** (`terminal-share.ts` unmodified) — `isReplayable` passes, so **`#play=demo` is a one-token shareable link that plays the whole narrated tour**. Safe only because the tour never navigates (above).

**The accepted share-link fidelity corner** (review should-fix, accepted as-is and documented in code): the demo's machine commits — `demo` itself, then `idea`/`fab`/`wt`/`rk`/`tu` — all pass the replayable predicate in `commitLine` and land in `sessionCommands` like any commit, so a post-demo `share` link reads `#play=demo,idea,fab,wt,rk,tu,…`: the demo's own machine-committed steps consume `REPLAY_CAP = 10` slots (post-demo user commands can be pushed past the cap), and on replay `demo` REPLACES the queue (the `startSequence` replacement semantics), so **everything after `demo` is dropped** — the tour replays; any recorded post-demo user commands do not. This is the one **named exception** to tx5p's "a generated link replays exactly what it claims" contract — accepted because it is self-healing (the duplicated tail never double-plays; the replayed result is the narrated tour the link advertises) and because suppressing machine-commit recording would fork `commitLine`'s single-path semantics for a harmless cosmetic.

### Reduced motion — synchronous, with the in-run microtask deferral

Under `prefers-reduced-motion: reduce`, `startSequence` resolves the whole sequence synchronously: per step — narration via `printBeforePrompt`, fill the command at once, `commitLine(false)` — with the `replayEpoch` guard between steps and `onDone` (the closing block) gated on the epoch; no per-character typing, no gaps, no start delay, and **no kill listener** (nothing is ever in flight). Per-step **conditional focus capture/restore** (preservation, not initiation — the `replayNext`/rm-deluxe precedent): a typed `demo` reaches the loop with the input focused (Enter's `freshPrompt(true)`), and each commit's `freezeInput` would silently drop that focus to `body`; at activation (`#play=` under reduce) nothing holds focus, so the capture is a no-op — byte-identical to the pre-`4vkd` loop.

**The in-run deferral**: started from inside `run()` (a typed or replayed `demo`), the previous input is frozen and the live prompt doesn't exist until the in-flight `commitLine` emits it — filling the frozen element would corrupt the just-echoed `$ demo` line. The synchronous run is deferred by exactly one **`queueMicrotask`** (gated on `input.isContentEditable` — the `printBeforePrompt` no-live-prompt precedent): the microtask runs after the in-flight commit completes (live prompt exists) but BEFORE any user event can be processed (events are tasks, not microtasks), so nothing is ever observably in flight. The activation path (`#play=demo` at load) runs synchronously with no deferral, as before.

### `snake` — the first input-owning surface (the real work)

Every prior command was a one-shot or a finite stream; even the replay engine only *types at* the prompt. `snake` is the island's first surface that **owns the keyboard** and **rewrites the DOM in place** — two deliberate firsts, each with a sanctioned mechanism:

- **The in-place board (a sanctioned bypass of the stream engine).** A game cannot be append-only — it must redraw the same cells — so the board does NOT ride `startStream`: `startSnake()` appends **ONE aria-hidden `shell-line shell-out` container directly to `session`** (the `sl`-train direct-DOM precedent; `run()` executes before `commitLine`'s `freshPrompt`, so the board lands above the live prompt by construction) and each tick rewrites its `textContent` (lib-rendered board rows + the island's status row, newline-joined — one block element, scroll never touched mid-game). Geometry: **`SNAKE_COLS = 46` × `SNAKE_ROWS = 10` interior** (48×12 with borders + a status row) — sized so board + status + game-over line + live prompt fit the 22 rem (~14.5-line) session viewport without `scrollToBottom` cropping the top border; **`SNAKE_TICK_MS = 140`** reads as classic terminal-snake speed. Head/body/food are `@`/`o`/`*` (`SNAKE_HEAD`/`SNAKE_BODY`/`SNAKE_FOOD`); the status row shows the live score.
- **The pure game core lives in the lib.** `snakeInit`/`snakeTurn`/`snakeStep`/`renderSnakeBoard` are pure `state → state`/`state → string[]` functions in `terminal-toys.ts`: steering with the **180° reversal guard**, grow+score on food with respawn on a free cell, wall AND self collision with the **tail-vacated-cell allowance** (moving into the cell the tail is leaving is legal), and the bordered render incl. the centered `SNAKE_BANNER` game-over overlay. The island owns ONLY the timer, the DOM writes, and the key wiring (`snakeGame = { state, board, timer }`).
- **Input takeover: a game-mode flag at the TOP of `onKeydown`.** `snakeGame !== undefined` is the flag; the branch sits after the `dismissIdleHint()`/`stopReplay()` first statements and BEFORE every existing branch (Ctrl-combos/↑↓/Tab/Enter), delegating to `handleSnakeKey(e)` — the o33t stream-cancel + key-capture discipline extended from "any key kills the replay" to a real takeover. While active: **arrows AND WASD steer** (lowercased `e.key` against the `SNAKE_KEY_DIRS` record, `Object.hasOwn`-guarded — the o33t idiom; `preventDefault` is load-bearing — arrows otherwise drive history recall and page scroll); **`q` and plain Ctrl-C quit** and release; **plain Ctrl-L tears the game down and falls through** (`handleSnakeKey` returns false ONLY here — the normal Ctrl-L branch then clears the transcript, board included, and emits its single prompt: the prompt invariant stays owned by the existing paths); `r`/Enter restart on a game-over board; **printable chars and the `SNAKE_SWALLOW_KEYS` navigation set** (Tab/Enter/Backspace/Delete/PageUp/Down/Home/End) are swallowed — nothing types into the prompt mid-game, Enter cannot commit; **other modified combos (Ctrl-Shift-C copy, Cmd-R, …) bypass the terminal's branches but are never `preventDefault`'d** — browser chrome stays usable (swallowing exists to protect the prompt, not to jail the tab). On quit the flag clears and every existing key path resumes untouched.
- **Focus-scoped capture, deliberately no document listener.** The capture rides the focused input's `onKeydown` (Enter's `commitLine(true)` focuses the fresh prompt, so keys arrive by default); the tx5p document-capture pattern was rejected — it exists for replay, where nothing holds focus. Clicking away pauses steering until the terminal is clicked again — an accepted egg-grade tradeoff.
- **Game over → restart → quit.** On collision `snakeTick` stops the clock but keeps the game-mode flag (the over state still owns the keys), `renderSnakeBoard` freezes the board under the banner, and `game over — score: N` is announced via `printBeforePrompt`. `r`/Enter restarts in the SAME container with score 0; `q`/Ctrl-C calls `quitSnake()` — teardown + the announced `(snake: keys released — final score N.)` confirmation (without it no user, sighted or not, has a signal that typing works again). **Quit deliberately leaves the frozen board in the transcript** (the `sl` train removes itself; a frozen final board is the better share/screenshot artifact).
- **Three announced moments (the sanctioned multi-moment exception).** The o33t rule — one announced summary per command output — was written for one-shot output; an input-owning *session* has three meaningful moments, each announced exactly once: the start controls line (`snake — arrows/wasd steer · q quits`, printed via `ctx.print` BEFORE the board appends), `game over — score: N` per crash, and the quit release. Every board rewrite stays aria-hidden live-region garbage.
- **Teardown edges & the prompt invariant.** `commitLine` calls **`teardownSnake()` beside its `stopStream()`** (the commit-kills-stream contract extended to game teardown) — mid-game the only commit path is a by18 chip tap, since typed keys are swallowed; the chip's command must not race a live game loop (the frozen board stays as the artifact). `teardownSnake()` is the silent timer+flag clear shared by quit, commitLine, and the game branch's Ctrl-L path. The handler is a `void` handler (the `demoHandler` shape); quit/game-over lines ride `printBeforePrompt` — the exactly-one-trailing-prompt invariant holds on every path (start, tick, game over, restart, quit, chip, Ctrl-L).
- **Reduced motion: an honest decline.** Under `prefers-reduced-motion` the handler returns only the static note `snake needs motion — your system prefers reduced, so the game sits this one out.` — no board, no timer, no key capture (the backlog sanctioned decline-or-pause; declining ships no motion to users who opted out — the AGENT_LOG honest-machinery lineage). Per-toy reduced-motion postures, summarized: cowsay static print (no interaction), cmatrix ONE static frame block, snake declines.

## Accessibility

- The input is a real focusable, keyboard-navigable control: `contenteditable="true"` with `role="textbox"`, `aria-multiline="false"`, an `aria-label`, and `spellcheck`/`autocapitalize`/`autocorrect` off, plus an explicit `paste` handler that forces `text/plain` and flattens newlines (so a multiline/formatted clipboard payload can't distort the single prompt line — robust regardless of `plaintext-only` browser support, a PR-review fix). (No `tabindex` is set — `contenteditable` is the deliberate native-focusable mechanism.)
- **Block cursor, not the OS caret.** The native text-caret is hidden (`caret-color: transparent`) and a trailing `.shell-input-cursor` block (`▊`, reusing the static skin's `.shell-cursor` glyph + `shell-blink`) stands in, so the prompt reads like a TTY rather than a form field. The block blinks only while focused (`.is-active`, toggled on `focus`/`blur`); idle it is dimmed and steady. There is **no** focus-ring box outline (it read as a form field — removed).
- **Click anywhere in the terminal focuses the prompt** (caret to end), matching how a real terminal grabs the cursor. The handler skips clicks on links (let them navigate), skips when text is selected (don't steal a copy-selection), and skips clicks inside the command bar (a chip commit must not summon the soft keyboard — change `by18`); the surface gets `cursor: text` to hint it's typeable.
- The command-bar chips (change `by18`) are native `<button>`s — tap, Enter, and Space all fire `click`, keyboard-navigable for free — with a visible `var(--c-accent)` `:focus-visible` outline; the bar carries `role="group"` + `aria-label="quick commands"`.
- `cd` / `open` / `install` / `man` resolve to **real** `window.location` navigation, never a JS-only dead end — since change `cuur` the first three go through `navigateWithBeat` (a printed clickable anchor + a 900 ms cancellable beat), so the link is also directly tappable/clickable. No-JS users keep the static transcript's working `<a>` links; the enhancement never removes or hides them.
- **Command output is announced to screen readers** (change `cuur`): `pre.shell-session` is an `aria-live="polite"` / `aria-atomic="false"` region set at activation before the greeting prints; each fresh prompt's `$` span is `aria-hidden` so prompts don't announce noise (see § Command polish & accessible output).

## Design Decisions
